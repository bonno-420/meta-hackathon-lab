# loop-031 — チェックポイントの質問を、ターミナルの外でも返すようにする

2026-11-05 朝。実施: 統括（本人の指摘による）。

## 本人の指摘（発端）

- Sorano の走行（runs/sorano-wheel、別ラインの実行）で、承認で止まった報告に**承認の質問そのものが含まれていなかった**。ラインの説明: 「選択形式の質問が出るのは対話端末（TTY）で実行したときだけ。エージェント実行では出ない仕様」。
- 本人の評価: 「こんなの誰が使うの？」「俺ならダウンロードしない」「よかった出さなくて」「恥ずかしい」。
- 事実として: loop-029 で統括が実装した質問フローは TTY 判定（make-lp.mjs の INTERACTIVE）の内側にだけあり、本人の実際の運用（チャット経由のライン実行）では質問が一度も現れない作りだった。「求人票を投げたら次はチェックポイント」という本人の要件に対し、製品の中心の対話が到達不能だった。

## 修正（make-lp.mjs のみ。run-demo・ゲートは不変）

- 非対話実行でも、チェックポイントで止まったら **チェックポイントパッケージ**（生成物の提示・質問文・選択肢・回答コマンド）を出力して止まる。質問は実行形態によらず返る。
- 本人の回答は `node make-lp.mjs --resume <out-dir> --answer <choiceId> [--name] [--note]` で受け渡す。make-lp がその回答の記録（承認・1枚画確認・判定）を、対話フローと同じ記録作成処理で作り、走行を続ける。回答なしに記録は作られない。操作セッションは質問と回答の運搬であり、判断は本人のもの。
- 対話端末のフロー（プレビュー＋選択）は従来どおり併存する。ゲート停止はどちらの形態でも質問の対象にしない。

## 検証（統括の VM、非対話実行）

- FICT-E03 の新規走行（パイプ入力＝非対話）: 承認で停止し、パッケージ（事実18件の提示・質問・選択肢 approve/stop・回答コマンド）が出力された。
- `--answer approve` で再開: make-lp が承認記録を作成し、パイプライン自身の検証（approval stage）が pass、走行は企画を経て 1枚画の段階まで進行した。
- 1枚画の描画は、この VM に Chromium が入っておらず保留で停止した（playwright 未導入という環境要因。写真3枚の生成までは完了）。描画以降のチェックポイント（1枚画・文章・LP）への --answer は、同じ記録作成処理を使うが、この VM では未検証。導入が済み次第、同じ走行で続きを検証する。
- 全テストスイートへの影響: make-lp はスイートの対象外（従来どおり）。抽出ほか9スイートは loop-030 時点で全合格のまま。

## 追記: --answer の実走検証と、試して出た2つのバグ（2026-11-05 09:00–09:15）

検証走行 FICT-E03-ANSWERTEST / ANSWERTEST2（統括の VM、非対話、回答は --answer で受け渡し）:

- 承認: パッケージ出力 → `--answer approve` → make-lp が承認記録を作成 → パイプライン自身の承認検証 pass → 企画・1枚画へ進行。確認できた。
- 1枚画: 描画は当初この VM に Chromium がなく保留停止（環境要因）。導入後に再開すると完成イメージが描画され、チェックポイントで停止。`--answer confirm` → 確認記録の作成 → 生成へ進行。確認できた。
- 文章: 生成は実行されたが、ANSWERTEST2 では文章レビュー不合格で停止した（appeal-not-explanation 等の指摘）。これは機構の失敗ではなく、レビューゲートが品質で止めたもの（同じプロンプトで合格した走行もある領域のばらつき）。
- 試して出たバグ2件（いずれも「途中で手入れが要った箇所」として修正済み）:
  1. **記録のパスが絶対パスで書かれていた**（writeApproval / writeKvConfirmation が絶対パスを受けると相対化しなかった）。結果: 再開時にパスが二重化して読み込み失敗し、再検証の同一性チェックも落ちた（パイプライン側の不合格判定は正しい挙動）。loop-029 の対話フローにも潜在していた（KV 確認の往路は未検証だった）。修正: 記録のパスはリポジトリ相対に正規化する（relRoot)。
  2. **1枚画の確認ファイルが後段の再開で自動で渡らなかった**（run-demo は再開ごとに --kv-confirmation を要求する）。修正: make-lp は確認ファイルが存在すれば再開時に自動で渡す（kvExtra)。対話・非対話の両経路に適用。
- ANSWERTEST（1件目）はバグ1の混入した承認記録のため再検証で不合格となり、記録の手編集はしないため破棄した。修正後の ANSWERTEST2 で承認→1枚画の連鎖を再確認した。

## 着地の判断基準（2026-11-05 本人の言葉）

「着地の判断に使えるのは、版を固定して新しいチャットに求人票を貼り、その後の人の操作が『届いた実物を見て答える』だけだったか。途中で誰かがパスを直したり記録を補ったりしたなら、LPができても、その手入れが必要だった箇所が次に直す場所だよ。」

- 次の実地判定はこの基準で行う: 版を固定し、新しいチャットで求人票を貼り、人の操作が「答える」だけだったかを記録する。手入れが要った箇所は、次の修正対象として記録する。
