# 知見の集約と全体反映の抽出（loop-026、2026-11-04）

loop-022〜025 の実行記録と仕様棚卸しから、単一求人の出来事ではなく
全体（全求人の制作経路）に反映できるものを抽出した。

## 全体反映済み（制作経路に組み込み済み）

1. 見出しは仕事そのもの、短く（仕事＋場所）。契約・期間・訴求は本文の文に分ける
   （生成 v8、レビュー観点にも同じ物差し）
2. カードにならない訴求は「求人票の外の魅力」として、読み手への転換
   （こんな人に／こんな悩みに）で書く（生成規則＋レビュー観点 reader-conversion）
3. 募集要項はそれだけで把握できる形にする: 全事実の表＋原本の行だけが持つ
   必須項目（仕事内容・休日・応募資格）を原本のラベルのまま含める
4. 画像の生成前確認を設計に記録する（coverageChecks: ヒーローで説明できて
   いない大事な部分／福利厚生・待遇で必ず作るもの）。作業シーンはヒーロー＋1枚
5. 見出し選定の規則順序: KV が前面に出す訴求の規則を予備規則より先に適用する。
   仕事の帯は、見出しに取られた文の代わりに仕事の訴求の本文文を担う
6. 抽出の表記ゆれ（未記載項目の sourceLine 空文字）は照合・比較で null に
   正規化する（堅牢性）

## ゲート昇格の候補（本人の承認待ち — 昇格は D8 で本人が決める）

- G-A 完成チェック C7（決定的検査）: 募集要項に全 stated 事実と行の必須項目が
  存在することを機械で検査する（現在はページレビューの観点のみ）
- G-B 見出しの決定的スキャン: 見出し文が条件（雇用形態・期間）だけの文になって
  いないことと、長さの目安を機械で検査する（定型句スキャンと同型）
- G-C 画像設計チェックの拡張（G7）: coverageChecks（生成前確認）の記録がない
  画像設計を不合格にする

## 規定の挙動として設計するもの

知見の扱いは次の順序を規定の挙動とする（learning-flow の運用形）:
気づき → 集約（記録）→ 全体に反映できるものの抽出 → 制作経路への組み込み
（生成規則・レビュー観点・組み立て規則）→ ゲートへの昇格は本人の承認を経て
初めて行う。記録だけで終わらせない。本フローを docs/design の
learning-flow-statement への追記として提案する。
