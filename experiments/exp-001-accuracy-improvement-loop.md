# 実験 exp-001: 精度改善ループとオーケストレーションの目標達成率

- 状態: 設計済み（実施はループ2の live 実行から）
- 関連: `docs/decisions/D3-minimal-proof-scope.md`、`docs/decisions/D4-model-assignment.md`、`docs/model-selection.md`、`docs/prompts/loop2-implementation.md`

## 目的

サブ（Spark 1.3 Contributor）が実施と一次確認まで行い、Wonder が監査・判断するオーケストレーションで、監査 → 修正 → 再実行のループを回したときに、成果物の精度が実際に上がることを検証する。あわせて、その過程を数値で追える状態にする。

## 指標（定義）

- **目標達成率**: 完了条件を満たして監査で「合格」になったパス数 ÷ 実施したパス数。ループ単位の集計も併記する
- **差し戻し回数**: パスごとの差し戻し回数（監査 → 制作への差し戻し）
- **サブの自己検出率**: 監査で見つかった不備のうち、サブの一次確認で事前に申告されていたものの割合
- **エスカレーション率**: Wonder が直接実施に切り替えたパスの割合
- **達成あたりのコストと時間**: 合格1件にかかったトークン量・実費・所要時間

数値目標は置かない。まず測れる状態を作り、推移を見る（件数が少ない段階で率に目標を置いても意味が薄いため）。

## 対象（第1号）

ループ2の live 実行。FACT 抽出を実 API（Meta Model API）で実行し、E01・E02 の期待結果と照合する。現状はオフライン検証（照合ロジック、fixture 使用）まで完了し、live は `MODEL_API_KEY` の設定待ちで blocked が記録済み。

## 手順

1. サブが live 実行し、一次確認レポート（自己検出した不備を含む）を付けて返す
2. 監査（Wonder または統括）が、抽出の引用・行ID・判定・記録の完備を照合する
3. 不備があれば原因を特定し、修正は主要な変更を1要因だけにする（プロンプト / コード / 文脈供給のどれか）
4. 再実行する。同条件の再実行は「再現性検証」、1要因を変えた再実行は「改善実験」として区別して記録する
5. 結果（指標の実測）を本ファイルの結果表と `docs/model-selection.md` の台帳に記録する

## 判定

- ループを2周以上回し、目標達成率と差し戻し回数の推移が実測で記録できれば、本実験は「検証できた」とする
- 精度が上がらなかった場合も、それを結果として記録する（改善しないことの実測も知見）
