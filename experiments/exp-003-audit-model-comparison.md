# 実験 exp-003: 監査の実施モデル比較（Wonder と Spark）

- 実施日: 2026-10-28
- 状態: 完了（結果の解釈は統括の判断を含む）
- 関連: `docs/design/overall-audit-20261028.md`（Wonder 実施の全体監査）、`docs/design/exp-audit-spark-20261028.md`（本実験の監査記録）、`docs/model-selection.md`、`docs/decisions/D4-model-assignment.md`

## 目的と設計

- 目的: 監査の実施モデルを Wonder から Spark 1.3 Contributor に変えたとき、指摘の質と判定がどの程度保たれるかを実測する
- 変更要因は1つだけ: 監査の実施モデル。対象範囲と観点は、全体監査（Wonder）のうち2領域（記録の完全性、台帳の棚卸し）に揃えた
- 独立性: Spark のセッションには、Wonder の監査記録（`docs/design/overall-audit-20261028.md`）を読まないよう明示した。実施側も未読であることを報告した
- 対象の状態: 両監査とも HEAD `7a5c09f` 時点のリポジトリ

## 結果

- 判定: 両領域とも、Wonder が「修正」、Spark も「修正」で一致した。前段階への差し戻しは双方ともなし
- 指摘の一致（領域「記録の完全性」の中核3件は全て一致）:
  - `docs/model-selection.md` にループ10行がない【双方とも中】。Spark は原因（工程5の閉じ作業に台帳更新が含まれなかったこと）と回復方法（exp-001 第8行と run-record からの転記）まで特定した
  - exp-001 の表紙・集計が第3回時点のまま【双方とも指摘】
  - ループ3の独立監査レポートがリポジトリ内にない【Wonder は中、Spark は低。重大度の付け方に相違】
- Spark が追加で検出したもの（いずれも低）: L-010 の MIT 決定に独立した決定記録がなく根拠が弱い（F-04）、L-009 の「工程4ブリーフで判断を記録」の箇所が特定不能（F-05）、ほか受け入れ記録の粒度など3件
- Spark が検出しなかったもの: 全体監査の Spend Limit 確認の指摘。ただし当該項目は台帳の行ではなく roadmap 側の宿題であり、Spark は台帳の行に範囲を絞って読んだという観点の差がある。また本人の判断による取り下げ（2026-10-28）が実験直前にあり、リポジトリには未記録だった
- 所要時間: Spark は約6分（2領域）。Wonder の全体監査（7領域）の所要時間は未記録のため、時間の比較はできない

## 費用の比較について（限界）

- Spark セッションのトークン量と費用は、実施側に自己計測の手段がなく UNKNOWN だった。API の利用実績はツール別のキー単位でしか集計されないため、実験単位の実費は 2026-11-01 の Billing 突合でも分離できない
- したがって本実験は「質の比較」に限られ、費用対効果の実測はできていない。次に同種の実験を行う場合は、セッション単位の使用量を取得できる手段を事前に用意することが前提になる

## 解釈（統括の判断）

- 突合・棚卸しのような機械寄りの監査では、Spark は Wonder とほぼ互角の検出力を示した（中核の指摘の一致、追加の精度指摘2件）
- 一方で、重大度の較正と、台帳の外側（roadmap の宿題）まで含めた範囲の読みでは差が出た。解釈の争いや新規性リスクのような判断寄りの論点で Wonder に分があるという、本人の従来の見立て（監査こそハイコストモデル）と矛盾しない結果である
- 本実験をもって監査の定常割当（D4）を変更はしない。割当の変更を検討する場合は、本記録を材料として台帳に判断を残す

## 本人の判断（2026-10-28）

- Wonder の監査は、要所で保険のように使う
- 基本は Spark で行けるが、文脈の量や範囲が多いときは Wonder をセカンドで回す
- 別モデルを回すこと自体に意味があるため、どちらか一方ではなく両方を使う
- 本判断は `docs/model-selection.md` の「現在の方針」に監査の併用として反映した
