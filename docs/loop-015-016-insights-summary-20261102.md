## 集約（要点）

1. **ページの品質は、生成文の品質とは別物。** 欠陥は組み立て層で生まれ、組み立て層で直った（テンプレート改修で重複 20〜25→6〜8 groups、記録露出 51〜54→0、見出しずれ 1→0、hero 第一確認項目 6/6）。生成の評価だけではページは測れない。【B4・F18】
2. **改善は1要因ずつ変えると帰属がつく。** 世代列（基準→research→テンプレート→反映→競合解消）で、どの介入が何を動かしたかが全部追える。【I28】
3. **人間の判断は「反映メモ」に編むと伝わる。ただし層による。** 組み立て層の指示は 6/6 完全伝達。文章層の指示は、他の制約と衝突すると伝わらない。【H24】
4. **効かない指示は強めない。衝突している制約を特定して、制約側を直す。** R1（繰り返し削減）は gen-004 で再発し、原因（hero の逐語再掲と適合の逐語要件）を制約側で解いた gen-005 で解消した。【H25・I27】
5. **検出は2層（決定的チェック＋対照ジャッジ）で回る。** ジャッジが「ない」と言えることは陰性対照で確認済み。ただし「ある」の次は「目立つか」で、際立ちは機械でなく人間の目視が物差し。【F19・G22】
6. **調査（市場の型）は文章に効くが、ページには届かない。** 届ける経路（テンプレート接続）が別途要る。読み手の第一確認項目はケースごとに違い、給与とは限らない。【E15・C8】
7. **モデル運用の実務知見。** reasoning が max_tokens を食う（天井は本文量だけでなく入力文脈でも決まる）。守りは金額でなく呼び出し回数。素の単発生成に完結の保証はない。キーの取り違えは静かに全滅する。【A1〜A3・D11・E17】
8. **直し切った先に残るのは、表現でなく事実側の問題。** ペルソナの離脱点は、事実の曖昧さ・未記載（更新基準、シフト固定可否、総額試算）へ移った。ここは文章の改善でなく質問工程の領域。【H26】

## A. モデルの挙動（トークンと完結性）

1. **reasoning が max_tokens を食い、本文が空・切断になる現象は再現性がある。** loop-015: 上限800で reasoning 797・本文 null。上限4,000で成功（reasoning 1,876）。loop-016: 生成は 4,000 で reasoning がほぼ全量を占め本文 null → 8,000 に引き上げ。レビューは 2,000 で空応答 → 4,000。judge は 4,000 で reasoning 3,883 のため P3〜P5 が切断 → 8,000。vanilla の Wonder は 8,000 でも6件中3件が切断。
→ 上限は「本文の想定量＋reasoning の頭数」で決める。reasoning の実需は同じ条件でも 1,876〜3,365+ とばらつくため、固定費として読めない。
2. **守りは金額でなく呼び出し回数でしか作れない。** Baseten は残量が確認できない。loop-016 は呼び出し回数 40 回を枠にし、トークン上限は品質側の調整に回した。実費は「未記録」のまま正直に残す。
3. **素の単一応答には完結の保証がない。** vanilla の Wonder は単一プロンプト・単一応答で HTML を出し、3/6 件が上限で切れて未完結の文書になった（Spark 1.3 は 6/6 完結）。パイプライン側の「上限の実測→引き上げ」「文章生成と組み立ての分離」は、この完結性を支える工程として働いている。※vanilla は temperature 0.7（パイプライン側 0.4）という条件差があり、解釈では差し引く。

## B. ページの欠陥は生成でなく組み立てで生まれる

4. **gen-001 の文章そのものは健全だったが、完成LPの欠陥は組み立て層で発生した。** 生成文は6ケース全て適合 pass・散文要修正0。一方、完成LPでは (a) facts 表と本文の二重掲載（C-A では結合文が表内だけで3回、ページ全体で4回出現）、(b) 検証側の定型文の露出、(c) 企画・記録物（Target audience / Persona / Insights applied）のページへの印刷、(d) 見出しと中身のずれ、が発生した。生成の評価だけではページの欠陥は捕まらない。
5. **ページ級の欠陥は2層で機械的に捕まる。** 第1層（決定的チェック: 重複文・検証文辞書・記録ラベル・見出し適合）は API なしで全件検出。第2層（few-shot 対照ジャッジ、欠陥カタログ P1〜P5）は統括の ground truth（C-A・C-F）と照らして取りこぼしなしだった。検出は Baseten 枠を使わない。
6. **ジャッジの「ない」と言う力は当初未検証だった。** 試行では全項目「ある」が返った（ground truth と一致）。→ gen-003 で欠陥が実際に消えたページに対し「ない」への反転が確認でき、解消した（F19）。
7. **欠陥の直し方は書き換えでなく存否・配置。** 二重掲載は「同じ文を1回だけ置く」、検証文・記録物は「記録側へ寄せる」、見出しは「中身に合わせる」。文章の推敲ではなく、ページの編集判断で解ける種類の欠陥だった。

## C. 調査と訴求（市場の型）

8. **読み手の第一確認項目はケースごとに違い、給与とは限らない。** 調査工程（実在の公開求人→型への抽象化、出典記録つき）で固定した第一確認項目: C-A 年収、C-B day shift、C-C 給与より先に12か月の term、C-D 雇用元と就業先の分離、C-E 3時間枠＋徒歩圏、C-F 固定日程＋6週間。「給与表示が小さい」という違和感への答えは一律の拡大ではなく、ケースごとの第一項目を hero に出すこと（欠陥候補 P6 として検出側にも接続）。
9. **市場の型は本文を転用せずに取れる。** 調査は対象を企画から決め、公開求人を読み、文法・提示順・給与提示の型だけを抽象化して版固定した。事実の根拠は cases/ の固定データのみ、research は表現の型レイヤーとして分離できた（生成記録に researchApplied/version を残す配線まで完了）。
10. **ペルソナと hero の不一致は構造で判定できる。** C-F のペルソナは「term と pay を最初に確認する」と固定されているのに、gen-001 の hero は対象者への呼びかけで時給は表の中だった。本人の英語モラル感覚に頼らず、企画とページの突合で捕まる欠陥だった。

## E. gen-002（research 適用世代）の結果（2026-11-02 追加）

15. 【実測】**research は文章には効いたが、ページには効かなかった。** gen-002 は全6ケース適合 pass・散文要修正0。生成文は集約→分散に変化した（文数 C-A 5→11、C-B 6→11、C-C 6→11、CTA の分離、冠詞・表記の改善など）。一方で hero は両世代とも同一（loop16-complete.mjs の TITLES が固定で、research が hero に届く経路がない）、pagecheck 件数はほぼ不動（重複は文数比例で微増減）、judge P1〜P5 は全ケース「ある」のまま。**ページ級の欠陥はテンプレート起因であり、生成側の改善では動かない。** 直すなら組み立て側（hero を research の第一確認項目＋facts から組む、facts 表と本文の二重掲載をやめる）が次工程。
16. 【実測】**hero の直接チェックと judge の P6 判定がずれた。** 直接チェック（run-record の対照表）では第一確認項目は C-A 年収❌・C-B 日勤❌・C-C term✅・C-D 雇用元分離✅・C-E 部分的・C-F 6週間✅で両世代同一。一方 judge は gen-002 の P6 を全ケース「ない」とした（hero に雇用形態・勤務地が揃っていることを根拠に読んだ形跡）。P6 の判定はジャッジの印象でなく、hero 領域への第一確認項目の有無を機械で見るべき、という検出側の改善候補。
17. 【実測】**入力文脈が増えると reasoning も伸び、天井を押し上げる。** gen-002 は research 注入で prompt が約6,500トークンになり、reasoning が 6〜7k に増加。C-B は上限8,000 で reasoning 7,997 を占めて No content が2回発生し、12,000 に上げて安定した（A1 の続報: 天井は本文量だけでなく入力文脈の大きさでも決まる）。Baseten の数え方: 成功世代は 14/40 だが、失敗2回を含む実際の API 呼び出しは 16 回。残りは実呼び出し基準で 24 回。

## F. gen-003（テンプレート改修）の結果（2026-11-02 追加）

18. 【実測】**テンプレート改修でページ級の欠陥は大きく消えた。** gen-003 は gen-002 の文を逐語再利用し組み立てだけを変更（Baseten 消費0）。pagecheck: 重複グループ 20〜25 → 6〜8、検証文 10 groups → 2 groups、記録露出 51〜54 → **0**、見出しずれ 1 → **0**、hero の第一確認項目は 6/6 揃った。文章をいじらずに直ったこと自体が、B4・E15（欠陥は組み立て層にある）の裏取りになっている。
19. 【実測】**ジャッジは「ない」と言えた（陰性対照の問い解消）。** 欠陥が実際に消えた gen-003 で、judge は C-A・C-B の P1・P4、C-B・C-D・C-E・C-F の P6 を「ある→ない」に反転させた。全項目「ある」しか返さない検出器ではなかった。2層検出（決定的チェック＋対照ジャッジ）は、出す側と見る側の両方で実測が付いた。
20. 【実測・残件】**残ったのは分類の精度の問題。** (a) C-E・C-F では P1 が改善なしと判定されたが、残っている重複は「値の意図的な再掲」（条件サマリー等での再提示）で、文の二重掲載とは性質が違う。重複検出に「文の重複」と「値の再掲」の区別が要る（候補）。(b) 検証文の残り2 groups は CTA 付近の "All conditions above" / "No new facts" で、ブロック除去後も小さなメタ表現が残る。置くか記録側に寄せるかは表現方針の判断。

## G. 本人メモ（gen-003）の読み取り（2026-11-02 追加）

21. 【記録】**本人の目視は、検出が 0 にした後も残っていた露出を拾った。** gen-003 のメモ6件で、4/6ケースが「冒頭に作る側への指示・強調方針の説明が残っている」を指摘。pagecheck の記録露出は 0 だったが、辞書は企画ラベル系しか見ておらず、指示・方針系の文は対象外だった。検出辞書の拡張候補（「強調方針・指示」系）。内部フィールド名（employmentType / contractTerms）の表示も C-C で指摘され、同種の露出。
22. 【記録】**「ある」の次は「目立つか」。** hero の第一確認項目は 6/6 present になったが、メモでは C-A（年収）・C-B（日勤）・C-E（3時間・駅2分）で「もっと目に入ってほしい」が残った。存在のチェック（P6）の次段は際立ち（大きさ・位置）の問題で、機械チェックだけでは測りにくく、本人の目視とペルソナレビューが物差しになる。
23. 【記録】**繰り返しの感覚は、文の重複が減っても残る。** 5/6ケースが「同じ条件が何度も・長い」を指摘。残っているのは値の再掲（F20 の分類問題）で、本人は「再掲自体が長い」と感じている。反映メモでは「条件は1回詳しく、後は短い値・要約で」という形に編んだ（gen-004 で再発するか測る）。

## H. gen-004（反映メモ適用）の検証結果（2026-11-02 追加）

24. 【実測】**反映は層によって効き方が違う。組み立て層の指示は完全に伝わり、文章層の指示は他の制約と衝突すると伝わらない。** 本人のメモから編んだ反映メモ（R1〜R8＋ケース別）を gen-004 に適用した結果: R3（冒頭の指示文除去）・R4（内部フィールド名の人間化）・R5（hero の際立たせ）・R6（応募前チェックの条件項目化）・R7（CTA と実際の行動の一致）・R8（画像再配分）は **6/6ケース全て解消**。R2（事実の関係性の明確化）は 4 解消・2 部分。**R1（条件の繰り返しを減らす）だけが 5/6ケースで再発**し、pagecheck の重複はむしろ微増した（6〜8 → 7〜9 groups）。
25. 【実測】**R1 が効かなかった理由は指示の質でなく、制約同士の競合。** (a) R5 の hero-highlight が facts の値を hero でも逐語掲示するため、目立たせるほど重複が増える。(b) 適合チェックが事実文の逐語掲示を求めるため、生成側が条件を省くと適合で落ちる。「1回だけ書く」と「逐語で全部出す」と「目立たせる」が同時に成立しない。直すなら指示でなく制約側（highlight は文でなく値だけにする、適合の逐語要件の範囲を変える）が対象になる。loop-012 の「チェッカー必須文言と本人の修正が衝突した」件と同型。
26. 【記録】**ペルソナレビューの離脱点が、表現の問題から事実の解釈の問題へ移った。** gen-004 のレビュー6件では、指示文・フィールド名・チェック項目・CTA の分かりにくさは離脱理由に出てこない。残る離脱・疑問は「フレックスのコアタイムの実際」「引き継ぎリーダーが何をするか」「更新審査の基準」「シフトは固定できるか」「総額はいくらになるか」など、原本の事実が読み手の判断に対して曖昧・未記載な点に集中した。これは文章の直しでなく、質問工程（担当者への確認）で扱う種類の問題。AIっぽさの指摘には文内での言い換え繰り返し（"which averages two remote days per week..." 型）が残り、R1 の問題の文内版として記録する。

## I. gen-005（R1 の競合解消）と loop-016 の締め（2026-11-02 追加）

## J. vanilla ブラインド対照評価の結果（2026-11-02 追加、新セッションで実施）

29. 【実測】**事実の創作は、どの方式でも起きなかった。** vanilla（Wonder／Spark の単一プロンプト単一応答）とパイプライン（gen-005）の全18件で、固定 facts に無い数値・条件の出現は 0。少なくともこの実験範囲（架空・単純な facts）では、事実の厳密さはパイプラインの差別化点にならなかった。
