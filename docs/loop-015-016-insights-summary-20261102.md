## A. モデルの挙動（トークンと完結性）

1. **reasoning が max_tokens を食い、本文が空・切断になる現象は再現性がある。** loop-015: 上限800で reasoning 797・本文 null。上限4,000で成功（reasoning 1,876）。loop-016: 生成は 4,000 で reasoning がほぼ全量を占め本文 null → 8,000 に引き上げ。レビューは 2,000 で空応答 → 4,000。judge は 4,000 で reasoning 3,883 のため P3〜P5 が切断 → 8,000。vanilla の Wonder は 8,000 でも6件中3件が切断。
→ 上限は「本文の想定量＋reasoning の頭数」で決める。reasoning の実需は同じ条件でも 1,876〜3,365+ とばらつくため、固定費として読めない。
2. **守りは金額でなく呼び出し回数でしか作れない。** Baseten は残量が確認できない。loop-016 は呼び出し回数 40 回を枠にし、トークン上限は品質側の調整に回した。実費は「未記録」のまま正直に残す。
3. **素の単一応答には完結の保証がない。** vanilla の Wonder は単一プロンプト・単一応答で HTML を出し、3/6 件が上限で切れて未完結の文書になった（Spark 1.3 は 6/6 完結）。パイプライン側の「上限の実測→引き上げ」「文章生成と組み立ての分離」は、この完結性を支える工程として働いている。※vanilla は temperature 0.7（パイプライン側 0.4）という条件差があり、解釈では差し引く。

## B. ページの欠陥は生成でなく組み立てで生まれる

4. **gen-001 の文章そのものは健全だったが、完成LPの欠陥は組み立て層で発生した。** 生成文は6ケース全て適合 pass・散文要修正0。一方、完成LPでは (a) facts 表と本文の二重掲載（C-A では結合文が表内だけで3回、ページ全体で4回出現）、(b) 検証側の定型文の露出、(c) 企画・記録物（Target audience / Persona / Insights applied）のページへの印刷、(d) 見出しと中身のずれ、が発生した。生成の評価だけではページの欠陥は捕まらない。
5. **ページ級の欠陥は2層で機械的に捕まる。** 第1層（決定的チェック: 重複文・検証文辞書・記録ラベル・見出し適合）は API なしで全件検出。第2層（few-shot 対照ジャッジ、欠陥カタログ P1〜P5）は統括の ground truth（C-A・C-F）と照らして取りこぼしなしだった。検出は Baseten 枠を使わない。
6. **ジャッジの「ない」と言う力は未検証。** 試行では全項目「ある」が返った（ground truth と一致）。欠陥の無いページで「ない」と言えるかは、次回に対照（折りたたみ版などの陰性対照）を入れて測る。
7. **欠陥の直し方は書き換えでなく存否・配置。** 二重掲載は「同じ文を1回だけ置く」、検証文・記録物は「記録側へ寄せる」、見出しは「中身に合わせる」。文章の推敲ではなく、ページの編集判断で解ける種類の欠陥だった。

## C. 調査と訴求（市場の型）

8. **読み手の第一確認項目はケースごとに違い、給与とは限らない。** 調査工程（実在の公開求人→型への抽象化、出典記録つき）で固定した第一確認項目: C-A 年収、C-B day shift、C-C 給与より先に12か月の term、C-D 雇用元と就業先の分離、C-E 3時間枠＋徒歩圏、C-F 固定日程＋6週間。「給与表示が小さい」という違和感への答えは一律の拡大ではなく、ケースごとの第一項目を hero に出すこと（欠陥候補 P6 として検出側にも接続）。
9. **市場の型は本文を転用せずに取れる。** 調査は対象を企画から決め、公開求人を読み、文法・提示順・給与提示の型だけを抽象化して版固定した。事実の根拠は cases/ の固定データのみ、research は表現の型レイヤーとして分離できた（生成記録に researchApplied/version を残す配線まで完了）。
10. **ペルソナと hero の不一致は構造で判定できる。** C-F のペルソナは「term と pay を最初に確認する」と固定されているのに、gen-001 の hero は対象者への呼びかけで時給は表の中だった。本人の英語モラル感覚に頼らず、企画とページの突合で捕まる欠陥だった。
