# Fix plan — making the tool what the user wants to build (2026-11-03, coordinator)

Baselines (confirmed by the user, landed): `docs/design/intent-statement.md`, `docs/design/generation-flow-statement.md`, `docs/design/learning-flow-statement.md`. Design lineage: `docs/design/lp-full-pipeline-design-v1.md`, the gap-fill design (audited, passed 2026-11-03), and the loop-020 return material (key visual judged non-conforming against the planning; fix belongs at design level: the planning→image correspondence and its inspection).

## Gap (measured against the baselines, from the current origin code)

- G1 Entry: the runner is pinned to FICT-J01's artifact set (original JSON, fixed FACTs, existing approval record). There is no way to hand it a posting as text. (Intent: "You hand it a job posting".)
- G2 Planning: no stage takes a planning input. Text generation prompts are built from FACTs only; audience and appeal never enter the tool. (Flow: planning first.)
- G3 Images: `decideImagePlan` uses hardcoded prompts ("flat vector-style illustration of a fictional workplace building exterior", section prompts from FACT key names). No key-visual stage, no correspondence to planning, no stop at a key-visual preview, no resume. This is the direct ancestor of the loop-020 non-conformance.
- G4 Completion: C1–C4 only; image meaning is declared out of scope (N3). The flow now requires the key visual to be checked against the planning before presentation.
- G5 Page quality: the deterministic page checks and dicts exist only under `loops/loop-016/tools/` (candidate status). `checkCompletion` has no C5.
- G6 Previews and checkpoints: the runner's preview is a demo replay, optional (`allowPreview:false` in the CLI), and the assembled LP is never presented as a checkpoint. There is no up-front checkpoint-set choice (four-point / two-point) and no per-checkpoint confirmation record (R2).
- G7 Failures: any stage failure stops the run. There are no bounded retries and no holds carried to a preview (R1 table in the gap-fill design).
- G8 Learning: no input path carries preview feedback into a later generation inside the tool. In loop-016 this worked only as a coordinator relay (reflection memo handed in as an input file). The learning-flow statement records that as the current state.

## Fix (implementation in this repository, by the coordinator)

### Phase 1 — entry, planning, key visual

- F1 Text entry: the runner accepts a posting as a text file, pins it as a new source artifact (own id and version, sha256 recorded, lines split and numbered), then runs extraction and reconciliation unchanged and stops at approval with the extracted fact set presented as the approval candidate. The runner never creates an approval; the existing approval tooling records the human's decision afterwards, as today. FICT-J01's pinned path stays as it is.
- F2 Planning input: the runner accepts a planning file (audience and appeal) alongside the posting, recorded by file and hash. No planning input: the run stops after approval and records that it is waiting for planning (a checkpoint stop, not a failure). The tool never invents planning.
- F3 Key-visual stage (after approval, before text generation): first build a correspondence table — every visual element names its basis (a planning appeal item or an approved FACT) — and a prohibited-motif list taken from the planning's "what we will not say" plus the standing bans (residence/housing imagery for unstated housing, cash or income imagery, specific clock times or amounts, any text or numbers). The image prompt is constructed only from the correspondence. One key visual is generated with the existing image executor, the correspondence and prompt are recorded with it, and the run stops at the key-visual preview checkpoint. A resume mode takes the confirmed key visual (file and hash, with the confirmation recorded) and continues: text, then real images, then assembly.
- F4 Real images: section-image prompts are derived from the correspondence and the confirmed key visual's specification, replacing the hardcoded templates in `decideImagePlan`. The no-text / no-numbers rule stands.

### Phase 2 — completion, previews, checkpoints, holds

- F5 C5: port the loop-016 deterministic page checks into `src/` as a pagecheck module with the dictionaries versioned under `src/dicts/` (copied from `loops/loop-016/tools/dicts/`; the version is named in the run record). `checkCompletion` gains C5 on the runner side; `verify.mjs` is not modified.
- F6 Checkpoints and previews: the checkpoint set (four-point: planning, key visual, text, assembled page / two-point light: key visual, assembled page) is chosen before the run starts and recorded. At each selected checkpoint the run stops and writes a presentation record in the R2 format (what was presented, holds listed, per-checkpoint judgement fields: confirmed / corrected / held, corrections verbatim). A run that finishes without its selected previews being presented does not count as done.
- F7 Retries and holds (R1 table): extraction, reconciliation, FACT comparison, and approval never self-correct — contradictions and mismatches stop the run. Text generation, image generation, and assembly retry a bounded number of times on fixable failures; anything still unfixed is recorded as a hold and carried to the preview, presented with it, and never counted as complete.

### Phase 3 — learning input

- F8 Feedback input: the runner accepts a feedback memo file (the user's annotations on a preview, or a reflection memo compiled from them), records it by file and hash, and passes it to text generation as a binding input. Compiling the memo stays a human/coordinator act; the tool's part — accepting it as an input and recording it — is what this fix adds, and the run record says so.

## Invariants (unchanged)

Fact extraction and reconciliation, FACT comparison, approval and its invalidation, stopping on contradiction, fictional data only, no generation of any kind before approval, `verify.mjs` semantics unchanged, the runner never creates an approval, unstated items are never invented, images carry no text or numbers.

## Tests

Existing suites stay green. New failure-injection tests in the established style: text entry stops at approval with a candidate; missing planning stops after approval as a checkpoint; a planning whose "not say" includes housing produces a correspondence and prompt with no residence element; the key-visual stage stops and a resume continues from the confirmed file; C5 fails a page with repetition / a verifier phrase / a record label; holds are carried to the preview record; E02 still stops at reconciliation with no later stage executed.

## Order and approvals

Plan (this document) → implementation (no API spend) → audit against `docs/fix-audit-prompt-20261103.md` → live verification runs (API spend; the user's approval is asked before them) → landing. Live verification: one new fictional posting through the text entry end to end, with the key visual checked element-by-element against its planning before the run proceeds.
