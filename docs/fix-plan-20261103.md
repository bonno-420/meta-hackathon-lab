# Fix plan v2 — making the tool what the user wants to build (2026-11-03, coordinator)

v2: revised after a full read of the current code (every src module, the loop-016 tools, the loop-018 design and record, D8). v1 assumed extraction was reusable unchanged and that generation took no intent layer; the code says otherwise, and this version corrects both.

Baselines (confirmed by the user, landed): `docs/design/intent-statement.md`, `docs/design/generation-flow-statement.md`, `docs/design/learning-flow-statement.md`. Design lineage: `docs/design/lp-full-pipeline-design-v1.md`, the gap-fill design (audited, passed 2026-11-03), the loop-020 return material. Method traced from loop-015/016, where the produced LPs were the ones the user approved: per-case plan (audience, appeal, mustNot, CTA) fixed as data; image specs written per case from the plan (photorealistic, work content first); insights / research / reflection memo entering generation as recorded input blocks; assembly with a facts-built hero and each sentence placed once.

## Gap (measured against the baselines, from the current origin code)

- G1 Entry: pinned to FICT-J01's artifact set. `extract-and-check.mjs` hardcodes the input id, `loadOriginal()` reads only `src/fict-j01-v1.json`, the E02 summary is a constant, and the runner's defaults name the FICT-J01 files. There is no way to hand the tool a posting.
- G2 Planning: `generate.mjs` builds its prompt from FACTs only and forbids appeals by design (it is a transcription engine). The planning-aware path exists — `generate-persona.mjs` — but its intent layer (persona P-01, speaker S-01, worries W1–W5) is hardcoded in code for one case family, and the loop-016 method (plan as per-case data) lives only in experiment tools. Planning never enters the tool as an input.
- G3 Images: `decideImagePlan` uses hardcoded prompts ("flat vector-style illustration…", section prompts from FACT key names). No key-visual stage, no correspondence to planning, no stop at a key-visual preview, no resume. In loop-016 the image specs were written per case from the plan; nothing of that method is in the tool. This gap produced the loop-020 non-conformance.
- G4 Completion: C1–C4 only; image meaning is declared out of scope (N3). The confirmed flow requires the key visual to be checked against the planning before it is presented.
- G5 Page quality: the deterministic checks and dicts exist only under `loops/loop-016/tools/` (candidate status). `checkCompletion` has no C5.
- G6 Previews and checkpoints: the runner's preview is a demo replay, optional, and shows verifier furniture by design; the assembled LP itself is never presented as a checkpoint. No up-front checkpoint-set choice (four-point / two-point); no per-checkpoint confirmation record (R2).
- G7 Failures: any stage failure stops the run. No bounded retries, no holds carried to a preview (R1 table).
- G8 Learning: no input path carries preview feedback into a later generation inside the tool. In loop-016 the reflection memo entered as a file the generator loaded; in the tool there is no such input.
- G9 Fixture binding in checks: `checkGrounding`'s NUMERIC_REPRESENTATIONS hardcodes FICT-J01's values (1,500 / 10,000 / 60 / 8), so the verbatim-value check is bound to one fixture instead of deriving from the cited FACTs.

## Fix (implementation in this repository, by the coordinator)

### Phase 1 — entry, planning, key visual

- F1 Text entry: generalize `extract-and-check.mjs` to take the original as a parameter (file, id, version) instead of the hardcoded FICT-J01 constants; the FACT key set stays the job-domain schema of this tool. The entry pins a posting text file as a new source artifact in the existing original format (own id and version, sha256 recorded), runs extraction, schema completeness, quote-verbatim, and self-reconciliation (the posting's own text as the E01-side input), and writes the artifacts in the existing shapes (original, facts, manifest, extraction record) so `approve.mjs` draft works unchanged. The run stops at approval with the fact set as the candidate. The runner never creates an approval. FICT-J01's pinned path and the E02 stop stay byte-for-byte in behavior.
- F2 Planning input: a planning file (audience, appeal items, what-we-will-not-say, image specs per F3) is accepted alongside the posting and recorded by file and hash. Missing planning: the run stops after approval and records that it is waiting for planning (checkpoint stop, not a failure). The tool never invents planning. The intent layer for generation is read from this file (generalizing `generate-persona.mjs`'s hardcoded INTENT into data), keeping its factual discipline and grounding checks.
- F3 Key-visual stage (after approval, before text generation): the planning input carries the image correspondence — every visual element names its basis (a planning appeal item or an approved FACT) and its role (key visual / work / place). Prohibited motifs are computed from the planning's not-say list plus the standing bans (residence imagery for unstated housing, cash or income imagery, specific clock times or amounts, any text or numbers). The key-visual prompt is constructed only from the correspondence. One key visual is generated with the existing image executor; the correspondence, prompt, and image are recorded together; the run stops at the key-visual preview checkpoint. The pre-presentation check verifies the correspondence artifact and the prompt against the prohibited list (deterministic), and the element-by-element visual check against the planning is recorded in the presentation record (the loop-020 checklist). Resume takes the confirmed key visual (file and hash matching the confirmation record) and refuses anything else.
- F4 Real images: generated from the planning's image specs (roles: hero/work/place; work content first; place at most one, per the traced method), specified against the confirmed key visual, replacing `decideImagePlan`'s hardcoded templates in the pipeline path. The no-text / no-numbers rule stands.

### Phase 2 — assembly, completion, previews, checkpoints, holds

- F5 Assembly: `assembleLP` gains the traced composition: a hero block (the confirmed key visual plus the first-check FACT values as short chips), each generation sentence placed exactly once, no verifier or record furniture in the page (C5 enforces this). Sentences stay verbatim and in order.
- F6 C5: port the loop-016 deterministic page checks into `src/` as a pagecheck module with the dictionaries versioned under `src/dicts/` (copied from `loops/loop-016/tools/dicts/`; the version is named in the run record). `checkCompletion` gains C5 on the runner side; `verify.mjs` is not modified.
- F7 Checkpoints and presentation records: the checkpoint set (four-point: planning, key visual, text, assembled page / two-point light: key visual, assembled page) is chosen before the run starts and recorded. At each selected checkpoint the run stops and writes a presentation record in the R2 format (what was presented, holds listed, per-checkpoint judgement fields: confirmed / corrected / held, corrections verbatim). A run does not count as done while a selected preview is unpresented.
- F8 Retries and holds (R1 table): extraction, reconciliation, FACT comparison, and approval never self-correct. Text generation, image generation, and assembly retry a bounded number of times on fixable failures; anything still unfixed becomes a hold, recorded with stage and failed condition, carried to the preview, presented with it, never counted as complete.
- F9 Grounding generalization: `checkGrounding` derives numeric representations from the cited FACT items (normalized value and value string) instead of the hardcoded FICT-J01 table.

### Phase 3 — learning input

- F10 Feedback input: a feedback memo file (the user's annotations on a preview, or a reflection memo compiled from them) is accepted by the runner, recorded by file and hash, and passed into the intent layer of text generation as a binding input — the loop-016 mechanism. Compiling the memo stays a human/coordinator act; the run record says so.

## Invariants (unchanged)

Approval and its invalidation; stopping on contradiction; fictional data only; no generation of any kind before approval; `verify.mjs` unmodified; the runner never creates an approval; unstated items never invented and shown only as not stated (with the inquiry-invitation form where the intent layer applies it, and never an invented contact detail); images carry no text or numbers; every stage's pass/fail is that stage's own tool output.

## Tests

All existing suites stay green (their fixture expectations unchanged). New failure-injection tests in the established style: text entry pins and stops at approval; entry with a contradiction inside the posting stops at reconciliation; missing planning stops after approval as a checkpoint; a planning whose not-say list includes housing yields a correspondence and prompt with no residence element; the key-visual stage stops, and resume refuses an unconfirmed or hash-mismatched key visual; C5 fails a page with repetition / a verifier phrase / a record label; a defective page's holds reach the presentation record; grounding accepts a non-FICT-J01 numeric value derived from its own FACTs; E02 regression intact.
