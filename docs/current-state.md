## 製品の定義（本人の言葉）

「俺が欲しいのは、承認を飛ばして自動で完走することじゃない。人が判断すべきときには実物と質問が届き、答えた後の記録・再開・検査は道具が引き受けること。誰の環境でも」

## 着地の判断基準（本人の言葉）

「版を固定して新しいチャットに求人票を貼り、その後の人の操作が『届いた実物を見て答える』だけだったか。途中で誰かがパスを直したり記録を補ったりしたなら、LPができても、その手入れが必要だった箇所が次に直す場所だよ。」

## パイプラインの現在形

- 入口は1つ: `node make-lp.mjs <求人票テキスト>`（内部で src/run-demo.mjs を駆動）。手組みの LP は欠陥であり、作らない。
- 流れ: 原本の固定 → 抽出（fact-extract-v1.4）→ 事実照合 → 承認 → 企画 → 1枚画 → 文章 → 実画像 → 組み立て → 再検証（C1–C7、ゲート G-A〜G-E ほか）。
- チェックポイント（承認・企画・1枚画・文章・LP）では、実行形態によらず**生成物と選択式の質問が返る**:
  - ターミナル: プレビューページが開き、本人が選択する。
  - 非対話（エージェントのセッション等）: make-lp がチェックポイントパッケージ（生成物・質問・選択肢）を出力して止まる。操作セッションがそれを本人に提示し、本人の回答を `node make-lp.mjs --resume <out-dir> --answer <choiceId>` で受け渡す。make-lp が回答の記録を作成し、走行を続ける。
- 回答後の事務は道具が引き受ける: 承認・確認・判定の記録作成、再開（1枚画の確認ファイルは自動で引き渡す）、再検証の実行。
- ゲート（矛盾・検証不合格・レビュー不合格）は質問の対象にしない。止まったら、それが結果として報告される。
- 抽出の規則（v1.4 で確定）: 明示された事実は否定でも stated として記録する（例: 月収保証なし）。値が原本に現れない項目は書かない。原本にない「保証」等の語を混ぜない。抽出の訂正は最大1周。
- 言語の規則: 原本に言語指定マーカー（[EN] 等）があれば、その言語で生成する。日本語の値は英語の生成物に混ぜない。

## 検証済み（範囲を明記）

- 統括の VM（版 9cf8881）: 承認パッケージ → `--answer approve` → 承認記録の作成と承認検証の通過 → 企画・1枚画の描画 → 1枚画パッケージ → `--answer confirm` → 文章生成まで、受け渡しの連鎖を確認した（FICT-E03-ANSWERTEST2）。別の走行では文章レビュー不合格のゲート停止も観測した（機構の失敗ではなく品質ゲートの停止）。
- 本人の環境（版 9cf8881、新しいチャット、Sorano）: 承認 → 1枚画まで、人の操作は「実物を見て答える」だけ、手入れゼロで通過した。受け渡しの仕組みは着地した。走行は文章生成の段階で、生成側の根拠検査が文2（月収不保証の文言なしに保証へ言及）を検出してゲート停止した — 人の事務ではなく機械の生成品質の問題として、次の修正対象になった（2026-11-05 09:27 のライン報告）。
