- 宛先: 制作ライン
- 設計: `docs/design/baseten-verification-loop-design-v1.md`（改訂版、冒頭に改訂記録。監査M1・M2対応済み）
- 監査: 設計監査 `docs/design/baseten-verification-loop-design-review.md`（修正 M1・M2）→ 改訂 → 限定再監査 `docs/design/baseten-verification-loop-design-rereview.md` 合格。追加確認2件も実施ブリーフへ引き継ぎ済み
- 本ブリーフの位置づけ: 上記設計の改訂版と両監査を前提とする実施手順の確定版。本ブリーフで決める事項は本人の決定により固定する（数値の再変更は本ブリーフの改訂として記録する）
- 本体との分離: 本体（工程1–6）は常時提出可能な状態を保ち、本実施は本体のコードと記録に混ぜない

## 前提（設計 §1–§3、監査で担保済み）

- 実行基盤は Baseten の Muse Spark Open（`meta-models/muse-spark-open-1026`）。製品（L2）の実行時モデル（Meta Model API の Spark 1.3 系）とは分ける
- データは架空のみ
- キーは本人の環境にのみある（`~/.config/opencode/baseten-api-key`）。ライン側はキーを受け取らず、表示・コピー・コミットもしない。設定は本人の環境で行う
- 実費は「未記録（残量が確認できないため）」とし、金額で埋めない（台帳 L-003・L-012 の運用を継承）。代わりにサンプル数と1回あたりの使用量（取得できる場合）を残す。残量は Billing にも表示されず確認できないため、歯止めはサンプル数と1回あたり上限で設計する
- 記録は `loops/loop-015/` に Baseten であることを明示して置く（モデル名、反映メモ版、サンプル数、停止有無を必須）
- 仮説: 流れながらの差し戻しを後続の生成へ反映し続けると、同じ指摘の繰り返しが減り、散文評価の要修正も減る。反証条件は同じ指摘が世代をまたいで繰り返されることと要修正が減らないこと
- 判定: (i) メモの解消と (ii) 散文評価（当事者の声、生活翻訳、型への沿い方、第三者視点の混入なし）の要修正減少が両方そろった場合のみ「改善した」。片方だけは「部分改善」。反証条件に当たれば仮説が成り立たなかった実測として残す
- 台帳 `docs/learnings.md` への昇格は候補→検証→承認の既存の流れで行い、ループ側が自動で書き込まない。提出に使う場合は組み入れ前に監理ラインの監査を受ける（D8: 昇格の承認者は本人）

## 本ブリーフで固定する事項（本人の決定）

### 題材の選定と配分（O1の解消を含む）

- 題材は架空の2件とする
  - T-A: 企画の精度を見る群 1件
  - T-B: 文章側の検証サンプル 1件
- 題材の事実の固定記録は `loops/loop-015/topics/` に置く。記録は開始時に sha256 ハッシュで版を固定し、以降の適合確認の入力同一性の基準とする。形式は各 `topic-*.json` の `facts` 配列と `sourceFingerprint`、および本ブリーフが指すハッシュ値とする。ハッシュ値は `loops/loop-015/run-record.md` の「入力版」節に記録する
- 題材ごとに「企画（対象層・訴求）」を先に固定してから生成する（知見 L-027 を継承）

### 停止条件 K1–K5（具体値の固定）

| # | 条件 | 具体値・運用 |
|---|---|---|
| K1 | 本人の停止指示 | 直ちに止める。世代の途中でもできているサンプルは記録として残し、理由を `run-record.md` に記録する |
| K2 | サンプル数の上限 | 題材ごとに最大8世代、全体で16サンプルまで。達したら新しい生成を始めない |
| K2 補足（O2の解消） | 生成呼び出しの総数上限 | 上記とは別に、Baseten への生成呼び出しの総数を20回までとする（小サンプル分を含む）。不採用サンプル（適合で不採用）は世代に数えないが、この総数には数える。歯止めの主は世代数、資源の歯止めは総呼び出し数とする |
| K3 | 締切からの逆算での打ち切り | 設計の目安どおり。最終生成を 11/04 の日中までとし、11/04 の後段は監査と記録の整理だけにする。提出締切 2026-11-05 11:00 JST から逆算した運用であり、監査の所要が読み切れない点は本人が打ち切り時点を確定することで担保する |
| K4 | 同じ指摘の繰り返し | 同じ観点・同じ内容の指摘が3世代続いたら、その題材の世代列を止める。全体は止めず題材単位で止める |
| K5 | 適合落ちの継続 | 適合確認で落ちる生成が2回連続したら、その題材を止める。散文の質の前に事実が崩れているため、反映メモで直す対象にしない（M1の切り分け） |

### 1回あたりの上限

- 1回の生成あたりの上限（出力の量と再試行の有無）は実施前に固定する。再試行は自動では行わない
- 具体値は最初の小サンプルで実測してから本人が決める。本ブリーフでは数値を決めない（観察事項の「最初の小さいサンプルの暫定値」は、小サンプル自体を小さめの暫定値で実行することで担保する）

### 提示物とメモ欄

- `loops/loop-015/` の中に世代ごとの Markdown ファイル（`generations/<topic>/gen-NNN.md`）を置き、その中のメモ欄に本人が直接書き込む形とする
- 新規の道具は作らない
- メモ欄は文単位の書き込みを基本とし、サンプル全体への書き込みも置く。書き込み単位は「指摘1件」で対象の文と内容が分かる形で残し、要約して丸めない。状態は「未反映 / 反映済み / 見送り」を区別し、見送りは後続へ持ち越さない
- 本人の書き込みがないサンプルも記録として残す

### 反映メモの運用（限定再監査の追加確認を反映）

- 反映メモは統括（Muse）が本人の書き込みから整え、本人が確認してから次世代へ渡す（M2の確定。D11の統括の定義と一致し、ライン側のハブではない）
- 確認待ちのメモがある間も生成は止めない。世代は最新の確認済みの版で進める
- 確認済みの版がまだない初期は、反映メモなしで進める
- 整形に Baseten の実行は使わない。したがって K2 の数え方は生成サンプルのみを対象とし、1回あたり上限も生成だけを対象とする。将来的に Baseten 実行へ変える場合は、その実行を上限の対象に含め実行回数を記録することを本ブリーフの改訂で定める

### 適合確認の実施手段（M1の確定）

- 既存の再検証の機械検査（生成文の数値と事実の突合）を流用し、サンプルの題材となった架空の事実（`topics/` の固定記録）に対して照合する
- 本ループのサンプルは本体の承認工程を通らないため、本体の承認記録は入力にせず、題材の事実の固定記録をもって入力の同一性に代える。人間の意味確認は本人の書き込みと散文評価が担う
- 適合で落ちたサンプルは loop 記録には残すが提示の世代列には含めない。世代列の数え方では世代として数えず「不採用（適合で不採用）」と明示して記録する。単発で落ちた場合は次の生成を止めない。落ちる生成が続く場合の扱いは K5 とする

### 開示の要否

- 提出文に書く。実験記録として Baseten（Muse Spark Open）の利用を明記し、本体の実績と区別して表示する。開示しない形でも記録が成立することは設計 §3 のとおりだが、本実施では開示する形で固定する

## 実施の段取り

### 1. 疎通確認（本人の環境のみ）

- Baseten への接続を小さい呼び出し1回で確認し、結果を記録する
- 実行は本人の環境でのみ行い、ライン側はキーを受け取らない。キーの値自体は記録に残さない（存在確認のみ）。確認対象は `meta-models/muse-spark-open-1026` への到達可否とする
- 使用するスクリプトは `loops/loop-015/tools/baseten-check.mjs`（本ブリーフと同時作成）。出力は `loops/loop-015/connectivity-check.json` に残す（日時、モデル名、疎通OK/NG、取得できれば使用量、実費は未記録の旨）
- 疎通確認の呼び出しは K2 の世代数には含めないが、K2補足の生成呼び出し総数（20回）には含めるかどうかは、小サンプルの位置づけと合わせて `run-record.md` で明示する（本ブリーフでは小サンプル分を含む総数として定義済み。疎通確認の軽量呼び出しは総数に含めない）

### 2. 小サンプル（1回あたり上限の実測）

- 最初の小さいサンプル（暫定の小さい上限で実行）で1回あたりの使用量を実測する
- この実測をもとに、1回あたり上限の具体値を本人が決める
- 小サンプルは題材 T-A / T-B のいずれか一方で実行し、世代列の第1世代として扱うかは実測後に本人が決める（扱わない場合は記録に「小サンプル（較正用）」として残し、世代列には含めない選択も可とする。いずれの場合も `run-record.md` に明示する）

### 3. 本格稼働（止めずに回す）

- 設計 §2 の単位（企画の固定 → 生成 1回 → 適合の確認 → 散文評価 → 提示）で止めずに回す
- 生成は本人の確認を待たずに次へ進む。提示は世代列ごとに行い、新しいサンプルができたら提示側に追加する
- 適合で落ちたサンプルは「不採用」と明示して記録に残し、世代列には含めない（M1）

### 4. 反映メモの運用

- 反映メモは統括（Muse）が本人の書き込みから整え、本人が確認してから次世代へ渡す
- 確認待ちのメモがある間も生成は止めず、世代は最新の確認済みの版で進める。確認済みの版がまだない初期は反映メモなしで進める
- 世代ごとに「適用した反映メモの版」を記録し、どの指摘がどの世代から効いているかを追えるようにする

### 5. 停止（K1–K5）

- K1（本人の指示）、K2（世代数上限 8/全体16、総呼び出し20）、K3（11/04日中打ち切り）、K4（同じ指摘3世代継続で題材停止）、K5（適合落ち2回連続で題材停止）
- 止めた場合は理由とその時点までの記録を残す。題材単位の停止であり全体は止めない

## 記録（追跡可能性と提出への接続）

- `loops/loop-015/` に置く。必須: 実行基盤が Baseten であること、モデル名 `meta-models/muse-spark-open-1026`、反映メモの版、サンプル数（世代数と総呼び出し数）、停止の有無、打ち切り時点の確定内容
- 実費は「未記録（残量が確認できないため）」とし、金額で埋めない。代わりにサンプル数と1回あたりの使用量（取得できる場合）を残す
- 世代ごとに適用した反映メモの版を記録し、どの指摘がどの世代から効いているかを追えるようにする
- 改善の記録は、メモの解消と散文評価の要修正減少が両方そろった場合のみ「改善した」とし、片方だけなら「部分改善」、反証条件に当たれば仮説が成り立たなかった実測として残す
- 本ループの成果は提出物本体（統合デモ）には混ぜず実験記録として位置づける。提出に含める場合は実験の記録（仮説、世代列、改善したかどうか、止めた理由を含む）として参照できる形にし、本体の実績と区別して表示する（開示する形で固定）

## 監査の置き方

- 本ループの成果を提出に使う場合は組み入れ前に監理ラインの監査を受ける。監査では仮説と判定の記録が実測に基づくこと、改善と書く場合にメモ解消と散文評価の両方がそろっていること、本体の実績と混ざっていないことを照合する
- 提出に使わない場合もループの閉じ作業として記録の欠落を確認する。監査まで済ませるかは残り時間と本人の判断で決める
- 本体の提出は本ループに依存しない。本ループが止まった場合も本体の提出可能性に影響しない

- 疎通確認の疎通OK/NG（本人の環境で実行してから記録する）
