## 1. 目的（二重構造）

1. **プロダクト**: AIが目的を理解し、設計・制作・実行・監査・改善を一貫して進め、成果物を評価し、失敗から学び、プロセス自体も改善できる「AI開発・実行基盤」を作る。
2. **プロセス自体の検証**: 上記の基盤（＝開発プロセス）を、実際のプロダクト開発に適用して検証・改善すること自体が、今回の実験目的である。

プロダクトの具体的な要件と方向性は開始前準備資料を正本とし、本書はそれを変更しない。

## 2. レイヤー定義

| レイヤー | 内容 | 正本 |
|---|---|---|
| L1 開発プロセス基盤 | 本書の設計対象。サイクル、役割、文脈パック、監査、改善、記録の仕組み | 本書 |
| L2 プロダクト（ワークロード） | 準備資料の編集担当者向け事実照合デモ（架空求人の FACT 照合パイプライン） | 開始前準備資料 |

L1 と L2 の関係は、提出物を統合デモとすることで決定済みである（D1）。すなわち、基盤（L1）が編集ワークフロー（L2）を実行するデモを提出物とし、基盤側の工程と記録と、ワークフロー側の成果の両方が見える形にする。最小実証の範囲は候補 A（FICT-J01 v1 の FACT 照合、E01・E02）で決定済みであり（D3）、ループ2で実装と実API検証、成果物監査まで完了した。後続は統合デモの残り工程（人間承認 → LP生成 → 再検証）へ進む。

## 3. 開発サイクル

1. 初期企画・要件を確認する
2. 上位設計を作成する
3. 独立した監査工程で設計を評価する
4. 合格した設計を基に、詳細設計と引き継ぎ情報（文脈パック）を作成する
5. 再度監査を行い、合格した範囲を実装する
6. テストと成果物の監査を行う
7. 問題の原因を分析し、設計・実装・監査基準を改善する
8. 改善結果を記録し、次のサイクルに進む

常時並列ではなく、工程間でパスを受け渡す。モデルは全力投球を前提とし、制御するのは出力の方向と絞り（焦点・範囲）である（本人決定、context-pack §6）。

## 4. 役割（機能定義）

モデル割当は名称で決めず、利用可能な機能と費用を確認して決める（開始指示 §3）。この確認は実施済みであり、現行の割当は D4 とその追記で決定済みである。

- 駆動環境（コックピット）: Codex（主）/ OpenCode。できる限り Meta のプロダクトを優先し、Meta の基盤では利便性が大きく落ちる場合に限り Codex / OpenCode を使う（D4 追記）。
- 既定の流れ: サブ（Muse Spark 1.3 Contributor）が実施と一次確認まで行い、主担当（Muse Wonder）が監査と判断する。Wonder は原則として自分では作業せず、差し戻しが重なる場合に限り、修正回数とコストの見合いで直接実施に切り替える（D4 追記2、`docs/model-selection.md` の現行方針）。
- 確認済みの事実: Wonder は Meta Model API 経由で実呼び出し可能であり、単価は入力 $4 / 出力 $20（100万トークンあたり）。Spark 1.3 Contributor の単価は入力 $0.10 / 出力 $0.20。いずれも D4 とループ2の実測に基づく。
- 役割の機能定義（統括・調整、設計、実行、独立監査）は v1 を継承する。独立監査は工程遷移の判断を持ち、最も重みが大きい。

適用範囲の明示（C2 対応）: **プロダクト（L2）実行時のモデル割当は本書の対象外である。** 本書が定めるのは開発体制（L1）側の役割と割当であり、L2 の実行時にどの工程をどのモデルが担うかは、プロダクト側の設計で別に定める。本書の記述を L2 の割当の根拠に使わない。

## 5. 文脈パック仕様（工程間の受け渡し単位）

各パスは文脈パックを単位として受け渡す。パックには次を含める。

- 目的とスコープ（今回のパスでやること、やらないこと）
- 入力資料への参照とバージョン（Git のコミット SHA または文書バージョン）
- 制約（ルール、予算枠、禁止事項、対象リポジトリの AGENTS.md）
- 対象ペルソナ（監査時の利用者視点に使う場合）
- 受け入れ条件（監査ゲートへの参照。ゲート ID とバージョン）
- 未決事項（このパスでは決めないこと、判断が必要な点）
- 前パスの監査結果と差し戻し理由（差し戻し時は必須）

初回パスの例外（N7 対応）: ゲートがまだ存在しない初期のパスは、ゲート参照なしで開始してよい。そのパスで得られたゲート候補は、パス終了時に §7 の最小レコードで登録する。ループ1・ループ2はこの例外で運用したものとして扱う。

## 6. 監査設計

- 照合対象: 初期の企画・要件（応募資料と context-pack）と、実際の設計・成果物。
- 監査はモデルの自己判定だけで最終許可を出さない。数値・版の一致など機械検証できるものは機械検証し、意味の対応は人間の確認に残す（準備資料の原則を継承）。

### 判定の定義（三段階）

| 判定 | 意味と使い分けの基準 | 必須の付帯物 | 再監査 |
|---|---|---|---|
| 合格 | 受け入れ条件を満たし、次工程へ進んでよい | 判定理由（照合先の文書・節を特定すること） | 不要（次工程の成果物監査は別途行う） |
| 修正 | 同一工程の中で直せる不備がある。前工程の前提は覆さない | 理由と修正箇所の列挙、修正の完了条件 | 修正箇所に限定して再監査する |
| 前段階への差し戻し | 前工程の前提（要件解釈、設計判断、入力版）自体を覆す必要がある | 理由、前工程で決め直すべき事項、影響範囲 | 前工程の成果物全体を再監査する |

### プロダクト不変条件ゲート（観点1 対応）

L1 の監査が L2 成果物を検査するときの不変条件として、次を合格の前提にする。いずれを欠いても「合格」にしない。

| # | 不変条件 | 検査方法 | 備考 |
|---|---|---|---|
| G-INV-1 | 扱うのは架空データのみ（実在の求人・企業・個人の情報を使わない） | 機械検証（入力の ID・版が架空原本として登録されたものと一致するか）＋人間確認（混入の疑いの目視） | 実データ混入は停止条件でもある（下表） |
| G-INV-2 | 止める条件で止まる（矛盾、未解決の必須条件、原本からの指示注入、根拠のない数値・待遇の追加、承認後の原本変更） | 機械検証（数値・単位・版・行IDの突合）＋人間確認（意味の対応、注入の判定） | 止まらずに進んだ成果物は差し戻しとする |
| G-INV-3 | 「警告を無視する承認」を設けない（承認は矛盾一覧と同一画面で、警告を飛ばす分岐を作らない） | 人間確認（承認フローと画面に迂回路がないことの確認） | 迂回路があれば実装方式によらず不備とする |
| G-INV-4 | 再検証の合格は公開承認ではない（合格の効果はデモ内プレビューの許可まで） | 人間確認（表示と手順が「プレビュー許可」にとどまること）＋機械検証（公開に相当する出力を持たないこと） | 公開と読める表現があれば修正とする |

### 停止条件（統合表。N2 対応）

v1 の §6 と §10 に分散していた停止条件を本表に一本化する。本表が正であり、他節は本表を参照するだけとする。発動したら、そのパスを先に進めず、直ちに本人へ通知し、当該ループの記録（`loops/loop-NNN/`）に条件・根拠・時刻を残す。再開は、停止理由の解消が記録され、本人が再開を認めたときに限る。本人の応答がない間は停止を維持し、自動では再開しない。

| # | 停止条件 | 主な根拠 |
|---|---|---|
| S-1 | 重大なセキュリティ・安全上の問題（秘密情報の混入の疑いを含む） | v1 §6、§10 |
| S-2 | 実データの混入（架空データ以外の求人・企業・個人の情報） | context-pack §5、G-INV-1 |
| S-3 | 新規性リスク（期間外コードの混入、準備資料など既存物を提出物と混同する状態） | context-pack §2 |
| S-4 | プロダクトの止める条件に該当（矛盾、未解決の必須条件、原本からの指示注入、根拠のない追加、承認後の原本変更） | context-pack §5、G-INV-2 |
| S-5 | 残高・料金・課金対象が不明、計測の欠落、推定と実績の大きな乖離 | v1 §10 |
| S-6 | 想定外のモデルへの切替、権限の追加要求、規約上の疑義 | v1 §10 |

### エスカレーション（N3 対応）

- 「同じ経路」とは、**同一ゲート ID での連続した差し戻し**をいう。工程や文書の単位では数えない。
- 同一ゲート ID で差し戻しが 2 回続いたら、手動のパスの受け渡しをその時点で止め、人間（本人）に判断を上げる（典拠: `docs/project-instruction-v1.md` §2・§6。N1 は同ファイルの Git 配置により解消済み）。現行運用は文書と Git による手動運用であり、自動で回し続ける仕組みは前提にしない。
- 判断を上げる際に渡すもの: 対象の差分、監査と実施側の両論の併記、判断を求める点を明記した依頼文。渡し先と記録先は停止条件と共通（本人へ通知、当該ループの記録に残す）。

### ペルソナレビュー（N11 対応、候補の提示に留める）

- 必要に応じてユーザーペルソナによる評価を組み込む。発動条件の**候補**として、(a) LP生成の初回実査、(b) 提出直前の最終監査、を提示する。
- 実施するか、どの条件で発動するかは本人の決定事項であり、本書では決めない。実施する場合はコスト上限をそのパスの文脈パックに明記する。

## 7. 改善サイクルと監査基準（ゲート）の管理

- 差し戻し理由から改善候補を作る。候補はそのまま恒久ルールにしない。
- 候補 → 検証（再現実験または小規模な適用）→ 承認 → ゲートへ昇格、の順で採用する。承認者を誰とするかは未決である（D8、§11 の未決事項を参照）。
- §6 の不変条件ゲート（G-INV-1〜4）は常設の検査項目として扱い、本節の候補・昇格の流れとは別に常に適用する。

### ゲートの最小レコード

ゲート 1 件ごとに、次を最小レコードとして残す。

| 項目 | 内容 |
|---|---|
| ID | ゲートを一意に指す ID（エスカレーションの「同じ経路」の数え方に使う） |
| 版 | ゲート自体のバージョン |
| 検査対象 | 何を検査するか（工程、成果物、条件） |
| 合否基準 | 合格と不合格の境界。機械検証か人間確認かの別も含む |
| 由来 | どの差し戻し・実験から生まれたかへの参照 |
| 状態 | 候補 / 検証中 / 有効 / 撤回 のいずれか |

置き場所（`docs/gates/` を設けるかどうかを含む構成案の採否）は本人の判断事項であり、本書では未決と明示する。未決の間は、候補を当該ループの記録に最小レコードの形で残すことで代用する。

### ゲート自体の監査

- 契機: 各ループの終了時、および有効なゲートが 5 件に達したとき。重複、誤検知、過剰な複雑化・肥大化を評価し、統合・撤回もあり得る。
- 実施者: 監査ライン。結果は当該ループの記録に残す。
- 版管理と由来の記録は v1 を継承する（いつ、どの根拠で変わったかを追えるようにする）。

## 8. 実験設計

- **再現性検証**: 同一条件（入力、モデル、設定、プロンプト版）で再実行し、結果の一致・ばらつきを見る。実施は、監査で結果の信頼性が争点になった場合に限る。同条件の再実行を常時の必須とはしない（争点がない再実行は費用だけが掛かるため）。
- **改善実験**: 条件を変えて比較する。原則として一度に一つの主要要因だけを変更する。
- 両者を混同しない。実験ごとに、条件、変更要因、結果、解釈を記録する。記録の置き場所は `experiments/` とする（ループ2の実績 exp-001 で使用済み）。

## 9. 記録仕様

Git を唯一の正本とする。チャットだけに残して終わらせない。配置は `loops/loop-NNN/`（パスごとの記録）と `experiments/`（実験）を正とする。

### 必須項目（欠落したら監査で「修正」判定とする。N5 対応）

- 使用した入力資料と文脈パックのバージョン（入力版）
- 作成・変更した成果物（出力への参照を含む）
- 監査結果、差し戻し理由、修正内容
- 実費。金額が計測できない場合は、金額の代わりに「未記録」とその理由を残すこと（理由の記録をもって必須を満たす。推測の金額で埋めない）

### 任意項目（可能な範囲で記録する）

- 使用モデル、実行条件、プロンプトのバージョン（受け入れ条件の照合に必要な場合は、そのパスの文脈パックで必須に格上げする）
- 監査基準の追加・変更とその根拠
- トークン使用量、所要時間、再試行回数
- 合格率、差し戻し率、改善結果

## 10. コスト設計

- 予算枠は準備資料の案を継承する: 実使用枠 $100 ＋ 予備 $50、$75 で新規探索を停止。同時実行 1 件、自動再試行なしを初期条件とする。ここでいう新規探索とは、未確定の設計・モデル・手法の試行をいい、確定済みの実装と再検証は含めない。
- **台帳は一本化する（N6 対応）**: 費用は同一の台帳で確認し、区分列（API 費 / エージェント推論費）で経路を区別する。別の台帳に分けて二重に数えない。モデル選定の知見は `docs/model-selection.md` に記録し、費用の実績はそこの記録と矛盾しないようにする。
- 実費は dev.meta.ai の Billing 実績と突き合わせて確定する。単価ベースの算出値は算出値と明記し、突合が済むまで確定値として扱わない（ループ2の $0.001289 は算出値。突合は `docs/roadmap-v1.md` の宿題として 2026-11-01 まで）。
- 単価の確認済み事実: Spark 1.3 Contributor は入力 $0.10 / 出力 $0.20、Wonder は入力 $4 / 出力 $20（いずれも 100万トークンあたり、D4）。パートナー枠は未申請のため、$150 以外の枠は計画に計上しない。
- 停止条件は §6 の統合表（S-5、S-6 を含む）を正とする。本節に別の停止リストは置かない。
- ライン別・役割別の予算配分は未決である（D5、§11 の未決事項を参照）。D5 が決まるまでの間も、支出は都度台帳に残し、上記の枠（実使用 $100、$75 で新規探索を停止）を上限として扱う。

## 11. 運用の境界と未決事項

- 本リポジトリの AGENTS.md を優先する。コミット・公開・課金・外部リソース作成は本人の明示承認がある場合のみ。
- 初期段階では自動化ツールの開発に踏み込まない。文書と Git の運用でプロセスを回し、自動化は最小実証の結果を見て判断する。Windows の Muse Code では session messaging が使えない前提とし、工程間連携は Git 経由の文脈パックで行う（準備資料の仕様確認に基づく）。
