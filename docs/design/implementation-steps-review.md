## 観点2: 順序と依存

判定: 修正

根拠と修正案:

- 承認（工程2）→ 生成（工程3）→ 再検証（工程4）の順序は依存関係に合っている。生成が承認なしに実行できないこと（31 行）、再検証の差し戻し先が生成工程であること（36 行）も正しい。
- **S7 工程1の「再現性検証」の位置づけが v1.1 §8 とずれる。** v1.1 §8 は再現性検証を「監査で結果の信頼性が争点になった場合に限る」とした。一方、工程1（19 行）は再現性検証を常設の作業として置く。ループ2の成果物監査で観察事項（未記載 value の表現、スキーマ完全性）が出ているため、信頼性の確認自体に理由はあるが、工程案がその根拠と、対象とするプロンプト版（v1 のままか、v1.1 改訂後か）を書いていない。改善実験（v1.1、18 行）と再現性検証を同一工程で混ぜると、両者の区別（v1.1 §8）も曖昧になる。修正案: 順序を「v1 での再現性（ばらつきの把握）→ v1.1 の改善実験（1要因）」のように分けて書き、再現性を行う根拠（ループ2監査の観察事項）を添える。あるいは再現性を落とし、改善実験の前後比較に置き換える選択もあり得るが、その判断は実施側と統括で決めること。
- スキーマ完全性チェックを工程1（20 行）に置く位置は適切である。承認・生成の下流で欠落が見つかるより、上流で落とす方が手戻りが小さい。「ゲート候補として記録する」に留め、昇格を前提にしていない点は D8（昇格の承認者は本人）と整合する。
- 工程2と工程3が同期間（10/29–30）に並ぶ点は、承認の記録形式が先に固定されれば成立する。依存（工程3は工程2の承認形式に依存する）を一文で明記すること（S3 と合わせて直す）。

## 観点5: Cloudflare Pages の妥当性

判定: 修正

根拠と修正案:

- 静的な生成物の置き場として Pages を選ぶこと自体は妥当である。独立した Pages プロジェクトとし、pages.dev のサブドメインを使い、「MJ のドメインや DNS には触らない」（41 行）と分離を明記している点は、MJ 本番との分離として十分な方向である。置く内容（42 行）も、架空の LP プレビュー、停止状態の表示、説明と GitHub へのリンクに限られている。
- **S10 公開の承認 checkpoint がない。** Pages プロジェクトの作成とデプロイは、外部リソースの作成と外部への送信に当たる。AGENTS.md と D8 により、本人の明示承認がある場合のみ行う。工程案は「Pages のセットアップ自体は前倒しで行う」（43 行）としつつ、いつ・誰の承認で作るかを書いていない。修正案: セットアップの前に「本人の承認を得る」ことを工程に明記し、前倒しの実施日と合わせて置く。未承認のまま作らないこと。
- **S11 公開物の表示と公開前チェックが弱い。** E01 の LP プレビューは架空求人の LP であり、実在の求人と誤認される表示は避ける必要がある（G-INV-1 の人間確認、G-INV-4 の「公開と読める表現があれば修正」にも関わる）。工程案に、架空であることの明示（プレビュー内の表示）と、公開前に秘密情報・実データ・未確定の主張が混ざっていないことを確認する手順がない。修正案: 工程5 に「公開前チェック（架空表示の確認、含めてはいけない情報の混入なしの確認）」を追加し、結果を記録に残す。Pages の規約や公開可否の詳細は未確認であり、本レポートでは可否を断定しない。提出ルールとの関係は、Official Rules 精読（N8、2026-10-31 まで）の結果と合わせて最終監査で照合すること。
- Pages は提出の必須物（公開リポジトリ、デモ動画、Cerebral Valley への提出）ではない。位置づけを「任意の公開プレビュー」と工程案に明記すると、遅れた場合の切り離し判断がしやすくなる（観点6 と連動）。

## 観点6: リスク

判定: 修正

根拠と修正案:

- **一番転びやすいのは工程3（LP 生成）である。** 初めての生成経路で、品質（文章として読めるか）、根拠保持（S2）、「足さない」制御の 3 つが同時に乗る。保険の修正案: 最小形を先に固定する（対象は E01 のみ、文の構成要素を FACT の項目に対応させる）。それでも生成が安定しなければ、FACT の表形式の表示をプレビューの代替として工程5に逃がす。代替でも G-INV-4（プレビュー許可まで）は守れる。
- **次に転びやすいのは工程5（統合と Pages）である。** 初回の外部セットアップと差し替えが 10/30–31 に重なる。保険はすでにある程度書かれている（セットアップの前倒し）。これに S10 の承認を前倒しの前提として加え、Pages が遅れた場合の切り離し（リポジトリの記録と動画で提出を成立させ、Pages は間に合えば公開する）を工程案に明記すること（S12: 切り離し条件の明記）。
- 日程全体の保険（バッファ 11/03・11/04、E03–E10 を後回しにする方針）は roadmap 側にあり、工程案がそれを壊す記述はない。範囲の縮小順序（Pages → ペルソナ → E03 以降の順に落とす、など）を工程案に一文で置くと、遅延時の判断が速くなる。
- パートナークレジット（D7）の成否は中核工程の前提になっていない（$150 の枠で計画が閉じている）ため、リスクとして扱わない。
