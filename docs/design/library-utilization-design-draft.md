## 0. 全体像と本体との接続

文章側のパイプラインは次とする。

```
収集 → 構造化と型化 → 目録（登録・保留） → 参照セットの提案と承認 → 生成 → 適合監査（既存）＋散文評価（新設）
```

本体との接続点は 2 か所だけに絞る。

- **生成への入力追加（提案）**: 本体の生成（工程3）は「承認済み FACT のみ」を入力とする。本拡張では、承認された参照セット（型セット）を、事実を上書きしない追加の入力として渡す。事実の正は原本と FACT のままであり、型は文章の形だけを与える（§5）。生成プロンプトの版が上がるため、実験として記録し、本体の既存の合格済み経路はそのまま残す。
- **評価層の追加（提案）**: 本体の適合監査（再検証、工程4）の後ろに、散文評価を別の層として足す。適合監査の判定（プレビュー許可まで）には触れず、散文評価の結果は生成への差し戻し理由と、評価基準の候補の材料にだけ使う（§6）。

収集から型化までは本体の実行経路に入らない（在庫を作る側の工程）。そのため、本拡張が未完成でも本体の提出可能性には影響しない。

## 1. 収集

### 原則

- 取得元はユーザーが指定したものだけとする。指定のない取得元への自動的な拡大は設計に含めない。
- 媒体の自動クロールは、規約・ライセンスの確認が未了のため、本工程の本体には含めない。後付けの拡張点として、取得元の種別（指定ファイル、指定 URL の手動取得、将来のクロール）を差し替えられる形にしておく。指定入力（ファイルや貼り付けなど、経路を問わない）だけで全工程が回ることを本体の成立条件とする。
- 設計上の例示は架空のものだけを使う。実在の求人広告の本文を収集物として記録しない。将来、ユーザーが実在の広告を指定した場合の扱い（本文を残すか、型だけを残すか）は未決事項とする（後掲）。

### 密度による分岐

収集バッチの開始時に、対象領域の件数の見立て（多い / 少ない）を記録し、手順を分ける。見立ての根拠（検索の試し打ちの件数など）も残す。

- **件数が多い領域**: 業種とエリアで競合広告を検索し、参照候補を絞る。絞り込みの信号は、時給などの単価、出稿件数に加え、前提資料の優先観点（新規性の高い募集、掲載単価の高いもの、同業他社）を候補の並び替えに使う。
- **件数が少ない領域**: 同業に限定せず、職種と関連業種の似た仕事へ検索範囲を広げて候補数を確保する。広げた範囲（どこまでを関連とみなしたか）をバッチ記録に残す。

### 収集バッチの記録形式

バッチ 1 件ごとに次を記録する。置き場所は `loops/` ではなく収集側の記録として分けることを提案する（置き場所の確定は未決事項）。

| 項目 | 内容 |
|---|---|
| バッチ ID | 収集バッチを一意に指す ID |
| 母集団の定義 | 対象の業種・職種・エリアと、含める条件・除く条件 |
| 密度の見立て | 多い / 少ない と、その根拠 |
| 取得元 | ユーザーが指定した取得元（種別と指定内容への参照） |
| 取得日時 | 取得した日時 |
| 件数 | 取得件数と、候補に残した件数 |
| 除外の記録 | 除外したものと理由の要約（ライセンス不明、重複など） |

## 2. 構造化と型化

### 抽出項目と、既存の厳格 JSON 抽出との対応

収集物からは、事実の抽出と型の抽出を分ける。

- **条件（事実に当たる部分）**: 給与、勤務時間、交通費、勤務地、雇用形態など。本体の FACT 抽出（`src/extract-and-check.mjs`、`fact-extract-v1`）と同じ流儀で、出典位置と引用を結び、記載と未記載を区別する。収集物は他者の広告であり、こちらの原本ではないため、ここで抽出した条件は「その広告の記載」として扱い、生成の事実には使わない。使うのは次の訴求・構成の材料だけである。
- **訴求**: 何を売りにしているか（例: 架空の例として「未経験への安心」「収入の見通し」「生活との両立」）。文そのものではなく、訴求の種類として記録する。
- **構成**: 文章の並び（例: 導入 → 条件 → 働く場面 → 締め）。段落の役割の列として記録する。
- **その他（表現の材料）**: 言い換えの型（不利な条件を事実のまま別の角度で言う形）、生活翻訳の型（条件を読み手の生活の言葉に変える形）、語彙と禁則。文体ルール（自然な表現のルール）とは別の棚として扱う。

既存仕組みとの対応は次とする。新規の抽出形式は作らず、既存の「項目・状態・出典・引用・正規化値」の形を、収集物用の項目集合に差し替えて使う。検証（引用が原文どおりか、キーの欠落がないか）も既存の検証の考え方をそのまま使う。

### パターン分類の軸と「流通量」

分類の軸は次を初期案とする。軸自体の決定は本人の居場所である（前提資料 §7）ため、本書は案の提示に留める。

- 業種・職種、対象層（ペルソナ）、訴求の種類、構成の型、言い換え・生活翻訳の型の有無、媒体の種類。

集計する指標は **流通量** と名付ける（出現回数と、時期ごとの増減）。次を仮説として明記する。

> 仮説: 流通量は「広く模倣されている度合い」であって、効果（応募や採用に効いたこと）の証拠ではない。模倣の多さは、媒体テンプレートの強制、媒体側の制作都合、出稿量の多さでも増える。したがって流通量は、候補の並び替えと賞味期限（廃れた型の検出）にだけ使い、型の承認の根拠にはしない。承認の根拠は検証と本人の判断に置く。

### 型への抽象化の手順

1. 同じ訴求・構成を持つ収集物を複数集め、共通する並びと、事例ごとに変わる部分（数値、固有名、固有の言い回し）を分ける。
2. 変わる部分を差し替え可能な枠（スロット）にし、固有の表現と数値は残さない。型は「項目の列と、各枠に入るものの条件」として書く。
3. 型の候補として記録する。候補のままでは生成に使わない。
4. 検証: 架空の FACT に対してその型で生成を試し、事実との適合（適合監査）と散文評価で確かめる。再現実験と小規模な適用のどちらでもよい。
5. 承認: 本人が承認したものだけを目録へ登録する（型の登録の承認者は本人とする。これはゲート昇格の承認者を本人とする D8 と同じ形であり、新しい決定は作らない）。却下の場合は理由を候補の記録に残す。

型の出所の保持（G1）: 型は複数の収集物から抽象化されるため、出所は単一の由来を前提にしない。型の候補と登録レコードには、由来した収集バッチと事例の列（バッチ ID と事例への参照の列）を保持する。事例が増減したら列を更新し、版を上げる。

### 「どこからがコピーに当たるか」の線引き

モデルの判断に任せず、登録時と生成後の両方で確かめる判定条件として設計する。初期案は次のとおりとし、しきい値の確定は未決事項とする。

- **登録時の条件**: 型に、収集物の文そのもの（言い回しの連続）が残っていないこと。固有名・数値・固有の比喩が型に混入していないこと。機械的には、型の記述と収集物の原文との文字列の重なりを検出し、重なりがあれば候補に戻す。
- **生成後の条件**: 生成文が、参照した収集物のいずれかと、特徴的な言い回しの連続で一致しないこと。構成の一致だけではコピーとみなさない（構成は型として共有する前提のため）。数値の一致は事実（原本）由来かどうかで判定し、収集物由来の数値が紛れていたら不一致として扱う。
- 上記の「特徴的」の範囲としきい値は、本書では結論を出さない。未決事項として、判断材料（重なりの長さ、一致箇所の数）を記録する形式だけを先に決めることを提案する。

照合と原文保持の連関（G2）: 登録時と生成後のどちらの照合も、収集物の原文が保持されていることを前提とする。未決事項 U2 で「型だけを残す（本文を残さない）」と決めた場合、この照合はそのままでは成立しない。そのため U2 の判断材料に「照合が原文を必要とすること」を含め、代替の選択肢も併記する（未決事項リストを参照）。

生成後の照合の切り分け（G2）: 機械で測る範囲は、文字列の重なり（重なった文字列の長さと箇所数）と、数値の由来の突合（生成文の数値が原本の FACT にあるか）までとする。人間が確かめる範囲は、言い回しが「特徴的」に当たるか、言い換えで実質的に同じ表現になっていないか、構成以外の要素で原文に寄っていないか、とする。機械の結果だけで合否を決めず、人間の確認を残す（基本設計の原則を継承する）。

## 3. 目録（インデックス）

### 参照 1 件の単位

参照 1 件は「単独でライセンスと版を持ち、単独で承認の対象にできる最小の単位」と定義する。文章の型 1 件、テンプレート 1 ファイル、SVG 1 点は、いずれもこの定義では同じ粒度（1 件）として扱う。粒度の異なるものは、種類（型 / テンプレート / SVG / その他）の区別と、種類ごとの固有項目で吸収し、目録の共通項目は揃える。複数をまとめたものは単位ではなく「参照セット」として別に扱い、セットは単位への参照の列で表す。

目録に登録するのは型（と種類ごとの素材）だけであり、生成した完成文と収集物の原文そのものは登録しない（G3）。完成文と原文は、それぞれ生成の記録と収集側の記録に残すものであり、在庫化の対象ではない。

### 1 レコードの項目

| 項目 | 内容 |
|---|---|
| ID / 種類 | 参照を一意に指す ID と、種類（文章の型を本書の主対象とする） |
| 用途 | 何に使うものか（例: 架空の例として「飲食バイト向けの導入の型」） |
| 適用条件 | 業種・職種、対象層、訴求の種類など、その参照が合う条件 |
| ライセンス要約 | 利用してよい範囲の要約（全文ではなく要約と、出所への参照） |
| 出所 | どこから来たか。型の場合は由来した収集バッチと事例の列（G1）。それ以外は収集バッチ ID、または持ち込みの指定への参照 |
| 版 | 参照自体の版 |
| 登録日 / 最終利用日 | 登録した日と、最後に参照セットへ採用された日 |
| 状態 | 登録可 / 保留 / 却下 など（次の状態遷移による） |
| 流通量への参照 | 型の場合、流通量の集計（件数と時期）への参照。効果の指標としては扱わない |

デザイン側との共通化の検討: テンプレートと SVG は本書の対象外だが、上の共通項目（ID、用途、適用条件、ライセンス要約、出所、版、日付、状態）はデザイン素材にもそのまま使える形にしてある。種類ごとの固有項目（型なら構成と枠、SVG なら寸法など）は別表に分ける。共通化を採るかどうかは未決事項とする。

### ライセンスの状態遷移

申告（持ち込み時・収集時の自己申告）と、システム側の確認（参照先の表記の確認）が食い違った場合は、自動で登録も却下もしない。

```
申告あり → 確認中 →（一致）登録可 → 目録に登録
                  →（不一致・確認不能）保留 → 本人の最終判断 → 登録可 または 却下
```

- 保留の置き場所は、検索できる目録とは別の保留置き場とする。保留中の参照は、参照セットの提案の対象にしない。
- 最終判断はユーザー（本人）に上げる。判断と理由はレコードに残し、同じ出所からの後続の収集で再利用する。
- 申告がないものは確認中から始め、確認が済むまで登録しない。

型のライセンス状態の帰属（G1、規則の案）: 型の状態は、由来する全事例の確認状態のうち最も弱いものに合わせることを案として提示する。例えば、由来する事例のうち 1 件でも保留なら型も保留とし、すべてが登録可になって初めて型を登録可とする。この規則は案であり、確定は本人の確認事項として未決に残す（U8）。確定するまでは、型の登録のたびに由来事例の状態を列挙して本人の確認を得る扱いとする。

## 4. 参照セットの提案と承認

### 提案の手順

1. 企画（対象層・ペルソナ・訴求と、原本の版）を入力として受ける。
2. 目録の軽い情報（用途・適用条件・ライセンス要約）だけを読み、適用条件で候補を絞る。目録全体の本文は読まない（在庫の量と参照コストの分離、前提資料 §3）。
3. 小さな参照セット（型の組み合わせ）を、選んだ理由とともに提案する。理由には適用条件との対応を書き、流通量は並び替えの参考としてのみ添える。
4. 会話で詰め、本人が承認してから生成に入る（既存の承認ゲートと同じ型）。承認されていない参照は生成に使わない。
5. 採用された参照セットは、目録 ID と版の列として固定し、生成と評価の記録から参照できるようにする。最終利用日を更新する。

### 承認の記録フォーマット

提案 1 件ごとに次を残す。置き場所は当該ループの記録（`loops/loop-NNN/`）とする。

| 項目 | 内容 |
|---|---|
| 企画への参照 | 対象層・ペルソナ・訴求と、原本の版 |
| 提案内容 | 参照セット（目録 ID と版の列）と、選んだ理由 |
| 判断 | 承認 / 却下 / 修正して承認 のいずれかと、日時と判断者 |
| 修正理由 | 却下・修正の場合の理由（本人の言葉を要約せず残す） |
| 会話への参照 | 詰めた会話の記録への参照（ターン数を含む） |

### 提案精度への還流

- 判断と修正理由は、次回の提案の材料として蓄積する。自動で提案ルールを書き換えはしない。
- 蓄積から「提案の癖」（例: 特定の訴求で外し続ける型）の候補を抽出する場合は、型の登録と同じく 候補 → 検証 → 承認 を経て、提案の絞り込み条件に反映する。本人の承認なしに反映しない。

## 5. 生成

生成の入力は 3 層とし、型セットはその外側から文章の形を与えるものと位置づける。

| 層 | 内容 | 正 |
|---|---|---|
| 事実 | 原本と承認済み FACT（版つき） | 本体の FACT が正。型や収集物の条件で上書きしない |
| 意図 | 企画と、参照セットの承認で確定した訴求・対象層 | 承認記録 |
| 制約 | 法律、媒体ルール、クライアント条件 | 企画ごとに指定されたもの。未指定の制約を推測で足さない |
| 型セット | 承認された参照セット（型の構成と枠） | 文章の形だけを与える。事実と数値は与えない |

- 文章はテキストで生成する。数値はデータとして扱い、生成文中の数値は再検証で原本の数値と機械的に照合できる形を保つ（本体の再検証との整合）。
- 生成プロンプトは、型を使う場合と使わない場合を版で区別する（既存の `lp-generate-v1` に対する実験として記録する）。型ありの生成結果は、型なしの既存経路の合格実績をそのまま引き継がない。
- 生成後には §2 の「生成後の条件」（コピーの線引き）を確認する。一致があれば生成を差し戻す。

## 6. 散文評価

適合監査（事実・制約との照合で、プレビュー許可までを判定する既存の層）とは別に、散文としての質を評価する層を新設する。散文評価はプレビューの可否を決めず、生成への差し戻し理由と、文章の改善材料を出す。

### 評価観点（初期候補）

次は初期候補であり、確定した基準ではない。候補のまま評価に使い、昇格は次の仕組みで扱う。

- 当事者の声になっているか（書き手の説明ではなく、働く側の言葉になっているか）
- 生活翻訳があるか（条件が読み手の生活の言葉に置き換わっているか）
- 型に沿っているか（承認された型セットの構成と枠から外れていないか）
- 第三者視点の検証文が混ざっていないか（監査や検証の文章が本文に紛れていないか）

### 評価の記録フォーマット

評価 1 件ごとに次を残す。置き場所は当該ループの記録とする。

| 項目 | 内容 |
|---|---|
| 対象 | 生成文への参照（生成の記録と版）と、使った型セット |
| 観点ごとの判定 | 観点 ID、判定（良い / 要修正 / 対象外）、根拠となる生成文の引用 |
| 差し戻し | 生成へ差し戻すかどうかと、理由 |
| 評価の条件 | 評価に使ったモデル、プロンプト・観点リストの版、実費または未記録の理由 |

### 評価能力の育て方（既存の昇格の仕組みとの対応）

評価観点は、監査基準（ゲート）と同じ育て方をする。basic-design v1.1 §7 の「候補 → 検証 → 承認 → ゲートへ昇格」の流れと、D8（昇格の承認者は本人）に対応づける。

1. 本人の修正理由と、散文評価の差し戻し理由から、観点の候補を抽出する（候補のまま恒久ルールにしない）。
2. 候補の観点を過去の生成文に当てて検証し、妥当な指摘になるか確かめる。
3. 本人が承認した観点だけを、版つきの観点リストへ昇格させる。却下された候補と理由も残す。
4. 観点リスト自体も監査対象とし、重複と肥大化をループ終了時に見直す（ゲート自体の監査と同じ契機）。

## ハッカソン期間内の最小実装範囲の提案

組み入れ判断ゲート（11/01、D10）までに「作って回せる」範囲として、次を提案する。これを超える範囲（収集の自動化、流通量の集計基盤、在庫の大量登録）は期間内の対象にしない。

1. **目録の最小形**: 文章の型 3–5 件を、架空の事例だけから手で抽象化し、目録（ファイル形式は U4 の判断に従う）に登録する。最小実装の目録は文章側の項目だけで閉じ、デザイン側との共通化（U5）は前提にしない（G4）。ライセンス状態は「登録可」に限定し、保留フローは記録形式だけを用意する。あわせて、架空の事例で回す段階から、U1 の判断材料（重なりの長さ、一致箇所の数）を §2 の記録形式で残し、ゲート時点の判断材料とする（所見2）
2. **提案と承認の最小形**: E01 の企画に対して型セットを 1 件提案し、承認記録フォーマットで承認を得る。会話の自動化はせず、記録が残ることを成立条件とする。
3. **生成の最小形**: 承認された型セットを使い、E01 の生成を型あり版（新しいプロンプト版）で 1 回行い、既存の適合監査（再検証）を通す。型なしの既存経路は変更しない。
4. **散文評価の最小形**: 初期観点の候補で 1 回評価し、記録フォーマットで残す。観点の昇格は行わず、候補のままの運用実績だけを作る。

成立の判定: 上記 1–4 が架空データだけで 1 周し、記録が `loops/` に残ること。組み入れは、監査を経て本人が承認した場合のみとし、間に合わない場合は拡張として切り離して本体のみで提出する（D10 の方針を継承する）。
