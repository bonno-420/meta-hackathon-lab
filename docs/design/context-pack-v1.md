## 5. プロダクト設計の要約（開始前準備資料 2026-10-25、既存物）

正本: knowledge-vault リポジトリ `docs/meta-hackathon-prep-20261025` ブランチの
`inbox/2026-10-25_Meta_Global_AI_Developer_Hackathon_開始前準備.md`。

- 対象は架空求人だけを使う編集担当者向けデモ。実求人・応募者情報は使わない。
- 工程: `求人原本の固定 → FACT照合・矛盾検出 → 人間承認 → LP生成 → 再検証`。
- FACT 項目（給与・勤務時間・交通費・勤務地・雇用形態）は原文の引用位置（行 ID）と結ぶ。矛盾、未解決の必須条件、原本からの指示注入があれば処理を止める。
- 人間承認は矛盾一覧と同一画面で行い、「警告を無視する承認」は設けない。承認後に原本または FACT が変われば承認は失効し、再照合に戻す。
- LP 本文は承認済み FACT のみから生成し、表示文ごとに根拠の行 ID を保持する。再検証で数値・単位・範囲・否定・条件付き表現を再照合する。再検証の合格はデモ内プレビューの許可であり、公開承認ではない。
- 架空原本 FICT-J01 v1（L01–L06）と評価例 E01–E10（期待結果のみ、実測の精度なし）が用意されている。
- 含めないもの: 動画生成、応募フォーム、実サイト公開、本番 DB、顧客接続。
- 予算案（準備資料）: 実使用枠 $100 ＋ 予備 $50。$75 で新規探索を止める。API 利用と開発エージェント側の推論費は同じ台帳で確認する。同時実行 1 件、自動再試行なし、が初期案。

## 6. 開発の進め方（2026-10-27 本人決定）

- 起点は Muse（相談相手）とする。相談して決めた指示を Git に文脈パックとして置き、各ラインがそれぞれの環境で作業する。
- ラインは設計・監査・制作の 3 つに分け、常時並列ではなくパスを投げ合う。
- 監査が工程遷移の判断（進行 / 差し戻し / エスカレーション）を持ち、工程全体で最も重みが大きい。
- モデルは常時全力投球を前提とし、制御するのは出力の方向と絞り（焦点・範囲）。
- モデル配分の構想: Wonder が設計・監査・制作の基幹（オーケストレーション）、Spark が調査・実装・テスト等を担当。
- 対象リポジトリは `bonno-420/meta-hackathon-lab`（公開、期間内に作成）。コードは未着手。
- 詳細は `basic-design-v1.md` を参照。
