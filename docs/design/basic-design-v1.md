# 基本設計 v1 — AI開発・実行基盤とその開発プロセス

作成: 2026-10-27 / 状態: 設計案（独立監査に回す前のドラフト）。確定要件ではない。
入力: 本人のプロジェクト開始指示（2026-10-27）、開始前準備資料（2026-10-25、正本は knowledge-vault）、`context-pack-v1.md`。
方針: 確定事項・仮説・未確認事項を分離する。既存資料と矛盾する場合は上書きせず `review-notes-v1.md` に報告する。

## 1. 目的（二重構造）

1. **プロダクト**: AIが目的を理解し、設計・制作・実行・監査・改善を一貫して進め、成果物を評価し、失敗から学び、プロセス自体も改善できる「AI開発・実行基盤」を作る。
2. **プロセス自体の検証**: 上記の基盤（＝開発プロセス）を、実際のプロダクト開発に適用して検証・改善すること自体が、今回の実験目的である。

プロダクトの具体的な要件と方向性は開始前準備資料を正本とし、本書はそれを変更しない。

## 2. レイヤー定義

| レイヤー | 内容 | 正本 |
|---|---|---|
| L1 開発プロセス基盤 | 本書の設計対象。サイクル、役割、文脈パック、監査、改善、記録の仕組み | 本書 |
| L2 プロダクト（ワークロード） | 準備資料の編集担当者向け事実照合デモ（架空求人の FACT 照合パイプライン） | 開始前準備資料 |

L1 と L2 の関係（基盤そのものを提出物とするか、基盤で L2 を作り L2 を提出物とするか、統合デモとするか）は未決定。判断事項 D1（review-notes 参照）。本書は「L1 の最初のワークロードとして L2 の最小縦切りを使う」前提で設計するが、これは提案であり確定ではない。

## 3. 開発サイクル

1. 初期企画・要件を確認する
2. 上位設計を作成する
3. 独立した監査工程で設計を評価する
4. 合格した設計を基に、詳細設計と引き継ぎ情報（文脈パック）を作成する
5. 再度監査を行い、合格した範囲を実装する
6. テストと成果物の監査を行う
7. 問題の原因を分析し、設計・実装・監査基準を改善する
8. 改善結果を記録し、次のサイクルに進む

常時並列ではなく、工程間でパスを受け渡す。モデルは全力投球を前提とし、制御するのは出力の方向と絞り（焦点・範囲）である（本人決定、context-pack §6）。

## 4. 役割（機能定義）

モデル名で役割を決めない。実際に利用可能な機能と費用を確認したうえで割り当てる（開始指示 §3）。

| 役割 | 責務 |
|---|---|
| 統括・調整 | 全体目標、進行、優先順位、工程間連携の管理。起点は本人との相談窓口（Muse）が担う運用を想定 |
| 設計 | 要件、システム構造、作業手順、引き継ぎ情報の設計。下位機能として「要求・構想」「システム・工程」「次工程への文脈供給」を分ける |
| 実行 | 調査、制作、実装、テスト |
| 独立監査 | 設計・成果物を初期要件と照合し、合否と差し戻し理由を判断する。工程遷移の判断を持ち、最も重みが大きい |

モデル割当の決定手順: (a) 各モデルの利用可能性を実測で確認する（例: Wonder は API 経由の実呼び出しが未確認）、(b) 単価と上限を確認する、(c) 役割の要求（文脈長、推論の深さ、速度、コスト）に対応付ける、(d) 本人の承認を得て確定し、本書を更新する。

## 5. 文脈パック仕様（工程間の受け渡し単位）

各パスは文脈パックを単位として受け渡す。パックには次を含める。

- 目的とスコープ（今回のパスでやること、やらないこと）
- 入力資料への参照とバージョン（Git のコミット SHA または文書バージョン）
- 制約（ルール、予算枠、禁止事項、対象リポジトリの AGENTS.md）
- 対象ペルソナ（監査時の利用者視点に使う場合）
- 受け入れ条件（監査ゲートへの参照。ゲート ID とバージョン）
- 未決事項（このパスでは決めないこと、判断が必要な点）
- 前パスの監査結果と差し戻し理由（差し戻し時は必須）

## 6. 監査設計

- 照合対象: 初期の企画・要件（応募資料と context-pack）と、実際の設計・成果物。
- 必要に応じてユーザーペルソナによる評価を組み込む。
- 判定は「合格」「修正」「前段階への差し戻し」を基本とする。
- 重大なセキュリティ・安全上の問題は直ちに停止する。
- 同じ経路で差し戻しが 2 回続いたら自動ループを停止し、人間に判断を求める（本人決定）。
- 監査はモデルの自己判定だけで最終許可を出さない。数値・版の一致など機械検証できるものは機械検証し、意味の対応は人間の確認に残す（準備資料の原則を継承）。

## 7. 改善サイクルと監査基準（ゲート）の管理

- 差し戻し理由から改善候補を作る。候補はそのまま恒久ルールにしない。
- 候補 → 検証（再現実験または小規模な適用）→ 承認 → ゲートへ昇格、の順で採用する。承認者は本人を原則とする（判断事項 D8）。
- ゲート自体も監査対象とする: 重複、誤検知、過剰な複雑化・肥大化を定期的に評価し、統合・撤回もあり得る。
- ゲートはバージョン管理し、変更の根拠（どの差し戻し・実験に由来するか）を記録する。

## 8. 実験設計

- **再現性検証**: 同一条件（入力、モデル、設定、プロンプト版）で再実行し、結果の一致・ばらつきを見る。
- **改善実験**: 条件を変えて比較する。原則として一度に一つの主要要因だけを変更する。
- 両者を混同しない。実験ごとに、条件、変更要因、結果、解釈を記録する。

## 9. 記録仕様

Git を唯一の正本とする。チャットだけに残して終わらせない。

各パスで可能な範囲で記録する項目:

- 使用した入力資料と文脈パックのバージョン
- 使用モデル、実行条件、プロンプトのバージョン
- 作成・変更した成果物
- 監査結果、差し戻し理由、修正内容
- 監査基準の追加・変更とその根拠
- トークン使用量、実費、所要時間、再試行回数
- 合格率、差し戻し率、改善結果

配置案は review-notes-v1.md の「Git に残す成果物の構成案」を参照。

## 10. コスト設計

- 準備資料の予算案を継承する: 実使用枠 $100 ＋ 予備 $50、$75 で新規探索を停止、API 利用と開発エージェント側の推論費は同じ台帳で確認する。
- 同時実行 1 件、自動再試行なしを初期条件とする（準備資料）。
- ライン別・役割別の予算配分は、モデル割当の決定（§4）と合わせて再設計する（判断事項 D5）。
- 停止条件: 残高・料金・課金対象が不明、計測の欠落、推定と実績の大きな乖離、機密混入の疑い、想定外モデルへの切替、権限の追加要求、規約上の疑義。

## 11. 運用の境界

- 本リポジトリの AGENTS.md を優先する。コミット・公開・課金・外部リソース作成は本人の明示承認がある場合のみ。
- 初期段階では自動化ツールの開発に踏み込まない。文書と Git の運用でプロセスを回し、自動化は最小実証の結果を見て判断する。
- Windows の Muse Code では session messaging が使えない前提とし、工程間連携は Git 経由の文脈パックで行う（準備資料の仕様確認に基づく）。
