## 2. 応募資料から抽出した目的・確定要件・制約

**目的（プロダクト）**: 架空求人だけを使う編集担当者向けデモ。入力から表示文まで、どの事実を根拠にしたかを追えることを中心にする。

**確定要件（プロダクト）**:

- 工程: 原本の固定 → FACT照合・矛盾検出 → 人間承認 → LP生成 → 再検証
- FACT 項目は給与・勤務時間・交通費・勤務地・雇用形態。原文の引用位置（行 ID）と結び、確認済み / 矛盾 / 未記載を区別する
- 止める条件: 給与等の矛盾、未解決の必須条件、原本からの指示注入、根拠のない待遇・確約・数字の追加、承認後の原本変更
- 人間承認は矛盾一覧と同一画面。「警告を無視する承認」は設けない。承認後に原本・FACT が変われば承認は失効する
- LP 本文は承認済み FACT のみから生成し、表示文ごとに根拠の行 ID を保持する。再検証の合格はデモ内プレビューの許可であり、公開承認ではない
- 評価例: 架空原本 FICT-J01 v1（L01–L06）と E01–E10。期待結果のみで、実測の精度はない。E02–E08・E10 の見逃しを認めず、E01・E09 の過剰な拒否も記録する

**制約**:

- 実求人・応募者情報・顧客資料は使わない。含めないもの: 動画生成、応募フォーム、実サイト公開、本番 DB、顧客接続
- 予算案: 実使用枠 $100 ＋ 予備 $50、$75 で新規探索停止、同時実行 1 件、自動再試行なし
- 大会ルール: 期間内の新規作成のみ、公開リポジトリ、動画 3 分、Meta モデルの実質的な組み込み（context-pack §2）

## 9. 最小実証の候補と選定理由

前提: プロセスの 1 周回とプロダクトの最小縦切りを同時に検証できる単位にする。

- **候補 A（推奨）**: 題材 = FICT-J01 の FACT 照合工程。範囲は E01（正常）と E02（給与矛盾で停止）のみ。プロセスの設計パス → 監査パス → 照合の最小実装 → 成果物監査まで 1 周回を回す。LP 生成は含めない
  - 理由: 期待結果が E01・E02 で定義済みのため監査の照合先が存在する。停止条件が明確で、ゲート候補（給与矛盾の検出）が自然に得られる。コストと所要時間が小さく、期間内に複数周回できる
- **候補 B**: プロセス基盤の記録・ゲート管理ツールを先に実装する。— プロダクトの進捗が伴わず、作り込み過多のリスク。初期は不採用
- **候補 C**: FICT-J01 の全工程（承認 → LP 生成 → 再検証、E01–E10 全件）を一気に実装する。— 1 周回の単位として大きく、プロセス検証と実装デバッグが混ざる。候補 A の次段階とする
