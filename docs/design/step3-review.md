## 観点1: 生成物 JSON 形式の妥当性（文単位形式とヘッダの是非）

判定: 妥当。ヘッダの追加は可とする

- 生成物は、文ごとに本文・factKeys・sourceLines を保持する JSON であり（`loops/loop-008/generated-lp-v1.json:21-91`）、ブリーフ作業1の提案形式（step3-brief:30）のとおりである。全7文が本文と1つ以上の key と行 ID を持ち、行 ID を持たない文は含まれていない。
- 実施時に追加されたヘッダ（kind・version・promptVersion・model・input）は妥当と判断する（`loops/loop-008/generated-lp-v1.json:2-20`、生成は `src/generate.mjs:235-246`）。理由は次のとおり。第一に、入力の組（原本と FACT のファイル名と sha256、approvalId）を生成物自体から特定でき、工程4が「どの承認済み FACT に対する生成物か」を生成物の外の文脈なしに確認できる。第二に、ヘッダの値は承認記録から取られており、入力チェックで現在のファイルのバイト列と再計算で照合済みの組と一致することが担保されている（観点4）。第三に、文単位の形式そのものは提案どおりに保たれており、ヘッダは文の解釈を変えない。
- 引用粒度の原則でいう根拠の三点（FACT 項目の key、原本の行 ID、FACT に固定された quote）のうち、生成物の文は key と行 ID を保持し、quote は文の中に複製されていない。この点は、ヘッダが固定 FACT のファイルとハッシュを特定するため、その key から固定済み FACT の quote を一意に復元でき、参照として保持が成立している。工程4が `checkGrounding` を使う際も、生成物と FACT と原本を併せて渡す形が関数の前提になっている（`src/generate.mjs:139`）。したがって形式は、工程4が import して使う前提で十分である。
- なお、生成物の合格はデモ内プレビューの材料としての位置づけであり、再検証の合格なしにはプレビューにも公開にも使われないことが、run-record の引き継ぎに明記されている（`loops/loop-008/run-record.md:61`、G-INV-4）。

## 観点3: 引用粒度の原則「候補」の運用結果と、原則自体の妥当性

判定: 候補どおりに運用できた。原則は E01 の範囲で妥当であり、候補のまま昇格させない扱いが正しい

運用結果:

- 対応付けの単位は文であり、各文が key と行 ID の両方を保持している（generated-lp-v1.json:21-91）。複数項目を束ねた文では、束ねた全項目が列挙されている。企業名・求人番号・勤務地を束ねた文（L01 の3項目）、雇用形態・契約期間の文（L02 の2項目）、勤務時間・休憩・実働の文（L04 の3項目）、交通費と月上限の文（L05 の2項目）のいずれも、引かれた各 key の本来の行 ID が sourceLines に含まれていることを監査側で照合した。
- stated 13項目すべてがちょうど1回ずつ文に現れることを監査側で確認した。数値と条件は FACT の値の逐語である。時給1,500円、月上限10,000円、09:00〜18:00、休憩60分、実働8時間、契約期間3か月が文の中にそのまま保持され、「月収は保証しない。」は逐語で保持され、「月20日勤務は試算用の仮定である。」は仮定の文言を保持している。月収の見込み額の提示はない。
- 監査側でも `checkGrounding` を生成物に対して実行し、pass（7文、issues なし）を確認した。使用した生成プロンプトが現在のコードの生成するプロンプトと一致すること（改行の正規化後）も確認した。

原則自体の妥当性:

- この候補は、工程3の完了条件（文ごとに行 ID を付けること）と G-INV-2（止める条件で止まる、根拠のない追加をしない）の運用形として妥当である。quote を生成物に複製せず、固定済み FACT への参照（ヘッダの入力特定＋key）で保持する形は、工程1で観測された抽出時の粒度の揺れを工程3に持ち込まない方法として筋が通っている。
- ただし、機械検査の範囲には限定がある。根拠検査が機械で強制するのは、金額（円）と時刻の逐語、代表的な数値項目（時給・交通費上限・休憩・実働）の引用時の値の保持、未記載の断定のパターン、月20日勤務の仮定と月収の非保証の文言までであり（`src/generate.mjs:118-127,191-214`）、契約期間3か月のような期間・個数の表現や、「文が実際にその項目を使っているのに根拠に付けていない」という意味上の対応までは機械では網羅できない。今回の生成物については、監査側が文面と根拠の対応を全文化について目視でも確認し、対応の取りこぼしはなかった。原則を候補のまま昇格させない扱い（step3-brief:60、D8）はこの限定と整合しており、恒久ルール化する場合は、機械検査の範囲と、意味の対応は工程4の再検証で人間の確認に残ることを、原則の文面に明記すべきである（指摘1）。

## 観点4: 工程2監査の観察事項1の落とし穴が塞がれているか

判定: 塞がれている（テストで固定されていることを監査側の再実行で確認）

- 工程2監査の観察事項1は、`checkApprovalValidity` の返す `valid` は版の不変だけを意味し、下書きに対しても `valid: true` が返る、という落とし穴であった。
- 工程3の入力判定は、様式の定めどおり2条件の AND になっている（`src/generate.mjs:38-81`）。承認記録の status が `approved` で、approver と approvedAt が入っていること（同:49-66）、かつ `checkApprovalValidity` を実行時点で現在のファイルのバイト列から再計算し `valid: true` であること（同:67-80）である。承認記録内に静的に残る `validity.invalidated` は参照されていない（同:69 の再計算のみで判定される）。拒否の理由は reasonCode（approval-missing / approval-not-approved / approval-incomplete / approval-invalid）で区別される。
- テストで落とし穴が固定されている。下書きの承認記録について、再計算では `valid: true` になることを明示的に期待値として確認したうえで、入力判定では `approval-not-approved` で拒否されることが固定されている（`src/generate.test.mjs:40-45`、検証記録 `loops/loop-008/check-verification.json:13-29`）。FACT を改変した組では再計算で無効となり、「照合からやり直す」を含む理由で拒否される（テスト:59-62）。E02（承認記録なし）では、モデル呼び出しのスタブが1回も呼ばれないことまで含めて、承認記録の不在を理由に拒否される（テスト:66-71）。道具の CLI でも、入力チェックは API キーの確認より前に完了する（`src/generate.mjs:360-376`）ため、拒否時に費用が発生しない構造である。
