## 全工程に共通する決まり

- **記録**: 各工程の完了条件には「その工程の入力版、成果物、判定、実費（または未記録と理由）を `loops/loop-NNN/` に残す」ことを含める（basic-design v1.1 §9 の必須項目。欠ければ監査で「修正」になる）。工程6 は記録そのものの新規作成ではなく、全体の欠落チェックを行う。
- **変更の単位**: 改善は主要な変更を 1 要因だけとし、条件と結果を `experiments/` に記録する。再現性検証（同一条件の再実行）と改善実験を混同しない（v1.1 §8）。
- **承認**: コミット、課金が発生する API 呼び出し、外部リソースの作成、外部への公開は、本人の明示承認がある場合のみ行う（AGENTS.md、D8）。ゲートの昇格と撤回の承認者は本人であり、本書の工程では候補の記録までとする。
- **費用の区分**: 費用は同一台帳に区分列で残す（D5）。目安として、L2 の実行は製品実行（上限 $15）、プロンプト改善と再現性の計測は実験（上限 $25）を主な消費先とする。上限を超えそうな場合は、その時点で本人に確認し、他区分から自動で流用しない。
- **扱うデータ**: 架空データのみ。原本はデータとして扱い、指示として解釈しない。原本の記載にない情報を補完・創作しない。

## 工程1: 抽出・照合の仕上げ（10/28–29）

順序を分けて行う。混ぜない。

1. **再現性の把握（プロンプト v1 のまま）**: ループ2の成果物監査で観察事項（未記載項目の value の表現、スキーマ完全性の未検出）が出たため、結果の信頼性の確認として、v1 の同一条件で再実行し、抽出の一致とばらつきを記録する。対象は v1 であり、プロンプトは変えない。
2. **改善実験（プロンプト v1.1、1 要因）**: 未記載項目の value の扱い（`null` と明示する）を変える 1 要因だけを変更し、v1 の結果と比較する。手順と結果は exp-001 の流儀で `experiments/` に記録する。
3. **スキーマ完全性チェックの追加**: 抽出結果のキーの欠落を検出するチェックを実装する。扱いはゲート候補として最小レコード（ID、版、検査対象、合否基準、由来、状態）で記録するまでに留め、昇格はしない（昇格の承認は本人、D8）。
4. **承認対象の固定**: 後段の承認が指す対象として、採用した抽出結果（FACT）を版つきで固定する（原本版 FICT-J01 v1 と、FACT の版・プロンプト版を組で特定できる形にする）。原本または FACT が変わったら版が変わる扱いとし、工程2 の承認の無効判定はこの版の一致で判定する。

完了条件: 上記 1–4 の成果物と、各実験・実行の記録（入力版、成果物、判定、実費または未記録の理由）が残っていること。

## 工程2: 承認工程の実装（10/29–30）

- **承認の最小操作**: 凝った UI は作らない。承認は記録への記入で行う（誰が、いつ、どの原本版と FACT 版に対して承認したかを残す）。承認の記録形式は、工程3が依存するため、10/29 の早い時点で先に固定する。
- **承認できる条件**: 照合で矛盾がない場合に限る。矛盾がある場合は承認できない分岐とし、「警告を無視する承認」は作らない（G-INV-3）。未記載は未記載として表示に残し、承認の対象に含めない。
- **無効の判定**: 原本版または FACT 版が承認時点と異なれば、既存の承認は無効と判定し、照合からやり直す（承認後の原本変更は停止条件でもある）。

完了条件: 正常系で承認が記録できること、矛盾がある入力で承認できないこと、版が変わった場合に無効と判定できることの 3 点を、実行記録として残すこと。

## 工程3: 生成工程の実装（10/29–30）

- **最小形を先に固定する**: 対象は E01 のみとする。生成する文は FACT の項目に対応する範囲に絞り、項目に対応しない文は作らない。
- **入力の制限**: 承認済みで、かつ版が有効な FACT だけを入力とする。未承認、または承認が無効になった状態では実行できない。FACT にない情報を生成物に足さない（モデルは Spark 1.3 系）。
- **根拠の保持**: 生成した文ごとに、根拠とする FACT 項目と原本の行 ID を付けて保持する（準備資料の確定要件）。行 ID を持たない文は生成物に含めない。

完了条件: 承認済み FACT からのみ生成できること、未承認では実行できないこと、生成文のすべてに行 ID が付いていることを、実行記録として残すこと。

## 工程4: 再検証の実装（10/30）

- **照合の内容**: 生成物が承認済み FACT（承認時点の版）と一致するかを照合する。数値・単位・範囲・否定・条件付き表現は、行 ID をたどって機械検証できる範囲で突き合わせ、意味の対応は人間の確認に残す。
- **不一致の扱い**: 食い違えば生成工程（工程3）へ差し戻す。再検証の合格の効果は「デモ内プレビューの許可」までであり、公開承認ではない（G-INV-4）。公開と読める表現が生成物にあれば、不一致として扱う。

完了条件: 一致する生成物がプレビュー許可になること、意図的にずらした生成物が差し戻しになることの 2 点を、実行記録として残すこと。

## 工程5: 統合実行とデモシナリオ化、公開プレビュー（10/30–31）

- シナリオの記録は、11/01 のデモ動画の台本の下書きにそのまま使える形（場面の順序、各場面で見せる記録と成果物）で残す。

M2（10/30、roadmap）の判定対象はここまでとする。すなわち、工程1–4 と一続きの実行形が通り、記録が残っていることを M2 の達成とする。次項の公開プレビューは M2 に含めない（10/31 の作業とする）。この切り分けは roadmap の「10/30 に全工程が通る状態、10/31 にデモシナリオの固定」と矛盾しない。roadmap 自体の改訂は本書では行わない。

### 公開プレビュー（10/31。必須物ではない）

- **位置づけ**: Cloudflare Pages の公開プレビューは任意の追加物であり、提出の必須物（公開リポジトリ、デモ動画 3 分、Cerebral Valley への提出）ではない。遅れた場合は切り離してよい（「リスクと切り離し」参照）。
- **承認**: Pages プロジェクトの作成とデプロイは外部リソースの作成と外部への送信に当たるため、着手前に本人の明示承認を得る。承認を得るまではセットアップしない。セットアップ自体は承認が得られ次第、前倒しで行ってよい（実物の生成物への差し替えは本工程で行う）。
- **置き場所と分離**: 独立した Pages プロジェクトとし、pages.dev のサブドメインを使う。リポジトリの `site/` を公開し、MJ のドメインや DNS、MJ の本番環境には触らない。
- **置くもの**: E01 で生成された LP プレビュー、E02 で停止した状態の表示、プロジェクト説明と GitHub の記録へのリンク。
- **公開前チェック**: 公開する前に、次を確認して結果を記録に残す。(a) LP プレビューに架空の求人であることが明示されている（実在の求人と誤認される表示にしない）、(b) 実データ、秘密情報、未確定の主張が混ざっていない、(c) 再検証の合格を公開承認と読める表現にしていない（G-INV-4）。1 つでも満たさなければ公開しない。
- Pages の規約や料金の詳細は未確認であり、本書では公開可否を断定しない。提出ルールとの最終照合は、Official Rules の精読（2026-10-31 まで）と最終監査で行う。

完了条件: 統合実行の記録とシナリオ記録が残っていること。公開した場合は、承認を得たことと公開前チェックの結果が記録に残っていること（公開しない判断をした場合も、その判断を記録に残す）。

## 工程6: 提出の形に整える（10/31–11/02）

- **記録の欠落チェック**: 各工程の記録が `loops/` に残り、必須項目（入力版、成果物、判定、実費または未記録の理由）を欠いていないことを確認する。欠けがあれば、この工程で新規に作るのではなく、該当工程の記録として補う。
- **README**: L1 と L2 の関係、再現手順（必要な環境変数名と実行順序、期待される結果への参照。キー値そのものは書かない）、記録の場所を説明する。リポジトリ名が汎用的である点は、README と提出文面で内容を明確に示すことで補う（D6）。
- **ライセンスと帰属**: LICENSE と、使用したモデル・ツールの帰属表記を配置する。どのライセンスにするかは本人の判断事項であり、本書では決めない（未決と明示する。配置する作業だけを本工程に含める）。
- **提出文面の準備**: Cerebral Valley の提出フォームの入力項目を事前に確認し、プロジェクト説明文、トラック（Indie、D2）、リポジトリと動画の URL の置き場所、使用ツールの説明の下書きを用意する。フォームの正式な項目が未確認の間は、下書きを確定文として扱わない。
- デモ動画（11/01）と最終監査・提出（11/02）は `docs/roadmap-v1.md` のとおりとする。最終監査では、新規性、公開範囲、動画、Meta モデルの実質的な利用を照合する。

完了条件: 記録の欠落がないこと、README と提出文面の下書きが用意できていること、ライセンスの要否と帰属の置き場所が（選択自体は未決でも）明示されていること。

## リスクと切り離し

転びやすい順序と、遅れた場合の扱いを先に決めておく。

1. **工程3（LP 生成）が最も転びやすい**（初めての生成経路で、文章の品質、行 ID の保持、「足さない」制御が重なる）。最小形（E01 のみ、文を FACT の項目に対応させる）で先に通す。それでも生成が安定しない場合は、FACT の表形式の表示をプレビューの代替とし、生成文の表示は落とす（プレビュー許可までの効果は代替でも守れる）。
2. **工程5の公開プレビューが次に転びやすい**（初回の外部セットアップを含む）。承認とセットアップを前倒しにし、それでも遅れる場合は公開プレビューを切り離す。提出は公開リポジトリ、動画、提出フォームで成立させる。
3. **範囲の縮小順序**: 遅延した場合は、公開プレビュー → ペルソナレビュー（未決のため実施しない判断を含む）→ E03 以降の拡張、の順に落とし、工程1–4 と提出の形（工程6）は落とさない。
4. バッファ（11/03・11/04）は roadmap のとおり確保されている。本書の工程をバッファ側へずらす場合は、動画と提出を締切直前に置かない順序を維持する。
