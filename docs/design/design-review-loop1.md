## 観点1: 要件との照合

判定: 修正

根拠:

- 4 不変条件（架空データのみ、止める条件、「警告を無視する承認」を設けない、再検証の合格は公開承認ではない）は context-pack §5（47–51 行）と review-notes §2（18–22 行）に確定要件としてある。
- 基本設計は §1（12 行）で要件の非変更を宣言し、§6（63 行）で応募資料・context-pack との照合を監査対象に含める。直接の違反記述はない。
- しかし 4 不変条件が基本設計の監査チェックポイント（§6）にもゲート管理（§7）にも明示的に引き継がれていない。L1 の監査が L2 成果物を検査する際、照合すべき不変条件が設計書上で特定できない。

修正案:

- §6 または §7 に「プロダクト不変条件ゲート（仮）」として 4 条件を列挙し、各条件の検査方法（機械検証／人間確認の別）を付ける。例: 架空原本 ID 以外のデータ混入＝機械検証、承認画面の分岐＝人間確認。
- C2（review-notes 40 行）に対応し、§4 に「プロダクト実行時のモデル割当は本書の対象外であり未定のまま」と一行追記して適用範囲を明示する。

## 観点3: 監査設計の妥当性

判定: 修正

根拠:

- 判定三段階（§6、65 行）: 「合格」「修正」「前段階への差し戻し」の定義・使い分け基準・各判定に必須の付帯物（理由書式、再監査条件）がない。
- 即時停止（§6、66 行）: 「重大なセキュリティ・安全上の問題」の重大さの定義、停止後の手順（誰へ通知、記録場所、再開条件）がない。
- エスカレーション（§6、67 行）: 「同じ経路」の定義（同一ゲート／同一パス／同一文書のいずれか）、人間へ渡す情報の形式、応答がない場合の扱いがない。また「自動ループを停止」とあるが、§11（109 行）は文書と Git の手動運用を初期方針としており、自動化の前提が不整合（N3）。
- 停止条件が §6（66 行）と §10（104 行）の 2 か所に分散し、相互関係（同一の停止か、別種か）が未定義（N2）。さらに、新規性リスク（期間外コードの混入、context-pack §2・17 行由来）と実データ混入（context-pack §5・47 行由来）がどちらの停止リストにも明示されていない。

修正案:

- 三段階判定の定義表を追加する（例: 修正＝同工程内で直せる／差し戻し＝前工程の前提を覆す、再監査の要否つき）。
- §6 と §10 の停止条件を一表に統合し、発動時の手順（通知先＝本人、記録先＝当該 loop 記録、再開条件）を付ける。新規性リスクと実データ混入を停止条件に加える。
- 「同じ経路」を定義し（推奨: 同一ゲート ID での連続差し戻し）、エスカレーション時の提出物（差分・両論併記・判断依頼文）の雛形を用意する。N3 として「自動ループ」の語を現行運用（文書・Git）に合わせて言い換える。

## 観点4: ゲート管理

判定: 修正

根拠:

- 流れ（候補→検証→承認→昇格、§7・72–73 行）とゲートの版管理・由来記録（§7・75 行）はある。review-notes §7（67 行）の肥大化リスクへの応答として方向は正しい。
- しかし回す手順として不足がある。(a) 検証ステップの実施主体と合格基準がない。(b) ゲート自体の監査（§7・74 行）の「定期的」の頻度・契機・実施者がない。(c) 候補置き場の形式が未定義（review-notes §8・75 行の `docs/gates/` 案は「確定は設計監査の指摘を踏まえてから」とある）。(d) §5（57 行）は文脈パックにゲート ID 参照を求めるが、初回パス時点ではゲートが存在しないブートストラップ問題がある（N7）。

修正案:

- ゲート 1 件あたりの最小レコード（ID、版、検査対象、合否基準、由来、状態: 候補／検証中／有効／撤回）を定義し、`docs/gates/` 構成案の採否を決める。
- ゲート自体の監査の契機を「各ループ終了時＋ゲート 5 件到達時」のように具体化し、実施者を監査ラインと明記する。
- N7 として初回パスの例外規則を追加する（例: loop-001 はゲート参照なしで開始し、得られた候補を loop-001 終了時に登録する）。

## 観点5: 実験設計

判定: 修正

根拠:

- 再現性検証と改善実験の区別（§8・79–81 行）と単一要因変更の原則（80 行）は明確で、9 日間・ソロ体制でも理解できる粒度である。
- 実行可能性の懸念が 2 点ある。(a) 再現性検証（同一条件の再実行）が必須か任意か、どの契機で実施するかがなく、必須と読めば API 費が倍増し $100 実使用枠を圧迫する。(b) §9（87 行）の記録項目は 7 分類（89–95 行: 入力版、モデル・条件、成果物、監査結果、ゲート変更、コスト・時間、合格率等）で、ソロ・9 日間で毎パス全項目は重い。一方「可能な範囲で」とあるため監査の完全性が保証されず、必須と任意の線引きがない（N5）。

修正案:

- 再現性検証の実施契機を限定する（例: 監査で結果の信頼性が争点になった場合のみ）。争点なき再実行はしない原則を明記する。
- 記録項目を「必須（入力版、出力、監査結果、実費）」と「任意（所要時間、再試行回数、合格率等）」に分け、必須欠落は監査で「修正」判定とする規則を付ける。
- 実験記録の置き場として review-notes §8（79 行）の `experiments/` 案の採否を決める。

判定: 修正

根拠:

- 不足が 3 点ある。(a) 役割別配分は D5 へ送られ（§10・103 行）、モデル割当決定まで暫定の支出上限がない。loop-1 監査や最小実証は配分決定前に支出する。(b) $75 の「新規探索」の定義（実装・再検証との線引き）がない。(c) 超過時のカード請求条件（context-pack §3・27 行: 残高 ¥3,000 到達時または 11-01 請求）に対する hard stop が設計にない。Spend Limit 通知は未確認（context-pack §3・29 行）のまま、確認行動が設計に組み込まれていない。
- 費用が読めない活動: (1) 開発エージェント側推論費（Muse Code 側課金の単価・計測方法が未確認、review-notes §6・57–58 行も指摘）。(2) 再現性検証の再実行費（実施契機が未定義、観点5 と連動）。(3) 差し戻しループの上限なき反復費（同一経路 2 回ルールはあるが経路横断の上限なし）。(4) Wonder の単価（未確認、review-notes §6・58 行）。(5) パートナー枠は未申請のため $150 以外の枠は計上不可（context-pack §3・30 行）。
- 台帳の表現差: §10（101 行）「同じ台帳で確認」と review-notes §6（57 行）「台帳で区別して記録」は両立可能（同一台帳・区分列）だが、文言の不整合に見える（N6）。

修正案:

- D5 確定までの暫定ルールを即設する（例: loop-001 終了まで $10 上限、超過時は本人確認）。$75 ルールの「探索」を定義する（例: 未確定の設計・モデル・手法の試行。確定済み実装・再検証は探索に含めない）。
- 実使用 $100 到達を hard stop（予備 $50 の使用は本人承認制）と明記し、Spend Limit 通知状態の確認を loop-001 の必須タスクに加える。
- 台帳は「同一台帳・区分列（API 費／エージェント推論費）」と一本化し、実費は dev.meta.ai Billing 実績と突き合わせる（review-notes §6・59 行を継承）。

## D1–D8 の決定順序（監査の立場から）

推奨順序と理由:

1. D1（提出物の位置づけ）: 最優先。監査ゲートの検査対象が L1 か L2 か統合かで変わり、D1 未定ではゲートも受け入れ条件も書けない。C1・N10 と連動。
2. D4（モデル割当の検証手順）: Wonder の 1 回テストコール＋単価確認は安価で、D5 と役割割当の前提になる。不確実性の早期解消効果が最大。
3. D3（最小実証の範囲）: loop-001 の題材を固定しないと監査の照合先（候補 A なら E01・E02 の期待結果）が定まらない。候補 A 推奨を監査としても支持する（期待結果が既定で停止条件が明確なため）。
4. D5（予算の役割別配分）: D4 の後に正式配分。ただし暫定上限（観点6 の修正案）は D5 を待たず即設すること。
5. D8（ゲート昇格の承認者）: 初回ゲート昇格（loop-001 終了時が見込み）までに決定すれば足りる。N4 の権限境界と合わせて決める。
6. D6（提出リポジトリ）: 実装開始前なら低コスト。遅れるほど新規性証跡・履歴連続性（N12）のリスクが増すため D3 の前後で片付ける。
7. D2（トラック）: 提出とパートナー申請に必要だが、設計・ループ運用の進行を止めない。提出期限（11-04 21:00 ET）からの逆算で期限を切る。
8. D7（パートナー申請）: 最後。D2 が前提で、各社裁量・保証なし（context-pack §3・30 行）のため $150 の範囲で計画を閉じさせ、追加枠は不確実な上振れとして扱う。
