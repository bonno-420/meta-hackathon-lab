## 観点3: スキーマ完全性チェックの健全さ

判定: 修正（候補としての基準の限定は正直だが、到達性と検証証跡に欠落がある。F2）

- 実装（`src/extract-and-check.mjs:51-74`）は、ゲート候補の合否基準（`loops/loop-006/gate-candidate-schema-completeness.md:8`）どおり、期待キー15件の欠落・余分・重複、フィールドの有無、status の列挙、stated 項目の sourceLine・quote の存在を検査する。監査側が関数を抽出して実行したところ、合格ケースと、キー欠落・キー重複・フィールド欠落・items 非配列の4通りすべてで不合格になることを確認した。候補記録の最小項目（ID、版、検査対象、合否基準、由来、状態）もそろっており（同:5-12）、昇格していない扱いは D8 と整合する。
- 基準の対象外であるものが合格になることは、監査側でも確認した。捏造された quote、存在しない sourceLine（L99）、未記載項目の value が null でないこと、normalized の型の誤り、stated の value が空文字列であることは、いずれもこのチェックでは不合格にならない。これらは「完全性」という候補の基準がそもそも主張していない範囲であり、基準の限定自体は正直である。特に引用の逐語性については、このチェックに含めるべきではないと判断する。理由は、完全性（構造の検査）と逐語性（原本との対応の検査）は検査対象も必要な入力も異なり、一つの合否基準に混ぜると、候補としての合否の意味が曖昧になるためである。逐語性は別チェックとして扱うべきものである（F2）。
- ただし、次の2点は候補の範囲内での欠落である。
  1. **到達性**: `runLive` は `facts.items` が配列のときだけチェックを呼ぶため（`src/extract-and-check.mjs:335-340`）、実 API 経路で items が配列でない出力が来た場合、`schemaCheck` は記録に残らず（null のまま）、不合格として記録されない。関数単体は非配列を不合格にできる（同:52-54）のに、実経路では到達できない。またオフライン検証では `schemaCheck` は戻り値に含まれるだけで、総合の合否は従来の6チェックのみで決まる（同:253-254）。
  2. **検証証跡**: 否定テストは「本体関数を直接実行して検証」という申告のみで（`loops/loop-006/run-record.md:36`、gate 記録:11）、テストケースと結果の成果物がリポジトリにない。関数は export されておらず、ファイル末尾で `main()` が無条件に実行されるため（同:389-392）、コミットされた形のままでは他者が同じ方法を辿れない。同様に、オフライン回帰の再実行（同:14、scratch 出力）も成果物が残っていない。なお、監査側は現在のコードでオフライン検証をリポジトリ外の出力先で再実行し、従来の6件すべて pass とスキーマ合格を確認済みであり、主張の内容自体は正しい。問題は内容の真偽ではなく、検証したという記録の再現性である。

## 観点4: FACT 版固定の設計（工程2の前提として足りるか、sha256 の対象と置き場所）

判定: 修正（組の特定は人手では足りるが、機械的な照合の錨が不足している。F1）

- 良い点: 固定された `src/facts/FICT-J01-facts-v1.json` の items は、採用元である v1.1 実行の FACT と完全一致することを監査側で確認した。manifest には、原本 ID・版とその所在、プロンプト版、モデル、採用元の実行と開始時刻、スキーマ合格と E01・E02 の判定、版の決め方（採用のたびに +1、変わったら別ファイルで作り旧版は上書きしない）、採用者・採用根拠、未承認であることがそろっている（`src/facts/FICT-J01-facts-v1.manifest.json:2-24`）。工程2が「原本版と FACT 版の組」を指名するための識別情報としては足りており、`src/facts/` という置き場所も、実行記録（loops）と採用済み成果物を分ける意味で妥当である。
- **問題は sha256 の再現性である。** manifest と run-record に記載された `3dc7fbd1…534ec`（manifest:5、run-record:44）は、Git に保存されたバイト列（LF、3,282バイト）のハッシュとは一致する。しかしこの Windows チェックアウトの実ファイル（CRLF、3,413バイト）の sha256 は `46d951bb…f28e4` となり、一致しない。`core.autocrlf=true` で `.gitattributes` は存在せず、ハッシュの対象（ファイルのバイト列か、Git blob か、正規化した JSON か）と計算手順が manifest に書かれていない。監査依頼が求めた「sha256 の一致の確認」は、通常のファイルハッシュ計算では成立しない状態であり、工程2の承認・無効判定をこの sha256 で機械照合することは現状ではできない。
- あわせて、**原本側にコンテンツハッシュがない。** manifest の original は ID・版・ファイル名のみであり（manifest:6-10）、原本が「v1」の表記のまま書き換わった場合に、版の一致だけでは検出できない。工程書が無効判定を「版の一致で判定する」としている前提（`docs/design/implementation-steps-v1.md:30`）を機械的に担保するには、原本側も同一のバイト定義でのハッシュが必要である。
- 表記の揺れとして、factsVersion は整数 `1`、原本版は文字列 `v1`、ファイル名は `-v1`、run-record は組を `FICT-J01-facts-v1` と呼ぶ（run-record:60）。工程2の承認記録の様式では、組を指す単一の形式（ファイル名と sha256 を含む形）を先に固定すべき事項として申し送る。これは様式設計の宿題であり、本修正の対象には含めない。

## 修正事項と修正の完了条件

いずれも工程1の中で直せるものであり、live API の再実行は不要で、追加の API 費用は発生しない。再監査はこの2件に限定する。
