## 2. 訴求の核

LPの文は、承認されたFACTの範囲でだけ生成する。原本と食い違う入力は、生成に進まず止まる。

生成の流暢さではなく「拒否の設計」を伝える。承認なしに生成しない、再検証の合格は公開の許可ではない、未記載は未記載として残す。この3つの「しない」が製品の主張である。

補助の核（開発プロセス側）: ハイエンドモデルでなくても、能力に合った設計と効率のいい開発でここまでできる（実行は Muse Spark 1.3 Contributor、1回の統合実行は約 $0.002）。

## 4. リード文案（問題提起）

求人LPの誤記は、現場では事故である。給与、勤務時間、交通費。原本と違う数字が載れば、応募者との信頼も、媒体としての信用も失う。生成AIは流暢に書けるが、原本にない条件を足したり、数字を取り違えたりする。このデモは、生成の前に抽出・照合・人間の承認を置き、食い違いがあれば後段に進まず止まる。生成された文はすべて、原本の行と承認済みFACTにたどれる。

## 7. トーンの原則

- おしゃれな短文キャッチコピーに寄せすぎない。詩的な表現はできるだけ避け、事実と情報を伝える
- デメリットは隠さず、事実のまま別の角度から言い換える（例: 体力が要る仕事なら「体を動かすのが好きな方へ」「動きのある仕事が好きな方へ」。きついが高時給なら「手に職と安定した生活」）
- 誇張しない。効果の断言（応募が増える等、未検証のこと）は書かない
- 数字で語る（コスト、件数、時刻、ハッシュ）
- 「止まる」を弱みではなく設計として語る
- 架空データであることは常に明示する
