## 発見した矛盾・不一致

### K1: AGENTS.md の冒頭と README が「Muse Code 中心」の記述のままである

- `AGENTS.md` の Mission は "autonomous app development with Muse Code" とし、`README.md` も同じ文言である。リポジトリ作成時のテンプレート由来とみられる
- これは D4（駆動は Codex / OpenCode、Meta 製品を優先）とも、今回の前提（Muse Bot 主体）とも一致しない

### K2: 「開発の主体」の記述が文書ごとに異なり、一意に定まっていない

- AGENTS.md 英語部: Muse Code が主体のように読める
- AGENTS.md プロジェクト固有節: 駆動環境は Codex（主）/ OpenCode としつつ「Muse Code など Meta の開発基盤も優先する」と併記する
- D4 と台帳の現行方針: 起点・全体統括は Muse（統括）、ライン別（設計・監理・制作）の Wonder が作業統括、Spark が作業員。実際の駆動は Codex / OpenCode のセッションで、本人がセッションを立ち上げてパスを中継する
- context-pack v1 §6: 「起点は Muse（相談相手）」「Wonder が設計・監査・制作の基幹」とし、現在のライン体制より前の構想のままである
- 今回の前提（Muse Bot が調査・矛盾特定・調整案作成・監査を経て進める主体になること）は、上記のいずれの記述ともそのままでは一致しない

### K3: roadmap の「進め方の原則（再掲）」が旧モデル割当のままである

- 「サブ（Spark 1.3 Contributor）が実施と一次確認、Wonder は監査と判断」とあり、D4 追記3以降（Wonder は作業統括、受け入れは統括と本人）と台帳の現行方針に追随していない

### K4: 確定事実・現況の記述に鮮度のずれがある

- context-pack v1: §1「トラックは未決定」（決定済み: Indie、D2）、§3「パートナーは未申請」（Baseten 申請済み、D7）、§4「Wonder の実呼び出しは未確認」（2026-10-27 に本人が確認済み）、§6「コードは未着手」（ループ2で `src/` を実装済み）
- roadmap の「現在地」と「未決・宿題」: D2・D5・D6・D8 を未決として締切つきで並べているが、いずれも 2026-10-27 に決定済み（basic-design v1.1 §11 の未決表と同種のずれ。v1.1 側は追記で対応済み）

### K5: loops/ へのパス記録が不足している

- AGENTS.md はパスごとの記録を `loops/loop-NNN/` に残すことを必須としているが、実在するディレクトリは loop-002 のみである
- ループ1（設計監査）、ループ3（設計改訂）、ループ4（工程の確定サイクル）の記録は `docs/` と台帳に分散しており、loops/ にはない。監査可能性の観点で gap である

### K6: 実装の現状（矛盾ではないが、調整後の接続点として記録）

- `src/` は FACT 抽出と機械照合のみ（ループ2）。確定版の工程1–5 は未実施であり、今回の整合の完了後に工程1から始める流れと一致する
- 工程1の依頼文（`docs/prompts/step1-brief.md`）は現行体制（制作ライン宛て）で書かれているため、主体の確定に合わせて書き換えが必要になる見込み

### K7: 「Muse Bot」の用語と定義がリポジトリ内に存在しない

- 本プロジェクトの文書のどこにも「Muse Bot」の定義はない。前提の中核用語が未定義のままでは、調整案の確定ができない（未確認事項 U1）

## 未確認事項

- **U1（最重要）: 「Muse Bot」の同定。** 統括（Muse、Meta のパーソナルエージェント）自身を指すのか、別のエージェント（製品・機能）を指すのか。名称だけで推測しない。本人の確認が必要
- **U2: Muse Bot の実際の機能範囲。** Git への直接の読み書き、ファイル編集、コマンド実行、Meta Model API の呼び出しの可否を確認してから前提にする。U1 が統括を指す場合の実測は次のとおり: GitHub の読み書きは接続済み（書き込みは本人の承認カード経由）、自分の VM 上でのシェル実行とブラウザ操作が可能。一方、Meta Model API のキーは本人の Windows の環境変数にあり統括の VM にはないこと、リポジトリのローカルフォルダ（本人の PC 上）へは直接アクセスできず GitHub 経由になることは、制約として明記する
- **U3: ライン体制との関係。** Muse Bot を主体とした場合に、設計・監理・制作の各ラインと Wonder / Spark の役割をどう位置づけるか（主体の内部の分担か、独立監査の担い手として残すか）。U1 の確定後に決める
