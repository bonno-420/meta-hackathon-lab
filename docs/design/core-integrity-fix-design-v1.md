## A-1. 修正①: 確認記録と生成物の結合（verify.mjs）

### 現状の穴（実測の再確認）

`decideVerdict`（verify.mjs:183）は人間の確認について、status が completed、全ての文に result があり、全て「対応あり」であることだけを見る。確認記録の文と対象の生成物の文との照合がなく、無関係な文の確認記録でも pass になりうる。あわせて、これは知見台帳 L-024・L-025 で将来の道具改訂として残っていた項目の具体化である。

### 結合方式（決定）

判定時に、確認記録の文を生成物の文と直接照合する方式とする。確認記録にハッシュを持たせる方式は採らない（理由: 確認記録は人間が記入する成果物であり、ハッシュを人手で正しく運ぶ前提は弱い。文そのものの照合なら、既存の確認記録が持つ text をそのまま使える）。

- `decideVerdict` に生成物（文の列）を渡す引数を追加する。`runVerification` は読み込んだ生成物オブジェクトをそのまま渡す。生成物が渡されない呼び出しでは、人間の確認を pass と判定しない（未確定として倒す。fail closed）。
- human-confirmation の pass 条件に、次を必須として追加する。(a) 確認記録の文数が生成物の文数と等しい。(b) 各文について、確認記録の text が同位置の生成物の text と文字列として一致する。(c) 従来の条件（completed、全 result 記入、全て「対応あり」、確認者と確認日時があること）も維持する。あわせて L-024 のうち「確認者・確認日時の有無」はここで一緒に検査する。
- 不一致の場合の判定は fail とし、category は human-confirmation とする。理由文には、文数の不一致か、どの位置の文が一致しないかを含める（本文の全文は理由に載せない）。
- factKeys・sourceLines の対応そのものは従来どおり人間の確認の内容であり、機械照合の対象にしない（物差しを広げない。L-026 の前提を維持する）。

### loop-010 の移行

- loop-010 の確認記録は、生成物の文を写した text を文ごとに既に保持している（buildHumanConfirmationTemplate が生成物から写す形式であり、確定済みの記録も同形式）。したがって新方式でも、生成ファイルを変更せずに pass と判定できる。移行に追加の作業は要らない。
- 移行の確認方法: 修正後の道具で loop-010 の生成物と検証結果を読み、判定が pass のままであることを回帰テストと着地時の記録で示す。新しい生成と確認のやり直しは行わない。

## A-2. 修正②: プレビュー生成時の同一性照合（build-preview.mjs）

### 現状の穴

`writePreview`／`buildPreview` は verdict が pass かどうかだけを見ており、検証結果が対象とした生成物と、実際に表示する生成物の同一性を確認していない。PASS 後に生成文を差し替えてもプレビューが作れる。公開中のプレビューはこの経路で作られている。

### 照合方式（決定）

- `writePreview` は HTML を作る前に、次をすべて照合する。(a) 対象の生成ファイルの現在の sha256（F1 の定義。既存の `sha256File` を使う）が、検証結果の `target.generationSha256` と一致する。(b) 生成物の文数が `target.sentenceCount` と一致する。(c) 検証結果の `target.generationFile` が、今回渡された生成ファイルと一致する（パスの表記はリポジトリ相対でそろえる）。
- 1 つでも一致しなければ、HTML を書かずに理由を返して終了する（既存の「pass でなければ作らない」と同じ倒し方）。既存のファイルがある場合に上書きしないことも明記する。
- 純粋関数である `buildPreview` 本体にはファイル照合を持ち込まず、照合は `writePreview` 側で行い、結果を `buildPreview` の呼び出し条件とする。テストは `writePreview` 経由と、照合だけを切り出した関数で確かめる。
- 公開済みプレビューの再生成時も同じ経路を通す。照合が通らなければ公開物を更新しない。

## A-3. 修正③: 生成の鮮度と終了コード（run-demo.mjs）

### 現状の穴

`liveDeps.generate` は子プロセスの終了コードを見ず、実行記録ファイルが存在すれば前回のものでも読み、status が generated なら前回の生成ファイルを今回の生成物として進める。抽出側（`liveDeps.extract`）も同型である。

### 対象範囲（決定）

生成と抽出の両方を対象とする。理由は、同型の穴が両方にあり、片方だけ塞いでも「失敗を成功として扱う経路」が残るためである。変更箇所は `liveDeps` の 2 関数に限る。

### 鮮度と終了コードの方式（決定）

- 子プロセスの終了コードが 0 でない場合は、その時点で失敗として返す。実行記録ファイルと生成ファイルは読まない。
- 鮮度は「今回の実行で書かれたこと」で担保する。子プロセスを起動する前に、実行記録ファイルと生成ファイルについて、存在の有無と sha256 を控える。終了後に、実行記録ファイルが新規に作られたか、ハッシュが起動前と変わっていることを必須とする。変わっていなければ失敗として扱い、前回の内容は使わない。
- 実行記録の status が generated（抽出側は completed 相当）であることの確認は従来どおり必須とし、上記の終了コードと鮮度の条件と合わせて初めて後段へ進める。
- 失敗の場合の記録には、終了コードと、鮮度が確認できなかった旨を含める。費用は従来どおり未記録とし、推測で埋めない。

## A-4. 回帰テストの条件

既存テストが全部通ることを前提に、次をテストとして固定する。再現条件は統括の実測（ブリーフ①〜③）そのものを使う。

| # | 対象 | テスト条件 | 期待 |
|---|---|---|---|
| T1 | ① verify | 生成物と無関係な文（1文でも）の確認記録を completed・全て「対応あり」で与える | pass にならない |
| T2 | ① verify | 文数が生成物と異なる確認記録を与える。本文が途中だけ一致する場合を含む | pass にならない |
| T3 | ① 移行 | loop-010 の生成物と確定済み確認記録の組を与える | pass のままである |
| T4 | ② preview | PASS の検証結果を使い、生成ファイルの文を 1 文変更してからプレビュー生成を試みる | HTML が作られない（既存ファイルも上書きされない） |
| T5 | ② preview | 検証結果が対象とした生成ファイルと別のファイルを渡す | HTML が作られない |

| T7 | ③ run-demo | 子プロセスが終了コード 0 で終わっても、実行記録が更新されない状態にする | 成功として扱われない |

テストの置き場所は既存の対応するテストファイルとし、新しいテスト基盤は作らない。

## B. 見せ方の整理（設計）

対象は公開プレビュー、README、提出文、動画シナリオの素材。本節は文面と構成の設計であり、実装と公開は制作と着地の段階で本人の承認を得て行う。

### 共通の原則

- 記録の再生をリアルタイム実行のように見せない。各画面と文面では、それが「記録された実行と監査の再生」であることが分かる表記にする（実行日時と記録への参照を置く）。
- 人間が判断している箇所（承認、確認、受け入れ）を隠さない。誰が何を判断したかを、自動化の成果と並べて示す。

### 構成（プレビュー・README・提出文で共通の骨格）

1. **冒頭**: 何を作っているかを短く置く。AI が設計・制作・実行・監査・改善を回す開発・実行基盤であり、デモは架空求人の編集ワークフローであること。Muse が起点で設計・監査・修正を回してきたことを含める。
2. **通常の流れ**: 原本の固定 → 抽出 → 照合 → 人間の承認 → 生成 → 再検証（独立）→ プレビューの順に、記録を根拠として示す。
3. **停止の見せ場**: E02（原本の時給 1,500 円に対して要約が 1,700 円なら、矛盾として生成前に止まる）を、両方の値と出典を添えて置く。生成物ではなく停止の記録であることを明示する。
4. **監査で出力が変わった例（状態を明示して扱う）**: 候補は loop-012 → 013（企画を先に置く 1 要因の変更で散文評価が変わった記録）。ただし両者は未着地・ゲート未判断の拡張であるため、組み入れが決まるまでは本体の実績と混ぜず、「拡張の実験記録（未組み入れ）」と状態を明示した別の枠で扱う。組み入れない判断の場合はこの枠ごと置かない。
5. **担当と改善**: 統括（Muse）と各ライン（設計・監理・制作・書き込み）の担当範囲と、各ラインの監査で何が改善されたかを短く示す。改善の例は監査の記録（指摘と修正の組）から取り、成果だけを並べない。

動画シナリオの素材は、上記の骨格に沿って場面の順序と見せる記録を指定するところまでを本設計の範囲とし、台本の確定は動画制作の段階で行う。
