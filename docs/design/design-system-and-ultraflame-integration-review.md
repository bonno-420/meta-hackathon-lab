補足（事実）: Bootstrap は両リポジトリの現行コード・文書に実績がない（hackathon 側は grep 0 件、UltraFlame 側はファイル名と主要ファイルの範囲で確認できず）。Tailwind は UltraFlame 側に作法文書（版固定の方針つき）がある唯一の候補である。ただし UltraFlame の実読したコンポジションは手書き CSS であり、Tailwind の実使用は確認できていない（§7）。

補足（監査指摘 A5 への対応）: 候補の漏れとして2つを追加評価する。E. 現行＋CSS変数化（手書きのまま色・余白等を `:root` 変数に寄せる）: 現状スタックとの適合性は完全で、再現性も最良のまま、設計トークンの形式借用（§5-3）と接続しやすい。F. クラスレス系（Pico.css 等）: HTML にクラスを足さずに体裁が整い、適合性は高い。ただし E・F とも両リポジトリに実績はなく、本調査では未実測のため、品質・速度の評価は定性的な判断にとどまる。

補足（同）: 本表の「AI エージェントの実装安定性」「短期間の開発速度」の評価は、実測に基づかない定性的な判断である。また Bootstrap を CDN で使う場合の SRI（Subresource Integrity）は、版固定と組み合わせることで配信内容の同一性を担保する手段として、§5 の判断に含めた。

## 3. UltraFlame の機能をハッカソンプロジェクトに実装する（取り込み）（C・前提訂正により差し替え）

前提（2026-10-28、本人）: UltraFlame を「使う／統合する」のではない。UltraFlame の中から必要な機能を、ハッカソンプロジェクトの拡張としてプロジェクト側に実装する。初稿の方式比較（独立維持／パッケージ化／モノレポ／API 連携）は、この前提に合わないため判断対象から外した（比較自体は監査記録とあわせて経緯として残る）。

## 5. Muse の推奨と根拠

1. **（前提訂正により差し替え）UltraFlame との統合方式の採用は行わない。代わりに、UltraFlame の機能のうち必要なものを、仕様・考え方を参照してハッカソンプロジェクト側に新規実装する（取り込み、§3）。** コードの直接移植（形 ii）と第三者コードの取り込み（形 iii）は行わない。根拠: 提出物の「期間中の新規作成」要件（新規性リスク、監査指摘 A4）、ライセンス境界（§1.2）。なお UltraFlame 自身のガバナンス（無関係なリポジトリを吸収しない、第二の編集正本を作らない）とも、取り込みは矛盾しない。

2. **生成 LP・プレビューの CSS は、判断ゲート1で次の3択から本人が選ぶ（監査指摘 A2 を受けて改訂）。**
   - (a) 手書き継続（現行 A）: 現行ページの CSS は5ルールのみで、今回の提出範囲では限界便益の観点で足りる。再現性は最良（同一入力→同一バイト列＋sha256 照合の文化と整合）。
   - (b) Bootstrap・版固定 CDN＋SRI: 暫定決定は既に「バージョン固定」であり、無固定 CDN への批判は当たらない。SRI で配信内容の同一性も担保できるため、公開プレビューの用途には十分というのが監査側の独立判断である。残る論点は、取得可否と第三者リクエストという外部依存のみ。
   - (c) Bootstrap・版固定ローカル配置: オフライン表示・同一オリジン・第三者リクエスト排除の範囲で (b) に優れるが、必須ではない。配置仕様の案は本節の補足に定義する。
   補足: 本人は Bootstrap へ個人的にこだわりはないことを確認済み（2026-10-28）。仕様駆動（トークンを CSS 変数で実装する）との相性では、(a) 手書き＋変数化が最も素直という観点も判断材料に加える。
   統括の見解: 提出範囲では (a) で足りる。
   **決定（2026-10-28、本人、判断ゲート1）: (a) 手書き継続＋CSS 変数化を採用する。**(b)(c) は採らない。必要になれば §9 の再評価条件で戻る。Bootstrap を使う場合も、本人が重視した「メジャーなライブラリを参照できると楽」という趣旨（作例の厚さ、エージェントの実装安定性）は (b)・(c) のどちらでも満たせる。UltraFlame の作法文書（§1.3）は判断材料の1つだが、動画レンダリングに関する作法の類推であり、それだけで (b) を退ける根拠にはしない。

   補足（(c) の配置仕様案。監査指摘 A6 への対応）: 配置先は `site/vendor/bootstrap/`、版は Bootstrap 5.3 系の固定版、取得元は公式配布（jsDelivr の該当版ファイル、または npm パッケージ `bootstrap` の `dist/css/bootstrap.min.css`）。取得したファイルの sha256 を生成記録（run-record）に残し、MIT ライセンス文を同ディレクトリに同梱する。生成器は相対パスで参照する。

3. **デザイントークンは、今すぐ共通パッケージ化せず、まず hackathon 側の「枠」の設計に UltraFlame の設計仕様形式（YAML フロントマター＋本文）を借りる形で小さく始める（対象は Web 用の design.md 側に限る。監査指摘 A8）。**
   根拠: トークン化の受け皿が hackathon 側にまだない（直書き2色のみ）。形式の借用はコード結合なしで可能で、将来 Tailwind の `@theme` や Bootstrap 変数へ写す際の原簿になる。パッケージ化（方式2）は消費者が増えてからでも遅くない。

4. **提出期限（11/04）に直結するデモ動画の制作を、UltraFlame のパイプラインに全面的には依存しない。**
   根拠: UltraFlame はリリース HOLD、negative スイートが意図的に失敗する既知のガード不備があり、検証済み環境は Windows のみ（`README.md`、`AGENTS.md`）。使う場合も、フォールバック（通常の編集手段）を残した範囲に限るべきであり、依存の判断は動画制作の開始時点（11/01 目安）で本人が行う。

5. **管理画面のライブラリ選定は行わない（保留）。**

6. **取り込みの中心は「設計仕様＋適合監査のペア」であり、提出範囲ではその最小実装までに絞る（§3）。** すなわち、設計仕様形式の実装（トークンの原簿）、機械検査としての WCAG コントラストチェックのゲート候補化、仕様（訴求設計ドラフト）との適合の人間確認、の3点である。求人インフォグラフィック等の大きめの機能は、実体の追加調査を経て、提出後の拡張計画に置く。
   根拠: §4.1 のとおり対象自体が未定義。選定の前提（画面の要否・生成方式）が決まった時点で、本書 §2 の比較を再利用して判断する。
