## 観点1: 様式が工程2の要求を満たすか

判定: 満たす

- 工程2の要求は、承認は記録への記入で行い「誰が、いつ、どの原本版と FACT 版に対して承認したか」を残すこと、矛盾があれば承認できない分岐とし「警告を無視する承認」を作らないこと（G-INV-3）、原本版または FACT 版が変われば承認を無効とし照合からやり直すことである（`docs/design/implementation-steps-v1.md:36-38`）。
- 様式はこれらを次の形で満たす。承認対象の指名はファイル名とハッシュによる単一形式に統一され（様式:6-11）、承認記録の置き場所は FACT ファイルに隣接させ FACT 版ごとに最大1つと定められた（様式:13-16）。フィールド定義は JSON の形で列挙され、approvalId、承認者、日時、対象の組（原本と FACT の ID・版・ファイル・sha256）、根拠（照合、スキーマ、逐語性）、範囲（対象、未記載項目、その扱い、効果）、有効性（無効化規則と状態）がすべて含まれている（様式:18-46）。承認不可の条件として、照合が「停止（矛盾あり）」の対象には承認記録を作らないこと、作成時は対象2ファイルの sha256 を再計算して manifest と指名に一致しなければ作らないことが、様式レベルの決まりとして明記された（様式:48-51）。
- 必須記録項目の列挙という工程1監査の申し送りへの回答になっている。上記のフィールド定義がそのまま必須項目の列挙として機能し、確定した承認記録にも全項目がそろっている（観点4）。未記載項目のステータスの記録方法も定義されている。承認記録の側では、対象 FACT（ハッシュで固定され、status が保持されている）の中で未記載であるキーを `scope.unstatedItems` に列挙し、「未記載は未記載として表示に残し、承認の対象に含めない」という扱いを併記する方式であり（様式:34-38）、記録の読み手が未記載の範囲と扱いを取り違える余地はない。
- 基本設計 §7 のゲート記録との関係では、本工程ではゲートの昇格は行われておらず、承認の仕組みをゲートとして扱う記述もないため、D8 の昇格承認の問題は生じていない。承認の取り消しと approvalId の連番規則は「残す未決」として様式に明示されており（様式:59-62）、勝手に決められていない。

## 観点3: 無効判定（checkApprovalValidity）の意味とテスト

判定: 様式の無効化規則と一致する（FACT 改変ケースの再現可能なテストあり）

- 様式の無効化規則は「原本または FACT の sha256 が本記録と異なれば無効とし、照合からやり直す」である（様式:40-44）。`checkApprovalValidity` は現在の両ファイルの sha256 を承認記録の指名と比べて有効・無効を返し、無効の場合は「原本または FACT のハッシュが承認記録と異なるため無効。照合からやり直す」という理由を返す（`src/approve.mjs:86-99`）。実施計画が求めた「無効の場合に次の手順が戻り値で分かること」も満たす。CLI では無効のときに終了コード 1 になる（同:127-136）。
- FACT のコピーを改変したケースで無効になることは、再現可能なテストとして残っている。テストは確定済み承認の写しを用意し、無改変の実ファイルでは有効、改変したコピーでは無効＋理由あり、となることを検証している（`src/approve.test.mjs:65-75`）。監査側の再実行でも pass した。確定した実際の承認記録に対しても監査側で CLI を実行し、`valid: true`（両ハッシュ一致）を確認した。
- 留意点として、この関数の返す `valid` は「版が承認時点と変わっていないこと」だけを意味し、承認の成立（status が approved で、approver と approvedAt が入っていること）は含まない。実際、下書き（status: draft）に対して実行すると `valid: true` が返り、status は併せて返される。様式の無効化規則自体はハッシュの一致に限られているため関数の意味は規則と一致しているが、工程3の入力条件（「承認済みで、かつ版が有効な FACT だけを入力とする」）では、status の確認と本関数の結果の両方を見る必要がある。これは工程2の不備ではなく、工程3への引き継ぎとして指摘一覧に残す（指摘1）。

## 実測・記録・判断の区別

- **実測（本セッションで確認した事実）**: Git の最新を取り直し、HEAD と作業ツリーを確認した。様式・実施計画・コード・テスト・承認記録・実行記録の実文を照合した。テストをリポジトリ外の出力先で再実行し、11件すべて pass と、コミット済み記録との一致（`runAt` を除く）を確認した。確定した承認記録と下書きに対して無効判定を実行し、確定記録で `valid: true`、下書きでも `valid: true`（status は draft）が返ることを確認した。原本と FACT の sha256 を作業ツリーと Git blob で再計算し、承認記録・manifest と一致した。下書きと確定記録の差分が status・approver・approvedAt の3項目だけであることを確認した。
- **記録に基づく事項**: 様式が本人の決定であること、本人が下書きを確認して確定したことは、様式と run-record の記録に基づく。工程2の実施コミットの作成者が本人の Git アカウントであることは、この記録と整合する傍証として扱った。
- **判断（監査としての判定）**: 総合判定「合格」、指摘1–4 を重大度「低」の観察事項として工程3へ引き継ぐことは、本監査の判断である。推測で埋めた箇所はない。
- **未確認事項**: 本人が下書きを確認したという行為そのものは Git の外の行為であり、独立した証跡では確認していない。確定実費にあたるものは本工程では発生していない（Muse Bot の推論費は未記録として理由が記録されている）。
