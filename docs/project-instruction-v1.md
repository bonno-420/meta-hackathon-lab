# プロジェクト開始指示（記録）

- 指示日: 2026-10-27

- 位置づけ: 本書はプロジェクトの方針・決定の典拠である。設計・監査の各判断は本書と `docs/decisions/` の決定記録を参照する。指示、判断、決定は Git に残し、あとから検証できるようにする（本人の運用原則）。

## 1. 今回作りたいもの

AIが目的を理解し、設計・制作・実行・監査・改善までを一貫して進め、実際の成果につなげる仕組みを開発する。単なるAIチャットやコード生成ツールではなく、成果物を評価し、失敗から学び、開発プロセスそのものも継続的に改善できる AI 開発・実行基盤を目指す。

プロダクトの具体的な要件と方向性は、既存のハッカソン応募資料（開始前準備資料）を正本とする。応募資料の内容を勝手に変更したり、独自の仮説を確定要件として扱ったりしない。

## 2. 中核となる開発思想（サイクル）

1. 初期企画・要件を確認する
2. 上位設計を作成する
3. 独立した監査工程で設計を評価する
4. 合格した設計を基に詳細設計と引き継ぎ情報を作成する
5. 再度監査を行い、合格した範囲を実装する
6. テストと成果物の監査を行う
7. 問題の原因を分析し、設計・実装・監査基準を改善する
8. 改善結果を記録し、次のサイクルに進む

監査では、初期の企画・要件と実際の成果物を照合する。必要に応じてユーザーペルソナによる評価も組み込む。

監査の判断は「合格」「修正」「前段階への差し戻し」を基本とする。重大なセキュリティ・安全上の問題は直ちに停止する。同じ経路で差し戻しが2回続いた場合は、自動ループを停止して人間に判断を求める。

## 3. AIの役割分担

役割分担は設計段階で検討し、実際に必要な構成を決める。想定する機能は次の4つ。

- 統括・調整役: 全体目標、進行、優先順位、各工程間の連携を管理する
- 設計役: 要件、システム構造、作業手順、引き継ぎ情報を設計する
- 実行役: 調査、制作、実装、テストなどを担当する
- 独立監査役: 設計や成果物を初期要件と照合し、合否と差し戻し理由を判断する

Wonder や Spark などのモデル・機能をどの役割に割り当てるかは、実際に利用可能な機能と費用を確認したうえで決定する。名称だけで役割や能力を決めつけない。

## 4. 開発プロセス自体も実験対象にする

プロダクトを作るだけでなく、プロダクトを作る AI のプロセスそのものを検証・改善することが重要な目的である。まず開発プロセスを設計し、そのプロセスを実際のプロダクト開発に適用する。その結果を評価し、プロセスを改善して再実行する。

各サイクルで可能な範囲で記録する情報:

- 使用した入力資料とコンテキストパックのバージョン
- 使用モデル、実行条件、プロンプトのバージョン
- 作成・変更した成果物
- 監査結果、差し戻し理由、修正内容
- 監査基準の追加・変更とその根拠
- トークン使用量、実費、所要時間、再試行回数
- 合格率、差し戻し率、改善結果

同一条件で再実行する再現性検証と、条件を変える改善実験は区別する。改善実験では、原則として一度に一つの主要要因を変更し、結果を比較する。

失敗から得た知見をそのまま恒久ルールにしない。新しい監査基準は候補として記録し、検証と承認を経て採用する。監査基準自体についても、重複、誤検知、過剰な複雑化がないか定期的に評価する。

## 5. Gitを唯一の正本とする

重要な作業、設計、意思決定、検証結果は Git に記録する。チャットだけに残して終わらせない。指示・判断・決定も Git に残し、あとから検証できるようにする。

追跡できる構成の対象: 応募資料と初期要件への参照、設計書とアーキテクチャ、意思決定記録と未解決事項、監査基準とそのバージョン、工程間の引き継ぎ情報、実装・テスト・監査の記録、実験条件、コスト、改善履歴。

既存のリポジトリ構成や AGENTS.md などのルールがある場合は、それを優先して確認する。既存資料を不用意に上書きせず、変更履歴が追える形で作業する。

## 6. 進め方

初期段階では、いきなり大規模な実装や並列作業を始めない。まず全体設計と最小実証の境界を明確にする。

コード変更、破壊的操作、本番環境への変更、外部への公開などは、必要性と影響を説明し、承認が必要なものについては本人の確認を得てから実行する。

## 7. 進め方への期待

指示を単なるタスク一覧として処理するのではなく、応募資料を理解したうえで、実現方法を自ら設計し、監査を受け、記録を残しながら改善する。ただし、独断で企画の目的を変えたり、不明点を事実として埋めたりしない。重要な判断には根拠を添え、選択肢とトレードオフを明らかにする。
