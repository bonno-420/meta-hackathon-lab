## 2. 実測で分かったこと（推測ではないもの）

- **抽出は安く、正確だった**: FACT 抽出 1 回は入力 362 / 出力 6,264 トークン、算出 $0.001289、約 45 秒（ループ2）。引用と行 ID は 15 項目すべて正確で、補完はなかった。費用の中心は Spark の実行ではなく監査側のパス回数になる（D5 の根拠）。
- **モデルの出力は型を明示しないと揺れる**: 未記載項目の value が「未記載」という文字列と空で揺れた（L-001）。プロンプトで型を明示する改訂（v1.1）で対処済み。
- **機械照合と人間確認の境界が実働した**: 数値の突合は機械、意味の対応は人間確認という分担で、E01（一致）と E02（矛盾で停止）の両方が期待どおりに動いた。再検証では、判定は機械の出力に人間確認を記入した複合であり、再導出の経路がない点が将来の道具改訂として残っている（L-025）。
- **費用は枠に対して誤差の範囲**: 累計は実験 $0.0024082（上限 $25）、製品実行 $0.002755（同 $15）。いずれも単価ベースの算出値で、確定は Billing 突合（11/01）待ち。
- **監査の往復は機能した**: 設計監査（ループ1）は「修正」で N1–N12 を出し、改訂版 v1.1 は合格。工程案は「修正」（S1–S12）→ 改訂 → 限定再監査で合格。ライブラリ設計も「修正」（G1–G5）→ 改訂 → 限定再監査で合格。差し戻し（前段階へ戻す）になった事例はまだない。
- **文書の着地には切り捨ての実例がある**: バイト照合（sha256）はコピーの正確さしか保証せず、内容の欠落を通してしまった（L-020）。着地時は行数・節構成・末尾まで見ることが手順として確定した。

## 3. 知見の主題（台帳 L-001〜L-029 の読み替え）

## 4. ライブラリ活用工程で得た設計上の知見（新規）

- 型の指標は効果ではなく流通量として扱う（模倣の多さは媒体の都合でも増える、という仮説を明記した）。承認の根拠は流通量ではなく検証と本人の判断に置く。
- 型の出所とライセンスは単一由来で持てない。全事例のうち最も弱い状態に合わせる規則を案とし、確定は未決（U8）に残した。確定までは登録ごとに事例の状態を列挙して確認を得る暫定運用で回る。
- コピーの線引きの照合は原文の保持を前提とする。「型だけを残す」判断（U2）とは連関するため、判断材料に含めた。機械で測るのは重なりと数値の由来までで、特徴的かどうかは人間が確かめる。
- 完成文と原文そのものは在庫化しない。在庫化するのは型だけであり、散文評価は適合監査とは別の層として、観点を候補 → 検証 → 承認 → 昇格で育てる（ゲートの仕組みと同型）。
