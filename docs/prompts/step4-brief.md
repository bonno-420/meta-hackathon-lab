## 作業

### 1. 再検証の道具の実装

- 再検証を行う小さなスクリプトを `src/` に置く（提案名: `src/verify.mjs`）。構造は工程1〜3の道具に倣い、import 可能な関数（入力同一性の検査、再検証の実行、判定）と CLI を分ける
- 道具は既存の検査を import して再利用し、新しい物差しを作らない。根拠検査は `src/generate.mjs` の `checkGrounding` を、承認の有効性は `src/approve.mjs` の `checkApprovalValidity`（とハッシュ計算 `sha256File`）を import する。入力同一性のうち承認まわりの判定は、工程3の開始条件と同じもの（`src/generate.mjs` の `checkGenerationInput`）を再適用する
- 道具は API を呼ばない。モデルも API キーも使わない。再検証はオフラインで完結し、結果は JSON として出す（記録の置き方は作業7）
- ハッシュの定義は F1（ファイルの保存バイト列そのものに対する sha256、UTF-8/LF）に統一する

### 2. 機械検査（a）: 入力同一性

再検証の前提として、生成物が「承認時点の版の、承認済み FACT に対する生成物」であることを、現在のファイルの実バイトから確認する。検査対象の原本・FACT ファイルは、生成物ヘッダの `input.original.file` と `input.facts.file` が指すものとする。次の3点をすべて満たす場合に限り、後段の検査に進む。

1. **ヘッダと現在のファイルの一致**: 生成物ヘッダの `input.original.sha256` と `input.facts.sha256` が、現在の原本・FACT ファイルの実バイトから再計算した sha256 と一致すること（ファイル名もヘッダの指すものと一致すること）
2. **承認記録の特定**: 生成物ヘッダの `input.approvalId` が、渡された承認記録の `approvalId` と一致すること
3. **承認の有効性**: 承認記録の `status` が `approved` で approver と approvedAt が入っていること、かつ `checkApprovalValidity` を実行時点で再計算して `valid: true` であること（工程3の開始条件と同一の2条件とする。承認記録内に静的に残っている `validity.invalidated` は根拠にしない。下書きは再計算で `valid: true` でも不合格とする — 工程2監査の観察事項1の落とし穴への対策を、再検証側でも固定する）

- どれか1つでも満たさなければ、生成物は失効したものとして不合格にする（どの点が一致しなかったかを区別して記録する）。この場合は根拠検査（作業3）に進まない。対象の同一性が担保できない生成物に対して、合格を出す経路を作らないためである

### 3. 機械検査（b）: 根拠検査の再実行

- 入力同一性が確認できた生成物について、`checkGrounding` を import して再実行する。渡す生成物・FACT・原本は、作業2で同一性を確認したファイルの組とする
- これは生成時と同じ物差しで再測る設計である。再検証の独立性は物差しを変えることではなく、(i) 生成側の実行記録や申告値を判定材料にしないこと、(ii) 入力の同一性を現在のバイト列から取り直すこと、(iii) 検査を再検証側の実行として再び走らせること、で担保する。この設計の是非は監査の対象とする（§9）
- `checkGrounding` が機械で強制する範囲は、工程3監査の観察事項1のとおり限定されている（円金額と時刻の逐語、代表的な数値項目の引用時の値の保持、未記載の断定のパターン、月20日勤務の仮定と月収の非保証の文言）。期間・個数などの数量表現と、文と根拠の意味の対応は機械では覆えないため、作業4の人間の確認に残る
- grounding の結果（pass / fail、checked 件数、issues の内訳）は、工程3の `generation-run.json` の申告値とは独立に、再検証の結果として記録する

### 4. 人間の確認（意味の対応）

- 機械検査で覆えない「意味の対応」は、工程3監査の観察事項1の引き継ぎどおり人間の確認に残る。再検証の合格は、機械検査（作業2・3）の pass と、本項の人間確認の両方を条件とする
- 確認者は統括と本人とする。対象は生成物の全文化とし、文ごとに次を確認する
  1. 文が実際に使っている項目と、その文に付けられた factKeys・sourceLines が対応しているか（使っているのに根拠に付けていない項目、使っていないのに付けられた項目がないか）
  2. 期間・個数などの数量表現（例: 契約期間3か月）が、FACT の値と意味のうえで一致しているか
  3. 否定・条件の意味が反転していないか（例: 「保証しない」が保証と読める文になっていないか）
  4. 公開や申込の受付と読める表現が生成物に混ざっていないか（混ざっていれば不一致として扱う。`docs/design/implementation-steps-v1.md` 工程4の定め）
- 確認の記録形式: 再検証結果 JSON に人間確認のセクションを持たせ、文ごとに確認結果（対応あり／不一致の内容）、確認者、確認日時を残す。run-record にも、人間確認を実施した事実と結果の要約を残す。全文化の確認が終わるまで、再検証は合格にならない
- 引用粒度の原則（候補）は本工程でも昇格しない（昇格は本人の承認事項、D8）。観察事項1が求めた「機械検査の範囲と、意味の対応は人間の確認に残ることの明記」は、この作業3・4による再検証側の分担の固定をもって実施形とする
- LLM による意味チェックは今回入れない。理由は、原則（候補）が定める機械検査の範囲の限定と整合させるためである。機械で覆えない範囲を LLM の判定で覆ったことにすると、検査範囲の境界が曖昧になり、「機械検査＋人間の確認」という分担自体の検証ができなくなる。LLM による意味チェックは将来の改善実験の候補として記録に留めるに限り、本工程では実施しない

### 5. 判定の出し方（観察事項2の反映）

- 判定は、生成物の status や工程3の実行記録の申告値から出さない。再検証側で得た次の3点だけで出す: 入力同一性の結果、作業3の grounding の再実行結果、作業4の人間確認の結果
- **合格**: 3点すべてが満たされた場合とする。効果はデモ内プレビューの許可までであり、公開の許可ではない（G-INV-4）。この効果の範囲を、再検証結果 JSON と run-record の両方に明記する
- **不合格**: 理由を分類して記録する — 入力同一性の不一致（失効）、grounding の不合格（issues の内訳）、人間確認での不一致（対象文と内容）。不合格は工程3への差し戻し扱いとする。再検証側では生成物を改変しない（直す場合は工程3の再実行であり、再実行で得た生成物は改めて再検証の対象になる）

### 6. テスト設計

検証は再現可能なテストファイルとして残す（提案名: `src/verify.test.mjs`）。結果は `loops/loop-009/check-verification.json` に記録する。再検証の道具は API を呼ばないため、テストもすべてオフラインで再現可能である。改変ケースは、リポジトリ内の固定ファイルを書き換えず、一時フォルダにコピーを作って行う（工程3のテストの流儀を継承する）。

| 系 | ケース | 期待 |
|---|---|---|
| 正常系 | loop-008 の実生成物（原本 v1 × FACT v1 × 承認 FICT-J01-approval-1） | 入力同一性が確認でき、根拠検査の再実行が pass する（機械検査 pass。再検証の合格そのものは作業4の人間確認を経て確定する） |
| 改変検出 | 金額を書き換えた生成物のコピー（例: 時給1,500円を1,700円に） | 根拠検査で検出され、不合格になる |
| 改変検出 | 未記載項目の断定文を混入させた生成物のコピー（例: 寮の有無を断定する文の追加） | 根拠検査で検出され、不合格になる |
| 改変検出 | 未知の factKey を引く文を混入させた生成物のコピー（例: workLocationX） | 根拠検査で検出され、不合格になる（工程3の生成系テスト補強3ケースと同種のものを、再検証側でも検出できることの固定） |
| 改変検出 | 未知の行 ID（例: L99）を引く文、根拠を持たない文（factKeys が空）を混入させた生成物のコピー | 根拠検査で検出され、不合格になる |
| 入力同一性 | FACT を差し替えた組（生成物ヘッダの FACT のハッシュと、現在の FACT ファイルの実バイトが一致しない） | 失効として不合格になる。根拠検査には進まない |
| 入力同一性 | 承認記録が下書きの組（`loops/loop-007/approval-draft.json` を承認記録として渡す） | 不合格になる。再計算の有効性が `valid: true` でも不合格であることを明示的に確認する |
| 入力同一性 | ヘッダの approvalId を書き換えた生成物のコピー | 不合格になる（承認記録を特定できない） |

- あわせて、既存スイート（工程1の12件とオフライン検証6件、工程2の11件、工程3の23件）の回帰がないことを確認する

**監理ラインに見てほしい点**

- 入力同一性の担保方法: ヘッダのハッシュと現在のファイルの実バイトの照合、承認記録の特定、承認の有効性の再計算という3点の組み合わせで、「承認時点の版の承認済み FACT に対する生成物」であることが担保できているか
- 生成時と同じ `checkGrounding` を再実行する設計の是非: 物差しを共有することが再検証の独立性を損なわないか。独立性の担保を「申告値を材料にしない・同一性を取り直す・再実行する」に置く設計の評価を含めて見てほしい
- 人間確認の記録形式: 全文化の確認が追跡可能な粒度（文ごとの結果、確認者、日時）で残っているか。機械検査と人間の確認の境界が、記録のうえでも区別できているか
- 判定が status に依存していないこと: 生成物の status や工程3の実行記録（`generation-run.json`）の申告値を、判定の根拠にしていないことの再確認
