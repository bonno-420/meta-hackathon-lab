## 作業

### 1. 承認の道具の実装

- 承認記録（JSON）を作る小さなスクリプトを `src/` に置く。凝った UI は作らない（ステップ v1 工程2）
- 処理の順序: (a) 原本と FACT の sha256 を F1 の定義で再計算し、manifest の記載と一致することを確認する。一致しなければ承認を作らない。(b) 承認の根拠となる照合記録（対象 FACT に対する照合が「一致」で、「停止（矛盾あり）」でないこと）を確認する。根拠は様式の basis に参照として残す。(c) 様式どおりの承認 JSON の下書きを作る
- **承認の確定は本人の行為である。** 統括は下書きまでを作り、本人が内容（対象の組・根拠・未記載項目の扱い）を確認して承認した時点で、確定した承認記録として保存する。本人の明示確認なしに approver と approvedAt を埋めない

### 2. 無効判定の実装

- 現在の原本・FACT のハッシュと承認記録を比べ、有効・無効と理由を返す関数を、import 可能な形で置く（工程4の再検証からも使う）
- 無効の場合は「照合からやり直す」が次の手順であることを、戻り値と記録で分かるようにする

### 3. 完了条件3点の実行記録（ステップ v1 工程2の完了条件）

1. 正常系: FICT-J01 原本 v1 × FACT v1 について、承認の下書き → 本人の確定 → 承認記録の成立までを通す
2. 矛盾系: 矛盾のある FACT（テスト用フィクスチャ）では承認が作成できないことを示す
3. 版変更系: FACT のコピーを改変したケースで、無効と判定できることを示す

- 検証は再現可能なテストファイルとして残し（工程1の F2 で標準になった形）、結果を `loops/loop-007/` に記録する

## 費用

- 実 API の実行はない（機械処理のみ）。Muse Bot の推論費は未記録（理由つき）とする

## 停止条件

- 様式が未決定のまま着手しない
- ハッシュが manifest と一致しない対象には承認を作らない
- 本人の確定なしに承認記録を成立させない
