# プロンプト: ループ1・設計監査パス（独立監査役）

用途: VS Code 上の Muse Code に、このリポジトリ内で設計の独立監査を実行させるための指示文。
前提: 監査対象の設計一式（context-pack-v1 / basic-design-v1 / review-notes-v1）は main にコミット済み。
このプロンプト自体のバージョン: v1（2026-10-27）

---

このリポジトリの `AGENTS.md` と `README.md` を最初に読んでください。

今回は「独立監査」フェーズです。あなたは設計者とは独立した監査役として振る舞ってください。
コードの実装、設計文書の書き換え、コミットは行わないでください。成果物は監査レポートのドラフト作成までです。

## 読むもの（この順で）

1. `docs/design/context-pack-v1.md` — 確定事実（参加者ステータス、ルール、クレジット、環境の実測状態、プロダクト設計の要約、進め方）
2. `docs/design/basic-design-v1.md` — 監査対象の基本設計
3. `docs/design/review-notes-v1.md` — 照合結果、不明点・矛盾点（C1–C7）、判断事項（D1–D8）。すでに自己申告されている論点

## 監査の観点

1. **要件との照合**: 基本設計が、応募資料由来の確定要件・制約（context-pack §5 と review-notes §2）から逸脱していないか。特に「架空データのみ」「止める条件」「警告を無視する承認を設けない」「再検証の合格は公開承認ではない」を侵していないか
2. **確定・仮説・未確認の分離**: 基本設計の中で、未確認事項が確定した前提として使われている箇所はないか（例: Wonder の利用可能性、モデル割当、トラック）
3. **監査設計自体の妥当性**: 判定（合格 / 修正 / 前段階への差し戻し）、即時停止条件、同一経路 2 回差し戻しでの人間へのエスカレーションが、運用可能な具体性で書かれているか。抜けている停止条件はないか
4. **ゲート管理**: 候補 → 検証 → 承認 → 昇格の流れと、ゲート自体の監査（重複・誤検知・肥大化）が、実際に回せる手順になっているか
5. **実験設計**: 再現性検証と改善実験の区別、単一要因変更の原則、記録項目が、9 日間・ソロ・$150 の制約の中で実行可能か。重すぎる記録はないか
6. **コスト**: 予算案（実使用 $100 ＋ 予備 $50、$75 で探索停止）と基本設計の活動量が見合っているか。費用が読めない活動があれば指摘すること
7. **矛盾・未決の扱い**: C1–C7 は正しく引き継がれているか。新たに見つけた矛盾・不明点があれば追加すること。既存の記述を勝手に上書きしないこと

## 出力

- `docs/design/design-review-loop1.md` を新規作成し、監査レポートのドラフトを書いてください（コミットはしないでください）。
- 形式: 観点ごとに「判定（合格 / 修正 / 差し戻し相当）」「根拠（どの文書のどの記述か）」「修正案または確認すべき点」を書く。総合判定も先頭に置く。
- 確認できない情報は推測で埋めず「未確認」と明記すること。情報源を使った場合は URL と確認日を付けること。
- 最後に、D1–D8 のうち監査の立場から先に決めるべきだと思うものの順序と理由を付けてください。

外部サービスへの登録、課金、デプロイ、ファイルの変更（上記ドラフト作成を除く）は行わず、報告して次の指示を待ってください。
