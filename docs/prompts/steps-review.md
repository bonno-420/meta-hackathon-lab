# 文脈パック: 実装工程案の監査

- 位置づけ: 設計 → 監査の監査パス。統括が用意した工程案を、独立した監査として Wonder が検証する
- 監査対象: `docs/design/implementation-steps-draft.md`

## 最初にやること

1. `git status` を確認し、マージ未完了などの異常があれば作業を始めずに状態を報告する。次に `git pull --ff-only` で最新化する
2. 次を読む: `docs/design/implementation-steps-draft.md`、`docs/design/basic-design-v1.1.md`、`docs/design/design-review-loop1.md`、`docs/project-instruction-v1.md`、`docs/roadmap-v1.md`、`docs/decisions/` の全件、`docs/model-selection.md`、リポジトリの `AGENTS.md`

## 監査の観点

1. **抜け漏れ**: 統合デモの完成と提出に必要な作業で、工程案に落ちているものはないか。例: 提出フォームの入力項目の事前確認、デモデータと原本の固定方法、README や再現手順、動画台本との接続、ライセンスや帰属の表記、Cloudflare のセットアップ手順そのもの
2. **順序と依存**: 工程の並びは依存関係に合っているか。承認 → 生成 → 再検証の実装順序、プロンプト v1.1 実験と統合実装の前後関係、スキーマ完全性チェックを追加する位置は適切か
3. **日程の現実性**: `docs/roadmap-v1.md` のマイルストーン（M2 10/30 統合完成、M3 11/01 動画、M4 11/02 提出）に収まるか。作業量の見積もりが甘い工程はどこか
4. **設計との整合**: basic-design v1.1 の不変条件ゲート（G-INV-1〜4）、停止条件（S-1〜S-6）、記録仕様（必須項目）、ゲート管理の流れと矛盾しないか
5. **Cloudflare Pages の妥当性**: 静的な生成物の置き場として適切か。MJ の本番環境との分離は十分か。公開する内容に、含めてはいけない情報（実データ、秘密情報、未確定の主張）は混ざらないか。提出ルールとの関係で問題はないか
6. **リスク**: 一番転びやすい工程はどこか。その場合の保険（範囲の縮小、前倒し、順序の入替）は用意されているか

## 成果物と進め方

- 監査結果を新規ファイル `docs/design/implementation-steps-review.md` に記録する。判定は「合格 / 修正 / 前段階への差し戻し」のいずれかとし、観点ごとに根拠を示す。新たな論点があれば番号（S1, S2, ...）を付けて列挙する
- 工程案 itself は書き換えない。修正が必要な場合は、修正案の提示までとする
- コミットはしない（作業ツリーに残す）
- 報告は、実測・記録・推測を分けて書く
