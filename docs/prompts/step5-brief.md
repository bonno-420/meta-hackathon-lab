## 作業

### 1. 統合ランナーの実装

- 統合実行を行う薄いランナーを `src/` に置く（提案名: `src/run-demo.mjs`）。既存の道具を import（関数）または CLI 連携で順に実行し、結果を1つの統合結果 JSON に集約する
- ランナーは新しい判定ロジックを作らない。各工程の合否は、その工程の道具の出力（照合の判定、承認の有効性、生成の入力チェックと根拠検査、再検証の判定）そのもので決める。ランナー自身が合格を作る経路（前段の不合格を上書きする、検査を省略する）を持たない
- 後段は前段の合格でのみ実行する。前段が止まる条件（矛盾、未記載の必須条件の未解決、入力同一性の不一致）では、後段の道具を呼ばず、止まった工程と理由を統合結果に記録する
- 実行はライブとする。抽出（工程1）と生成（工程3）は API を呼ぶ（モデルは各道具の既定どおり `muse-spark-1.3-contributor`）。API キーは制作ラインの環境の既存の供給方法によるものとし、キー値を記録や成果物に書かない

### 2. 統合実行（E01）: 各工程の接続と承認の扱い

E01 は次の順で通す。

1. **抽出・照合**: `src/extract-and-check.mjs` のライブ実行で FICT-J01 v1 の抽出と照合を行い、E01 の判定が「一致」になることを再現確認する。あわせて作業3の E02 評価も同じ実行で得る
2. **承認**: 承認は人間の行為であり、統合実行では新たに作らない。固定済みの FACT v1 に対する承認記録 `FICT-J01-approval-1` を入力とし、`checkApprovalValidity` の再計算と status の確認で有効性を再確認する（工程3の開始条件と同一の組み合わせ）。抽出の再実行で得た FACT 候補が固定済み FACT v1 と食い違う場合は、その時点で止めて記録する（承認は FACT v1 の組にのみ成立しているため）
3. **生成**: 工程3の入力チェック（status = approved ＋有効性の再計算の AND）を通過した場合に限り、`runGeneration` で生成をライブ実行し、本ループの生成物を得る。入力チェックで拒否された場合は API を呼ばずに止める
4. **再検証**: 得られた生成物に `runVerification` を実行する（入力同一性＋根拠検査の再実行）。最終判定は作業4の人間確認を経て確定する

### 3. 停止系（E02）と止まる条件

- E02 は照合で停止することを統合実行でも示す。`src/extract-and-check.mjs` の E02 評価（要約側の時給1,700円が FACT の1,500円と矛盾）は「停止（矛盾あり）」となり、E02 については承認・生成・再検証・プレビューを実行しない。停止理由（矛盾の内訳）は統合結果と run-record に残す
- E02 に承認記録は存在しない（工程2の G-INV-3: 矛盾で停止した対象に承認記録を作らない）。統合実行でも E02 の承認を試みない
- 一般の止まる条件として、矛盾の検出、未記載の必須条件の未解決、入力同一性の不一致を扱う。いずれも「警告を無視して進める」経路を作らない

### 4. 再検証と人間確認の扱い（統合実行内）

- 統合実行の再検証は、工程4と同じ分担（機械検査＋意味対応の人間確認）とする。人間確認は統括と本人が、統合実行で得られた生成物の全文化について行い、結果は本ループの再検証結果 JSON の人間確認セクションに記録する
- ランナーの自動実行は機械検査までとし、最終判定が pending-human-confirmation の間はプレビュー（作業5）に進まない。人間確認を省略・形式化して公開まで自動で進む経路は作らない（L-026 の前提の維持。物差しの共通モードの受け皿は人間確認である）
- 引用粒度の原則（候補）は本工程でも昇格しない（昇格は本人の承認事項、D8）

### 5. プレビューの生成（入力の限定と文面の無編集）

- プレビューの生成器（提案名: `src/build-preview.mjs`、または `src/run-demo.mjs` の一部）は、入力を本ループの生成物とその再検証結果 JSON の組に限定する。再検証結果の `verdict` が pass（status: pass、pass: true）であることを生成器自身が確認し、pass でない場合は HTML を生成しない
- 生成先はリポジトリの `site/` とする（steps 工程5の定め）。構成は次のとおりとする
  1. **LP 本文**: 再検証済みの7文をそのまま、生成物の順序どおりに表示する
  2. **検証パネル**: 文ごとの根拠対応（factKeys・sourceLines）、再検証の結果（入力同一性・根拠検査・人間確認・最終判定と、その効果はデモ内プレビューの許可までであること）、未記載項目（更新の有無・寮）の扱い（未記載であることの表示）
  3. **E02 の停止表示**: 照合で停止した状態と停止理由の表示（生成物ではない。停止の記録の表示として扱う）
  4. **プロジェクト説明と記録へのリンク**: 架空の求人だけを使うデモであることの明示と、GitHub リポジトリ（記録の正本）へのリンク
- **再検証済みの文面は編集しない**。LP 本文の7文は、生成物の text とバイト一致させる。文体の調整（L-022）は表示方法の範囲（HTML の構造、見出しや段落の組み立て、スタイル）に限り、文そのものを書き換えない。文を書き換える場合は、工程3の再実行（生成）と工程4の再検証をやり直し、新しい生成物として本工程の対象にすること

### 6. ホスティングと公開前チェック

- Cloudflare Pages の新規プロジェクト（ハッカソン専用）を作成し、`site/` をデプロイする。プロジェクト名は実施時に決めて run-record に記録し、公開 URL（pages.dev のサブドメイン）も記録する。デプロイは制作ラインの環境から wrangler で行う
- **MJ（mj-staff.co.jp）のゾーン・DNS・既存のプロジェクトや Worker には一切触れない**。デプロイ先は新規プロジェクトのみとし、MJ の本番環境と混ざる設定（カスタムドメインの追加を含む）をしない
- デプロイの前に、公開前チェックを steps 工程5の定めどおり行い、結果を記録に残す: (a) LP プレビューに架空の求人であることが明示されている、(b) 実データ・秘密情報・未確定の主張が混ざっていない、(c) 再検証の合格を公開承認と読める表現にしていない（G-INV-4）。1つでも満たさなければ公開しない
- プレビューは架空データのみで構成し、実在の求人・応募者情報・個人情報は含まない
- 公開プレビューは提出の必須物ではない。セットアップやデプロイが遅れた・失敗した場合は、作業9の切り離しに従う。Pages の規約や料金の詳細は未確認であり、本ブリーフでは公開可否や費用を断定しない

検証は再現可能なテストファイルとして残す（提案名: `src/run-demo.test.mjs`。プレビュー生成器のテストを含む）。結果は `loops/loop-010/check-verification.json` に記録する。改変ケースは、リポジトリ内の固定ファイルを書き換えず、一時フォルダにコピーを作って行う。ライブ実行を伴う確認はテストと分け、作業8の実行記録として残す。

| 系 | ケース | 期待 |
|---|---|---|
| 統合（E01） | 固定した入力で統合実行を通す（ライブ実行の記録として確認） | 全工程が通り、再検証が合格（人間確認を経て確定）し、プレビューが生成される |
