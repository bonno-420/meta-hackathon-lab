## 改訂項目（監査の修正案に対応するもの）

1. プロダクト不変条件ゲートを明記する（観点1）: 4不変条件（架空データのみ、止める条件、「警告を無視する承認」を設けない、再検証の合格は公開承認ではない）を §6 または §7 に列挙し、各条件の検査方法（機械検証／人間確認の別）を付ける
2. §4 に「プロダクト実行時のモデル割当は本書の対象外である」と明示する（C2）
3. 監査の三段階判定（合格／修正／前段階への差し戻し）の定義表を追加する: 使い分けの基準、各判定に必須の付帯物（理由の書式、再監査の要否）
4. 停止条件を一表に統合する（N2）: §6 と §10 に分散した停止条件を一本化し、新規性リスク（期間外コードの混入）と実データ混入を加える。発動時の手順（通知先は本人、記録先は当該ループの記録、再開条件）も付ける
5. 「同じ経路」を定義する（推奨: 同一ゲートIDでの連続差し戻し）。「自動ループを停止」の表現は、現行運用（文書と Git による手動運用）に合わせて言い換える（N3）
6. ゲートの最小レコードを定義する（ID、版、検査対象、合否基準、由来、状態: 候補／検証中／有効／撤回）。ゲート自体の監査の契機を具体化する（各ループ終了時＋ゲート5件到達時、実施者は監査ライン）。`docs/gates/` の構成案の採否は本人の判断事項として、v1.1 では未決と明示する
7. 初回パスの例外規則を追加する（N7）: ゲートが存在しない初期のパスはゲート参照なしで開始し、得られた候補はそのループの終了時に登録する
8. 記録項目を必須と任意に分ける（N5）: 必須は入力版、出力、監査結果、実費。必須の欠落は監査で「修正」判定とする規則を付ける
9. 再現性検証の実施契機を限定する（観点5）: 監査で結果の信頼性が争点になった場合のみ。同条件の再実行を常時必須にしない
10. コスト台帳の表現を一本化する（N6）: 同一台帳に区分列（API 費／エージェント推論費）を設ける形に統一する
11. ペルソナレビューの発動条件に候補を書く（N11）: 例として、LP生成の初回実査、提出直前の最終監査。最終決定は本人事項であり、候補として提示するに留める
