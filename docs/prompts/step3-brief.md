## 目的と範囲

- 承認済み FACT v1（FICT-J01）のみを入力として、LP 文面（生成物）を Spark 1.3 系モデルで生成する

- 生成物はデモ内プレビューの材料であり、公開物ではない。再検証（工程4）の合格をもって初めてプレビュー許可の対象になる（G-INV-4）

## 作業

### 1. 生成の道具の実装

- LP 文面を生成する小さなスクリプトを `src/` に置く（提案名: `src/generate.mjs`）。凝った UI は作らない（ステップ v1 工程3）
- 構造は工程1・工程2の道具に倣い、import 可能な関数（入力チェック、生成、根拠の検査）と CLI を分ける。工程4（再検証）が生成物と根拠の対応を import して使える形にする
- モデルは Spark 1.3 系とする。実装は `src/extract-and-check.mjs` の流儀（モデル `muse-spark-1.3-contributor`、エンドポイント `https://api.meta.ai/v1`、API キーは環境変数 `MODEL_API_KEY` からのみ読み、決して記録しない、同時実行 1 件・自動再試行なし）を継承する
- 生成プロンプトは版を持つ（提案名: `lp-generate-v1`）。プロンプトには、承認済み FACT の stated 項目だけを材料として渡し、未記載項目は「未記載である」という情報としてのみ渡す（値は渡らない。後述の作業3）
- 生成の出力は JSON として保持し、文ごとに次を付ける: 文の本文、根拠とする FACT 項目の key（複数可）、原本の行 ID（複数可）。行 ID を持たない文は生成物に含めない（ステップ v1 工程3の完了条件）

### 2. 入力チェック（工程2監査の観察事項1の反映）

生成の開始条件は、次の2つを**両方**満たす場合に限る。どちらか一方だけでは開始しない。

1. **承認が成立していること**: 承認記録の `status` が `approved` であること（あわせて approver と approvedAt が入っていることを確認する）
2. **版が有効なこと**: `src/approve.mjs` の `checkApprovalValidity` を実行時点で再計算し、`valid: true` であること

- 承認記録内に静的に残っている `validity.invalidated` の値は根拠にしない。常に、対象2ファイルの現在のバイト列から再計算して判定する
- 下書き（status: draft）は、`checkApprovalValidity` が `valid: true` を返しても生成を拒否する。これは観察事項1が実測で示した落とし穴（下書きでも valid: true になる）への直接の対策であり、テストで固定する（作業5）
- 入力チェックは API 呼び出しより前に完了させる。拒否した場合は API を呼ばず、費用を発生させない。拒否の理由（status 不一致か、ハッシュ不一致か、承認記録の不在か）を戻り値と記録で分かるようにする

### 3. 未記載項目の扱い

- FACT v1 の未記載項目は renewal（更新の有無）と housing（寮の有無と費用）の2件であり、値は null である。承認の範囲は stated 項目のみで、この2件は承認の対象外である（承認記録の scope）
- 生成物でこの2件を事実として断定しない。「更新あり／なし」「寮あり／なし」等の値の主張は、いかなる文にも含めない
- この2件に触れる文を作る場合、その文は「未記載である」こと自体だけを述べる形に限る（原本 L02・L06 の記述どおり）。触れないことも許容するが、断定への言い換えは許容しない
- stated 項目でも、値の性質を変える言い換えをしない。特に monthlyDaysAssumption（月20日勤務）は「試算用の仮定」であり、monthlyIncomeGuarantee は「保証しない」である。月収の見込み額の提示や保証と読める表現は、仮定を事実化するものとして作らない（G-INV-2）

### 4. 引用粒度の原則（L-016 への回答。候補）

工程1の再現性確認では、FACT の逐語一致は 15件中7件で、差分8件はすべて表現の粒度差（quote の範囲の取り方、value の言い回し、引用末尾の句読点）であり、意味・数値・行IDの対応は全件一致した（`loops/loop-006/run-record.md`）。この実測を踏まえ、工程3では生成文と根拠の対応付けを次の原則（候補）で固定する。

1. **対応付けの単位は文とする**。生成物の1文は、根拠とする FACT 項目の key と原本の行 ID の両方を保持する。key だけ、行 ID だけの対応付けは不完全として扱う
2. **数値と条件は FACT の値を逐語保持する**。金額・時刻・期間・割合などの数量表現と、否定・条件の表現は、FACT の value（および normalized）から換算・丸め・単位変換・言い換えで意味を変えない。対象の例: 時給1,500円、月上限10,000円、09:00〜18:00、休憩60分、実働8時間、契約期間3か月、「保証しない」、「試算用の仮定」
3. **quote は固定済み FACT v1 のものをそのまま引き継ぐ**。工程1で揺れたのは抽出時の quote の範囲の取り方であり、工程3は抽出をやり直さない。生成文の根拠は「FACT 項目の key ＋ 原本の行 ID ＋ FACT に固定された quote」の三点で保持し、生成文そのものを quote とは扱わない
4. **1文に複数項目を束ねる場合は、束ねた全項目の key と行 ID を列挙する**。一部の項目だけを根拠として付ける部分的な根拠付けはしない
5. **FACT に対応しない文は作らない**。挨拶・訴求・評価などの修飾文も、対応する FACT 項目がなければ生成物に含めない（ステップ v1 工程3の最小形の定めと同旨）

- この原則は**候補**である。本実施ではこの候補に従って生成と検査を行うが、ゲートへの昇格や恒久ルール化は本人の承認事項であり（D8）、本工程では昇格しない。監査では、候補どおりに運用できたかと、候補自体の妥当性を検証の対象とする

### 5. 矛盾ケース（E02）の扱い

- E02 は照合で「停止（矛盾あり）」となったケースであり、承認記録は存在しない。存在しないのは未実施だからではなく、様式 §4 と G-INV-3 により、停止した対象への承認記録の作成自体が禁止され、工程2の道具でも作成が拒否されることを確認済みである（`loops/loop-007/check-verification.json` の `draft-refused-for-e02-contradiction`）
- したがって E02 に対する生成は、承認記録の不在を理由に、入力チェックの段階で拒否される。生成プロンプトに到達させない
- この拒否をテストで示す（作業6）。あわせて、拒否が API 呼び出しの前に起きることを確認する

### 6. テスト設計

検証は再現可能なテストファイルとして残す（工程1の F2 で標準になった形。提案名: `src/generate.test.mjs`）。結果は `loops/loop-008/check-verification.json` に記録する。

| 系 | ケース | 期待 |
|---|---|---|
| 入力チェック | 承認済みペア（FICT-J01 原本 v1 × FACT v1 × 承認 FICT-J01-approval-1） | 生成の開始が許可される |
| 入力チェック | 下書きの承認記録（`loops/loop-007/approval-draft.json`。status: draft） | 拒否される。`checkApprovalValidity` が valid: true を返す条件でも拒否されることを明示的に確認する |
| 入力チェック | FACT のコピーを改変した組 | 再計算で無効と判定され、拒否される（理由に「照合からやり直す」相当が含まれる） |
| 入力チェック | E02（承認記録なし） | 承認記録の不在を理由に拒否され、API が呼ばれない |
| 生成（正常系） | 承認済みペアで実生成 | 生成物が得られ、全文化が根拠を満たすこと。各文が根拠とする FACT 項目の key と原本の行 ID（いずれも実在するもの）を保持し、数値・時刻・条件は FACT の値の逐語であること。根拠検査が pass すること |
| 生成（未記載） | 未記載項目（renewal・housing）の断定を含む出力 | 値の断定（「更新あり／なし」「寮あり／なし」等）が根拠検査で検出されること。そのような断定が実生成物に現れていないこと |
| 生成（根拠検査） | FACT にない情報を含む出力（捏造した金額、実在しない key・行 ID を引く文、根拠を持たない文） | 根拠検査が検出して不合格にすること |

- 生成系の検証の置き方（実 API をテストファイル内で繰り返し呼ばない形にするかどうか）は、工程1・工程2のテストが API を呼ばない再現可能な形だったこととの整合で判断し、判断と理由を run-record に残すこと

- 本実施は工程3の初回実施である。プロンプトや条件を変えての再実行は改善実験として、再現性検証と区別して別に記録する
